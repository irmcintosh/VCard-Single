# VCard Native V1.2.1 — Quick Card Widget Enhancement Implementation Plan

**Date:** 2026-11-05  
**Status:** Proposed for owner review; **no widget source changes authorized by this document**.  
**Baseline:** V1.2.0 Quick Card widget; M1 country dropdown implemented and visually approved.  
**Scope:** M2 responsive professional-title presentation and M3 existing widget defects only.

## 1. Objective

Improve the **existing** Quick Card widget without building new widget types or requiring the owner to perform a separate ADB/launcher measurement campaign. Use responsive width-and-height rules with conservative fallbacks; verify visually during ordinary implementation testing. Grid labels are **design scenarios, not guaranteed dp measurements**.

## 2. Existing implementation (Codex source investigation; not independently compiled here)

- Android 12+ `RemoteViews(Map<SizeF, RemoteViews>)` in `QuickCardWidgetProvider.kt`.
- Four logical classes: VeryNarrow (120×48 dp), Compact (180×48 dp), Standard (120×160 dp), Expanded (260×120 dp).
- Three XML layouts: `quick_card_widget_compact.xml`, `quick_card_widget_standard.xml`, `quick_card_widget_expanded.xml`.
- Existing stored professional title and show-on-card preference must remain unchanged.
- Existing problems: cramped title in VeryNarrow, potential avatar/menu collision in narrow Standard, large-font text clipping in Expanded, and possibly stale font-dependent presentation after configuration changes.
- **Important:** Neither `VeryNarrow` nor `Compact` is guaranteed to equal a launcher 2×1 grid. Existing Standard and Expanded keys are not nested; host selection for overlapping matches has not been verified.

## 3. Target presentation

| Approximate launcher arrangement | Desired behavior, subject to actual available dimensions |
|---|---|
| 2×1 | Horizontal identity, avatar, name, title initials, usable menu |
| 2×2 | Centered identity and full title, up to two lines when it fits |
| 3×1 | Horizontal identity, full title on one line with ellipsis if necessary |
| 3×2 | Full title, up to two lines if space permits |
| 4×1 | Wide horizontal identity, full title on one line |
| 4×2 | Expanded identity, full title with available wrapping |
| 4×3 | More title wrapping when height permits |
| 4×4 | Spacious presentation, full title where possible |

No guarantee of a distinct presentation for each launcher grid arrangement; prioritize readable content and controls over literal cell-count mapping.

## 4. Proposed initials policy — requires owner approval

Generate initials **in memory from the displayed professional title** only when the selected responsive presentation is sufficiently narrow and short. Never persist or overwrite the original title.

- Split on whitespace and hyphens; preserve connecting words (e.g., `Director of Engineering` → `DOE`).
- For slash-separated tokens, use each meaningful component (`UX/UI Designer` → `UUD`); this is a proposal, not an established product decision.
- Skip punctuation-only tokens; do not create initials from emoji or punctuation.
- Keep a single uppercase acronym recognizable (`CTO` → `CTO`). For mixed long titles with a parenthetical acronym, avoid doubling the acronym; implementation should define and test this explicitly.
- Single word `Engineer` → `E` in initials mode; full word remains visible in larger modes.
- Examples: `Solution Engineer` → `SE`; `Senior Solution Engineer` → `SSE`; `Chief Technology Officer` → `CTO`; `Vice-President` → `VP`.
- For scripts where word-based initials are unreliable, show a safely truncated original title rather than producing misleading characters. Ensure Unicode-safe slicing; do not split surrogate pairs or combining sequences.
- Prefer all available initials where readable. Apply a compact-width limit only when necessary; **do not hard-code a five-character limit before checking real text fit**. Use ellipsis as the fallback.

## 5. Implementation sequence (one focused change set, after approval)

### A. Pure rendering policy and tests

1. Extend `QuickCardWidgetPolicy.kt` with an explicit responsive presentation decision based on available **width and height**, plus font scale, without introducing a widget-only profile field.
2. Preserve the four logical classes unless the implementation demonstrates a concrete reason to adjust breakpoint keys. Add only a small number of responsive entries where required; avoid a large map of duplicated photo-bearing `RemoteViews`.
3. Add title-initial derivation near `QuickCardWidgetProjection` in `QuickCardWidgetModel.kt` or an existing related pure helper. Do not reuse the avatar's name-initial function.
4. Write focused unit tests for title initials, acronym/Unicode fallbacks, narrow-versus-tall selection, and line-limit policy.

### B. Existing widget rendering

5. In `QuickCardWidgetProvider.kt`, select initials or the original title according to the responsive presentation, while preserving the title visibility flag.
6. Adapt title `maxLines` and font-dependent limits to available height. Preserve one-line ellipsis for short horizontal variants; allow additional lines in taller variants where layout permits.
7. Adjust the existing Standard/Expanded XML layouts **only as necessary** to protect avatar, name, title, and the 48dp menu touch target from collision or clipping. Prefer stable layout constraints over speculative runtime padding.
8. Preserve avatar/photo behavior, widget click/menu actions, accent/light-dark appearance, profile-save refresh, and launcher resizing.

### C. Refresh investigation during implementation

9. First verify whether existing update triggers and the responsive host handle appearance and font changes adequately. Do **not** modify `AndroidManifest.xml` or add a runtime receiver without a demonstrated need and a separate owner approval gate.
10. Do not change Gradle, SDK, dependencies, package/application ID, signing, schema, QR/contact/share behavior, or unrelated screens.

## 6. Focused verification after implementation

- Kotlin compilation and focused widget JVM tests; report actual commands and outcomes.
- Visual check on the existing emulator for small horizontal, centered medium, and expanded/tall arrangements; ordinary manual resizing is enough. **No standalone ADB measurement exercise required.**
- Confirm `SE`, `SSE`, `DOE`, `CTO`, one-word and punctuation examples; confirm full stored title unchanged.
- Check no avatar/menu overlap, no clipped menu, readable text at default and increased font scale, and correct behavior after resize and profile/appearance save.
- Spot-check existing photo/name/menu actions. Do not claim exhaustive device coverage or full regression testing.

## 8. Risks and safeguards

- Launcher grid counts are not fixed dp sizes; responsive rules must degrade gracefully rather than promise exact 2×1 mapping on every launcher.
- Android host choice among non-nested responsive entries remains unverified; prefer simple, predictable entries and test visible results.
- Additional map entries may increase binder/update payload because each contains `RemoteViews` and image data. Keep entries minimal.
- Larger font scale can invalidate text-height estimates; reduce line counts conservatively, preserving the menu and identity.
- Do not create automatic backups: the owner explicitly declined them. If the project protection skill mandates a backup for a proposed edit, **stop and request owner direction** rather than silently violating either requirement.
