# VCard Native V1.2 — Technical Constraints and Verification Gates

**Status:** Documentation of known constraints and preliminary technical approach. Not an approved implementation plan.
**Basis:** Earlier read-only V1.1 source audit and approved V1.2 requirements; current live Windows source not inspected in this documentation milestone.

## 1. Existing implementation baseline (reported by prior read-only audit)

- Android application ID: `com.mackseoul.vcardnative`; V1.1 version name `1.1.0`, code `2`.
- Single `:app` Android module; Kotlin/Jetpack Compose/Material 3.
- Profile and appearance model in `Profile.kt`; profile schema **4**; `ProfileRepository`, `ProfileCodec`, and `BackupDataCodec` use strict persisted appearance handling. Actual current workspace must be rechecked.
- `BusinessCard` in `MyCardScreen.kt`; `AppearanceScreen` currently supports light/dark and Sapphire/Jade/Amethyst, with draft Save and back confirmation. Current preview is not the actual `BusinessCard` renderer.
- `ContactQrEncoder`, `ContactQrRenderer`, and `ContactQrPanel` support contact and hosted URL QR contexts; `NativeContactSharing` includes scoped FileProvider-based sharing for existing contact artifacts.
- Social presets include LinkedIn, GitHub, Facebook, Instagram, X, YouTube, TikTok, Threads, Bluesky, Mastodon, Other.
- Quick Card Widget uses size-specific `RemoteViews` and existing body/overflow actions.
- Custom Share uses a persisted selection store and common export model; previous audit found preview/export phone formatting mismatch.

These are **audit-reported findings**, not fresh build or device verification.

## 2. Hard compatibility constraints

1. Preserve application identity, release signer, saved profile, photo/cover assets, and backup readability.
2. Do not change existing QR payloads, contact export field semantics, or Custom Share selected-field persistence.
3. Preserve existing widget size classes, content (name/title/photo/initials), and navigation actions. No organization field.
4. Keep Minimal-only hidden information in profile storage; switching styles must not delete or modify it.
5. Classic must match current V1.1 My Card reference, not the V1.0 source archive or a generated mockup.
6. No broad storage permission for PNG save/share; prefer MediaStore for gallery save and scoped content URI for shares.
7. Respect accessibility, long values, font scaling, and Android RemoteViews limitations.

## 3. Proposed architecture (requires separate approval)

- Share a single card data/interaction contract across seven render variants and the Appearance Editor preview.
- Extend appearance persistence to support style and Minimal selections with safe defaults and explicit backup round-trip behavior. **Schema 5 is a possibility, not authorized.**
- Preserve existing three accent identifiers/mappings; add three options only after color contrast review.
- Reuse QR matrix generation for PNG, add quiet zone and deterministic high-quality scaling; implement unique MediaStore filenames and temporary share grants.
- Use existing social platform definitions and URL opening; review icon licensing and accessibility labels.
- Reuse existing Custom Share export projection for preview values; no changes to payloads.

## 5. Mandatory project-protection process for future code work

Read `VCARD_NATIVE_ANDROID_STUDIO_PROTECTION_SKILL.md` before any task. First perform read-only inspection of actual current Windows files, identify exact changes, risks and verification, and request owner review. After separate authorization, inventory changed files, create verified timestamped recoverable external backups (including SHA-256 as required by established project workflow), implement only approved scope, and report diffs/tests. Do not silently change Gradle, SDK, JDK, Manifest, application ID, signing, or data schema. Do not assume CLI success proves Android Studio or device success.

## 6. Future verification gates

- Profile and backup round-trip tests across V1.1 and V1.2 data; defaults and Minimal selection persistence.
- Seven card variants, field/action parity except intentional Minimal hiding, accessibility and narrow-screen checks.
- All three QR contexts: payload parity, PNG scan, gallery save, share grant, unique names, and error handling.
- Social URL/order/duplicate parity and icon labels.
- Widget compact/standard/expanded actions, refresh and saved accent behavior on device.
- Custom Share exact export-value preview parity, including phone formatting.
- Unit/integration checks, physical-device validation, in-place V1.1→V1.2 upgrade, release signer verification.
