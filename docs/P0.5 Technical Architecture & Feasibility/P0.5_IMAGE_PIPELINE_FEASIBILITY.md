# VCard Native — P0.5 Image Pipeline Feasibility

**Status: PROPOSED — FEASIBILITY DOCUMENTATION; NO DECODER OR ENCODER SELECTED**  
**Date:** 2026-10-30  
**Decision coverage:** P0.5-05, P0.5-10, P0.5-12  
**Owner boundary:** P0.4 image limits, canonical-format rules, N04-only selection and exact-byte backup restoration are binding. This document evaluates implementation risks; no image code, dependency, SDK configuration or runtime test was created.

## 1. Approved input/output contract

The binding specification is [P0.4 Public Key & Image Contracts](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_PUBLIC_KEY_AND_IMAGE_CONTRACTS.md) and its [approval record](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_APPROVAL_RECORD.md). The approved initial still-image set is JPEG, PNG and WebP input; no animated/multiframe images, HEIF/AVIF, GIF, SVG, remote fetch, corrupt/truncated/polyglot input, crop/filter UI or source-file passthrough.

| Limit/behavior | Approved contract |
|---|---|
| Compressed source | <=20 MiB |
| Source dimensions | Each side <=8,192 pixels and total <=16,777,216 pixels |
| Portrait output | Longest edge <=1,024 pixels; no upscaling |
| Cover output | Longest edge <=2,048 pixels; no upscaling |
| Retained asset | <=8 MiB each |
| Canonical JPEG | Opaque JPEG source or opaque lossy WebP source; `image/jpeg`, `.jpg`, quality 90 |
| Canonical PNG | PNG source, any alpha-bearing source, lossless WebP source, or uncertain source classification; `image/png`, `.png` |
| Common pipeline | Decode bounded pixels, apply orientation, convert to sRGB, preserve aspect ratio, downsample, freshly encode, validate exact output and strip inherited metadata |
| Backup/restore | Hash/copy exact retained canonical bytes; never re-encode during restore |

Source MIME, extension and provider metadata are untrusted hints. Inspect actual image content and reject unsupported/ambiguous/truncated/multiframe sources under P0.4. Never silently flatten alpha, discard included images to make backup fit, alter crop selection, or choose another output based on a UI selector.

## 2. Feasibility finding

Android has platform image decoders/encoders and AndroidX `ExifInterface`, but those capabilities do not by themselves establish the entire contract. Decode limits, animated WebP detection, robust content sniffing, reliable lossy-versus-lossless WebP classification, orientation transforms, color conversion, peak allocation, metadata stripping, and per-device encoder output all need implementation-specific evidence.

Android's [supported-format guidance](https://developer.android.com/media/platform/supported-formats) documents JPEG/PNG/WebP platform support. `ImageDecoder` is available from API 28 and `ExifInterface` has a current stable 1.4.2 release in the research snapshot. This makes API-31 execution plausible at the platform-surface level, not proven for resource bounds, all codecs, malformed inputs or the primary Pixel. `ExifInterface` reads/writes metadata; it is not itself a bounded bitmap decode/re-encode pipeline. No decoder or encoder is selected.

A single 16,777,216-pixel ARGB_8888 bitmap is nominally 64 MiB before row stride, decoder scratch buffers, color conversion, orientation/resize intermediates or encoding buffers. Therefore, the approved pixel limit is not a safe heap allocation budget. Do not decode at full size and then scale. Estimate allocations before allocation, use bounded sampled/target-size decoding and avoid holding multiple full-size intermediates. Device memory pressure and concurrent UI work remain runtime questions.

## 4. Proposed bounded pipeline

1. **Acquire:** Through the already-approved N04-only user selection route, open the content URI while its temporary permission is valid. Do not assume filesystem paths or retain the source URI as saved asset ownership. Stream/copy with a hard 20 MiB input cap; cancellation leaves the old saved image and draft unchanged.
2. **Inspect before allocation:** Determine actual format from bytes/decoder, reject unsupported types and malformed/truncated content, obtain dimensions without full decode, enforce positive dimensions, side<=8,192 and pixels<=16,777,216 using checked multiplication. Detect and reject animated/multiframe input, or return unresolved/failure if the chosen API cannot distinguish it.
3. **Classify output:** JPEG -> JPEG only if fully opaque. PNG -> PNG. WebP -> determine lossy/lossless and alpha reliably; lossy+opaque may produce JPEG, while lossless or alpha produces PNG. If WebP mode/alpha is uncertain, choose PNG or reject if safe PNG encoding cannot be demonstrated. Never flatten alpha or guess a lossy branch.
4. **Decode bounded:** Select a decode sample/target size based on the role limit, preserving enough resolution for the maximum approved output without upscaling. Account for decoder row stride/scratch buffers and simultaneously live bitmaps. Apply cancellation and time/resource checks. Reject any path that needs an unbounded full-size decode.
5. **Normalize pixels:** Apply all EXIF orientation values 1-8, including mirrored/transposed cases, then convert to sRGB, resize proportionally with no upscaling, and preserve alpha only on the PNG branch. Role-specific cover/portrait display crops remain presentation-only; the source image is not cropped.
6. **Fresh encode:** JPEG opaque output at approved quality 90 or PNG preserving alpha/lossless requirements. Do not copy source bytes or carry metadata chunks forward. If output exceeds 8 MiB, fail with the existing inline correction path; no iterative quality reduction is authorized.
7. **Revalidate:** Reparse output and confirm actual codec/MIME-extension pair, byte count, positive dimensions, role geometry, alpha policy, orientation normalization, sRGB policy and absence of inherited EXIF/GPS/IPTC/XMP/comments/source URI. Compute SHA-256 over exact final bytes, assign an app-owned asset ID and canonicalization policy version 1. Only then make the new bytes eligible for explicit profile Save.
8. **Commit/cleanup:** Keep previous saved bytes until the coherent profile/asset Save or restore commit succeeds. Staging and replacement coordinate with P0.5-04/05/06 recovery. After success, clean only unreachable old/draft artifacts and retain exact bytes referenced by snapshots or active grants.

This sequence is an analysis aid, not approved implementation structure. If a target API cannot safely determine format/animation/alpha/WebP-lossless status, do not claim support based only on filename or MIME. A future evidence-backed limitation must be escalated rather than silently changing the approved input/output contract.

## 5. Metadata, orientation and color risks

The security/privacy goal is fresh pixel encoding rather than modifying/copying the original container. This should avoid carrying arbitrary source metadata, but the absence of EXIF/GPS/IPTC/XMP/comments/source URI must be checked on the actual encoded output. Some encoders may add color/profile metadata needed to describe sRGB; retain only what is required for normalized color interpretation under P0.4, not arbitrary source metadata.

`ExifInterface` documents reading orientation and supports metadata writing for JPEG/PNG/WebP; its `saveAttributes()` rewrites files and is not the selected canonicalization strategy. `ExifInterface` class documentation says AVIF reading is available only on API 31+ and HEIC on API 28+, but those formats are outside this approved input contract. No conclusion about AVIF support is needed for API-31 feasibility.

P0.5 must resolve:

- whether Android decoder metadata exposes exact source MIME, alpha and WebP lossy/lossless mode reliably;
- how to reject animated WebP and malformed containers across supported API/device codecs;
- whether all eight EXIF orientation variants are applied exactly once before re-encoding;
- how to explicitly convert wide-gamut inputs to sRGB without accidental double transforms;
- whether encoder output reliably excludes prohibited metadata while preserving opaque/alpha and approved geometry;
- what byte-for-byte guarantees apply only to retained bytes (not cross-version encoder output).

## 6. Failure behavior and saved-data consistency

- Invalid, oversized, unsupported or animated source: reject before replacing the current saved image; keep other draft edits and provide a clear field-level explanation.
- Picker cancellation or lost source permission: preserve prior saved bytes and current profile; no URI is treated as durable ownership.
- Decode/encode/resource failure or output >8 MiB: no partial image reference becomes saved; allow explicit re-selection/retry.
- Save failure after canonicalization: retain old saved generation and old image. Do not point metadata to staged/uncommitted bytes.
- Backup creation: include the exact retained image bytes and corresponding descriptor/hash from one coherent saved generation; if referenced bytes are missing, do not create a misleading complete backup.
- Restore: validate incoming image bytes/metadata before S02; copy exact bytes into staging; no re-encoding; commit with metadata as one recoverable aggregate.

No P0.4 contract allows a hidden image to be omitted from full backup, or an invalid image to be silently replaced by an older/different asset.

## 8. P0.6 verification obligations

Later authorized verification must include content-sniffing versus incorrect extension/MIME; 20 MiB boundary; dimensions at/over each side and pixel cap; overflow; truncated/polyglot/malformed inputs; animated WebP; JPEG/PNG/WebP lossless/lossy and alpha combinations; all eight EXIF orientations; wide-gamut/sRGB; metadata-bearing GPS/XMP/comment inputs; portrait/cover maximums and no-upscale cases; encoded output >8 MiB; low-memory/cancellation/provider loss; restart persistence; exact-byte backups; and failures during save/restore generation switch. Measure actual API 31/Pixel 9 Pro XL peak allocations and latency. These are future verification obligations, not tests run.
