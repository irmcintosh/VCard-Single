Reject malformed/truncated/excessive input, unsupported versions/algorithms/packet semantics, unsupported key containers, and any secret/private packet (5 or 7), including mixed public/private material. Inspect the complete input. No extracting public portions from private input, custom cryptographic parser, key generation, keyserver retrieval, encryption/decryption feature, or identity-certification feature is in scope.

## 3. Standards implications to preserve

### v4 and v6 are distinct formats

[RFC 9580](https://www.rfc-editor.org/rfc/rfc9580.html) obsoletes RFC 4880 and RFC 6637. It says implementations SHOULD create v6 keys and SHOULD accept v4 keys. VCard Native only evaluates imported public certificates; it does not generate keys. Do not treat the RFC's generation recommendation as permission to reject owner-approved v4 inputs.

- A v4 fingerprint is 20 bytes (SHA-1 over the version-specific public-key framing); its conventional hexadecimal form is 40 characters. A v6 fingerprint is 32 bytes (SHA-256 over different framing); its conventional hexadecimal form is 64 characters. They are not interchangeable.
- v6 primary keys require a valid Direct Key signature before use. A v6 key's subkeys must also be v6, require v6 binding signatures, and v6 keys produce v6 self-signatures. A v6 certificate does not require a User ID if the use does not depend on that textual identity.
- v6 cannot use deprecated Ed25519Legacy or Curve25519Legacy OIDs. Do not relabel or reinterpret their bytes as native Ed25519 (27) or X25519 (25). v4 Curve25519Legacy ECDH and native v6 X25519 are separate matrix cases.
- OpenPGP armor CRC24 is not a validity/authenticity check. RFC 9580 says input must not be rejected solely because CRC24 is absent, malformed or mismatched; it also says CRC24 should not be generated for an armored v6 transferable public key. Actual base64 and packet framing still require validation.

RFC 9580's RSA guidance says not to generate RSA below 3,072 bits and recommends against using keys below 3,072 bits; it prohibits use below 2,048 bits. The approved input range is 3,072-8,192 bits. The upper bound and parser cost limit are application bounds, not RFC limits.

### Validity is not usability or identity trust

The implementation must keep these questions separate:

1. Is the bounded public-only structure supported and well-formed?
2. Are required self-certifications/direct-key signatures, primary/subkey bindings, key flags and revocation material cryptographically verified?
3. Is a verified encryption component currently usable at the current reference time?
4. Has the app established real-world identity trust? It has not: successful certificate verification does not prove that the key belongs to a person.

A supported, structurally and cryptographically data-valid expired or verifiably revoked certificate remains eligible for storage and complete backup/restore under the approved retention policy. Its corresponding action remains unavailable. Do not report expired signatures as valid merely because key material is preserved. A revoked primary disables all encryption candidates; revoking one subkey must not cause another candidate to be treated as revoked, though that other candidate still needs its own valid binding, flags and current usability. If device-time uncertainty or unsupported revocation semantics prevent a safe usability decision, expose no active action and keep the case unresolved rather than inventing a trust result.

Unusual designated-revoker cases and revocation material that cannot be verified offline need explicit P0.5/P0.6 capability evidence. They are not permission to ignore revocation or to label a certificate usable. The exact policy for unresolved revocation state remains a documented owner escalation if a maintained candidate cannot distinguish it safely.

## 5. Restore and error policy

Key validation is part of candidate-backup validation before the existing S02 replacement point. It must not be deferred until after metadata/assets have been replaced. A backup containing a secret key, unsupported format, malformed structure, invalid required signature/binding, unsupported critical semantics or an unclassifiable required revocation is rejected as a whole; retain the prior profile, visibility settings, appearance, image and key. No partial restore, opaque import, key stripping, automatic conversion or substitute certificate.

A complete validated backup preserves supported expired and verifiably revoked public certificate bytes and supported revocation material. Validate key usability separately after restore; it must not turn a retained historical certificate into an available action. The backup entry SHA-256 verifies exact bytes only. It is not a fingerprint, signature, identity check or substitute for OpenPGP validation.

The P0.4 user-facing unsupported-format behavior remains factual and uses existing approved surfaces. No new screen, confirmation dialog or product feature is added. Parser exceptions and key contents must not be logged. Failure and cancellation outcomes are not successful Save/restore. Whole-aggregate rollback/recovery is specified separately in [P0.5 state, storage and recovery](P0.5_STATE_STORAGE_AND_RECOVERY.md); this document does not claim that a candidate library supplies it.

### D. Can 2.0.4 and 1.86 safely coexist without an unsupported override?

**Not established.** The declared graph is BC 1.84. Introducing BC 1.86 changes that graph whether through an explicit constraint or ordinary conflict resolution. Module `requires` values are not a statement that all newer versions are incompatible, but resolution success would not certify API, policy or security compatibility. No upstream endorsement of this exact upgrade was located in the inspected tag/release/metadata; this is not proof that maintainers reject it.

Normal dependency resolution selects a version of each module; it does not isolate two copies of identically named BC classes. See [Gradle dependency resolution](https://docs.gradle.org/current/userguide/dependency_resolution.html). Do not retain 1.84 and 1.86 as a supposed side-by-side provider workaround or change only bcpg while assuming the rest is safe. No configuration is prescribed or performed.

BC 1.86 changes certificate-validation semantics and includes public API changes. No exhaustive binary/API audit of PGPainless against it was performed, no linkage failure was demonstrated, and no build/test was run. Therefore the justified result is **unverified upgrade with security pressure to evaluate**, not “known compatible” or “proven API-incompatible.” An unmodified 1.84 graph is reproducible publication metadata, not a provisional production-safety recommendation.

- The high-level OpenPGP API is comparatively new and had several validation CVEs through 1.85.2; 1.86 is the first release with the fixes.

- No row, Android API-31 build or runtime evidence exists.

**C3: GopenPGP** is credible as a library and has the most readable key-property API, but it has no published Android artifact or minSdk statement, adds a separate native toolchain, and its documented `IsExpired` behavior conflates invalid and expired. ### A. Summary of findings

1. **The reader alone is not sufficient (D).** Only `OpenPGPKeyReader.parseCertificates` examines more than the first object, and it still leaves armor-level, counting, allowlist, silent-skip and CRC gaps (11B).
2. **An application-level screening step is necessary (I).** It can be built from BC enumeration APIs plus ordinary Java stream, size and text checks, so no OpenPGP framing code has to be written by the application (11C, 11E).
3. **Tag screening alone is not sufficient (I).** The tag is only meaningful at a verified packet boundary, which requires framing; partial and indeterminate lengths and other parser differentials are not exposed by BC's packet objects (11D).
4. **Complete enumeration is available from maintained BC classes (D):** `ArmoredInputStream` (builder), `BCPGInputStream.nextPacketTag/readPacket`, `Packet` accessors and the ring/factory classes. BC offers no per-packet skip, consumed-length or count-limit facility (11E).
5. **Limits must be applied before and during BC calls** because the reader reads its entire input into memory and BC's packet-level caps (2 MiB) are far above the P0.4 limits (11F).
6. **A candidate rule set and 36 negative/positive test cases are recorded for owner review (11G, 11I).** Seven owner decisions are open (11H).
7. **The approach can preserve expired/revoked retention and whole-restore rejection of unsupported formats (I)**, but only with an enumeration pass that is stricter than BC's ring reader, which silently drops unsupported subkeys and signatures (11J).

### B. What the high-level reader does with each kind of input

Behavior is from source reading of the named methods; none was executed. `parseCertificate`, `parseKeyOrCertificate` and `parseKeysOrCertificates` are included because they sit beside `parseCertificates` and a wrong choice would fail the P0.4 rule.

| Input | Behavior (from source) | Meets P0.4 alone? |
|---|---|---|
| One valid public certificate | All methods return it. **D** | Yes, structurally. |
| Public certificate followed by a secret key (tag 5) | `parseCertificate` and `parseKeyOrCertificate` read only the first object and return the certificate; the trailing secret key is never examined. `parseCertificates` reads the secret ring and throws `IOException` ("Encountered unexpected packet"). **D** | Only `parseCertificates`. |
| Secret key first, then a public certificate | `parseCertificate` throws; `parseKeyOrCertificate` returns an `OpenPGPKey` instead of rejecting (the caller must check the type); `parseKeysOrCertificates` returns a mixed list; `parseCertificates` throws. **D** | Only `parseCertificates`. |
| Secret subkey (tag 7) after or between certificate packets | `PGPPublicKeyRing` stops at any tag other than a public subkey; the factory then reads tag 7 through `readPacket`, sees a typed non-unknown packet and throws "unexpected packet in stream". `parseCertificates` therefore rejects it. **D** | Only `parseCertificates`. |
| Several public certificates | `parseCertificate` returns the first and ignores the rest; `parseCertificates` returns a list. The application must require exactly one. **D** | No; count check needed. |
| Unrecognizable public subkey inside a certificate (for example v4 with an unknown algorithm) | `readSubkey` catches non-EOF `IOException` and returns `null`; the ring silently drops the subkey. **D** | No; contradicts "reject unsupported". |

| Marker or padding packets inside the certificate | Skipped, with no count limit. At the top level a marker is skipped but a padding packet makes `parseCertificates` throw. **D** | No; P0.4 allows bounded marker and padding handling. |
| Trust packet (tag 12) | Accepted after keys, user IDs and signatures. **D** | No; not in the P0.4 recognized set. |
| Version 2, 3 or 5 key packet | `PublicKeyPacket` accepts versions 2 to 6. **D** | No; P0.4 matrix is v4 and v6. |
| Version 6 key with an unknown algorithm | Accepted as `UnknownBCPGKey` because its length is known. **D** | No; algorithm allowlist needed. |
| Unknown critical packet tag | The default `BcOpenPGPImplementation` factory sets `setThrowForUnknownCriticalPackets(true)`, so tags up to 39 not otherwise handled throw. **D** | Yes for that case. |
| **Possible silent stop of the loop (hypothesis, not tested)** | `nextObject()` returns `null` for end of stream, and `readSubkey` can also return `null` for an unrecognizable subkey. `parseCertificates` loops `while ((object = nextObject()) != null)`. A public-subkey packet (tag 14) that reaches the top level (for example after a marker, because the ring's subkey loop does not skip markers) and cannot be recognized would end the loop early, leaving later packets, including a secret key, unread. **D** (source flow) / **U** (execution) | Potential hole; negative test N-P7. |
| Binary input | `PGPUtil.getDecoderStream` returns binary data directly when the first byte has the high bit set. **D** | No; P0.4 requires ASCII armor. |
| Armor without a header (bare base64) | Accepted by the decoder-stream heuristic (`ArmoredInputStream(in, false)`). **D** | No. |

| Secret material in memory | A secret key ring is fully constructed (S2K, encrypted or unprotected secret data) before the reader rejects it. **D** | Acceptable only if no secret bytes or exception text are persisted or logged. |

**Conclusion for question 1 (I):** `parseCertificates` rejects the secret-bearing inputs it reaches that BC can frame. It does not, by itself, reject all inputs containing secret-key packets: it can be bypassed by the single-certificate methods, may stop early (the null-return hypothesis), and does not constrain armor-level content. It also accepts several things P0.4 requires to be rejected.

### C. Is an application-level packet-envelope check necessary, and what counts as screening

Yes (I), for six reasons visible in 11B: counts and limits are not enforced; the recognized-packet allowlist is not enforced; unsupported subkeys and signatures are silently dropped; the single-certificate methods ignore trailing content; the armor layer is lenient; and the CRC behavior diverges from P0.4.

The following separation is proposed so the owner can judge "no custom parser" (a proposal, not a decision):

| Bounded structural screening (application code, no OpenPGP interpretation) | Cryptographic and semantic parsing (must remain in maintained BC code) |
|---|---|
| Raw byte-length cap; reject empty input | Decoding key material and multiprecision integers |
| ASCII armor envelope: one block, the label line, nothing but whitespace outside it | Packet framing, partial and indeterminate lengths, header formats |
| Looping over BC's packet enumeration, comparing tag, version and algorithm integers that BC objects expose | Signature subpacket parsing, key flags, expiry, revocation |
| Counting packets, subkeys and user IDs; stopping at the limit | Signature and binding verification, fingerprints |
| Reconciling the enumerated counts against what the ring reader accepted | Policy, algorithm strength and hash acceptability |

BC's `readPacket` itself decodes key material while enumerating (for example `PublicKeyPacket.parseKey`), so enumeration is not free of parsing. It remains maintained BC code. **I:** the line to keep is that application code must never read packet header octets, lengths, MPIs or subpackets itself.

### D. Why tag screening alone is not sufficient

`BCPGInputStream.nextPacketTag()` decodes the tag for both header formats (`b & 0x3f` for new, `(b & 0x3f) >> 2` for old) without consuming the byte. **D.** That makes it a safe peek before `readPacket()`, which is how a tag-5 or tag-7 packet can be rejected before its secret body is decoded. It is not a screening method on its own:

| Hazard | Evidence and effect | Mitigation using BC | Residual gap |
|---|---|---|---|
| Tag peek does not validate the header | `nextPacketTag()` does not test bit 7; `readPacket()` throws "invalid header encountered". **D** | Advance only with `readPacket()` | None beyond tests |
| A tag byte is meaningful only at a packet boundary | Scanning raw bytes for tag-5 patterns misreads packet bodies. **I** | Enumerate through `readPacket()` | None if BC framing is trusted |
| Old-format indeterminate length (length type 3) | `readPacket` sets `objStream = this` for a zero-length partial packet, so the typed packet reads from the shared stream with no body bound; what follows is parsed as the next header. Under RFC rules the packet would extend to the end of input. **D** (source) / **I** (differential) | Not exposed by `Packet` (only tag, new-format flag, critical flag). | Differential against other OpenPGP implementations; see options below |
| Partial body lengths (new format) | Handled by `PartialInputStream`; the partial flag is not recorded on the packet. **D** | None through the object API | Same |
| Body bytes left unread by a packet constructor | Typed packets read from `new BufferedInputStream(pis)` (default 8,192-byte buffer). Bytes of a larger body that the constructor does not consume would be parsed as the next header. Whether constructors drain their bodies was not established. **D** / **U** | Test with trailing bytes in a key packet larger than 8,192 bytes | **U** |
| Top-level tag 13, 17 or 19 handling in `PGPObjectFactory` | `new UnknownPacket(tag, in)` calls `readAll()`, consuming the rest of the stream without framing. **D** | Rejected anyway because the result is not a ring | None for rejection; matters for differential reasoning |
| Trailing packets after the ring | The ring constructor stops without consuming them. **D** | `parseCertificates` or an enumeration to end of input | Null-return hypothesis |
| Unknown or private tags | Tags 40-59 are non-critical and tags 60-63 experimental; the factory returns them as objects, which `parseCertificates` then rejects as non-ring. **D** | Allowlist the six permitted tags | None |
| Private-use algorithm IDs in public-key packets | Version 6 packets with unknown algorithms are accepted as `UnknownBCPGKey`. **D** | Algorithm allowlist from `getAlgorithm()` | None |

Options for partial and indeterminate lengths, none verified:

1. **Accept BC's framing.** Cheapest; leaves a differential against other consumers of the stored certificate. P0.4 shares no key through QR or .vcf, which lowers but does not remove the concern. **I**
2. **Canonical round-trip comparison.** Re-encode the ring with BC (`getEncoded(PacketFormat.ROUNDTRIP)`) and compare with the decoded input. This detects partial and indeterminate lengths without application framing code, but would also reject valid non-minimal length encodings, certificates carrying trust, marker or padding packets, and anything BC normalizes. False rejects of legitimate historical certificates are likely; the effect on the P0.4 policy is **U**.
3. **Application inspection of header octets.** This is custom framing; it conflicts with the intent of the no-custom-parser rule. **I**
4. **Owner policy.** Declare that only definite-length framing is supported and decide which of the above enforces it.

No option is recommended by this research.

### F. Resource limits before and during parsing

| Stage | Limit | Mechanism and evidence |
|---|---|---|
| Before BC sees the input | 1 to 65,536 raw bytes, enforced by the application | `OpenPGPKeyReader` calls `Streams.readAll`, so the bound must exist before the call. **D** |
| Armor layer | Headers at most a small application-chosen count; BC's defaults are 4,096 bytes per line and 64 lines, adjustable through global properties that should not be relied on | **D** |
| Decoded size | At most about 49,152 bytes (raw cap times 3/4) | **I** |
| Packet count | At most 128, counted as packets are enumerated, aborting before reading packet 129; markers and padding count | P0.4 limit; BC provides none. **D** |
| Primary, subkeys, user IDs | Exactly one tag 6, at most 4 tag 14, at most 8 tag 13, counted during enumeration | BC provides none. **D** |
| Per-packet allocation | BC constants cap public-key packets and subpackets at 2 MiB, far above P0.4. Inside packet bodies BC's own length hint falls back to the heap size (the 1.85.x notes describe this for user-attribute subpackets), so a truncated packet may allocate up to its declared bound before failing. | **D** / **I**: at most one such transient allocation per rejected input, to be measured |
| RSA modulus size | The MPI bit-count field is 16 bits (up to 65,535 bits). Reject above 8,192 bits using BC's key accessors before any signature verification | **I**: CPU bound for verification; measurement U |
| Signature work | Bounded by 128 packets, but each RSA verification at 8,192 bits and the total on API-31-class hardware are unmeasured | **U** |
| Decompression and nesting | Tag 8 is excluded by the allowlist; no recursion applies to the six permitted tags | **I** |
| Errors | History includes an armor `StackOverflowError` and heap errors that escape `IOException`. Treat any `Throwable` during screening as rejection, without logging messages (BC messages can contain packet descriptions) | **I** |
| Time | No documented wall-clock bound | **U** |

### G. Candidate acceptance and rejection rules (proposed for owner review, not approved)

All must hold, evaluated in order. "Via BC" means the check uses BC objects or accessors, not application parsing.

| # | Rule |
|---|---|
| R1 | Raw input is 1 to 65,536 bytes. |
| R2 | Armor: the first non-whitespace content is the line `-----BEGIN PGP PUBLIC KEY BLOCK-----` (label via `getArmorHeaderLine()`), the block ends with the matching `END` line, and only ASCII whitespace lies outside the block. Binary, headerless, cleartext-signed, private-key-labelled and multi-block input is rejected. The CRC24 line is not a gate. (Enforcing "only whitespace outside" requires a bounded text check by the application; see H3.) |
| R3 | The armored body decodes without error. |
| R4 | Enumerating the decoded bytes through `BCPGInputStream` reaches end of input with no exception and at most 128 packets. |
| R5 | Before each `readPacket()`, the peeked tag is one of 6, 14, 2, 13, 10, 21. Tags 5 and 7 are classified as private material; every other tag is classified as unsupported. |
| R6 | The first packet other than marker or padding is tag 6; there is exactly one tag 6, at most 4 tag 14 and at most 8 tag 13. |
| R7 | Every key packet has version 4 or 6, all key packets share the primary's version, and every algorithm is in the P0.4 matrix. RSA moduli are 3,072 to 8,192 bits. |
| R8 | No `UnsupportedPacketVersionException` or other parse failure occurs on any signature packet. |
| R9 | Reconciliation: constructing the ring from the same decoded bytes accepts every enumerated non-marker, non-padding packet (key count equals 1 plus the tag-14 count; accepted user-ID and signature counts equal the enumerated counts). `parseCertificates` over the same bytes returns exactly one certificate and nothing else. |
| R10 | Cryptographic verification and usability evaluation (sections 3 and 7) run only after R1 to R9 pass. |

Where a rejected input contains a tag 5 or 7 that enumeration reaches, the outcome is the private-material rejection; where framing fails earlier, a later private packet is unreachable and the outcome is malformed or unsupported. P0.4 "inspect the entire accepted input" is satisfied for accepted inputs by construction; for rejected inputs it cannot be guaranteed, but acceptance is unaffected.

### H. Open owner decisions

1. Is armor-envelope text checking (R2) acceptable under the no-custom-parser rule? The alternative is relying on BC's lenient armor behavior.
2. How are partial and indeterminate lengths handled (11D options 1 to 4)?

5. Are old-format packet headers accepted (BC accepts them; P0.4 is silent)?

7. Are trust packets and user-attribute packets rejected as unsupported (consistent with the P0.4 recognized list), accepting that some real-world certificates carry them?

## 12. Whole-input validation feasibility: verdict by question — 2026-10-30

**Research-only. The owner has not approved the seven packet-handling policies in section 11H or the rules R1 to R10 in section 11G; they remain recommendations needing evidence. P0.5-09 remains PROPOSED/PENDING; FG-00 through FG-07 remain open; P0.1 to P0.4 are unchanged.** This section refines section 11; where they differ, section 12 governs. Evidence tags **D**, **M**, **I**, **U** are as in section 10A, plus one more: **HY** (labelled HY1, HY2; not to be confused with the "H" decision references (H2, H4, H6) used in the section 11I test table, which point to the numbered owner decisions in section 11H) marks an *untested hypothesis* drawn from reading source flow, which must be executed before it is believed or dismissed. Verdicts use three words: **Enforceable** (maintained BC APIs can do it, subject to the stated test), **Unenforceable** (BC cannot do it; a gap against P0.4 or an owner decision is needed) and **Unresolved** (evidence is insufficient either way). No design is selected.

### A. Verdict summary

| # | Question | Verdict | Deciding evidence |
|---|---|---|---|
| 1 | Enumerate and account for every packet, including unsupported, malformed and trailing content | **Unresolved** | BC enumerates every framed packet, but bytes inside a declared packet body that the packet class does not read are not exposed, and may be silently absorbed (HY1). |
| 2 | Detect old-format headers, partial lengths and indeterminate lengths | **Old format: Enforceable. Partial and indeterminate: Unresolved** | `Packet.hasNewPacketFormat()` exists; no accessor records the partial or indeterminate flag. |
| 3 | Reject secret-key packets anywhere before accepting a certificate | **Unresolved** (enforceable for every packet BC frames; not shown for bytes BC does not frame) | Peek-before-read works; HY1 and the null-return stop (HY2) could hide a later packet. |
| 4 | Reconcile packet, subkey and user-ID counts without silent omission | **Enforceable for BC's silent skips; not for BC's own framing blind spots** | Two passes over the same BC reader share blind spots. |
| 5 | Armor envelope and CRC24 within the P0.4 contract | **Envelope: Enforceable with a bounded text check (owner decision). CRC: Unenforceable in full** | A malformed CRC line still throws with the CRC ignored. |
| 6 | Would rejecting trust, user-attribute or uncommon framing exclude supported historical keys | **Unresolved for prevalence; settled for the packet list** | P0.4 already excludes tags 12 and 17; uncommon framing is not addressed by P0.4. |

### C. Per-question analysis

#### Question 1: enumeration and accounting of every packet

- **API and source:** `BCPGInputStream.nextPacketTag()` and `readPacket()` ([source](https://github.com/bcgit/bc-java/blob/r1rv86/pg/src/main/java/org/bouncycastle/bcpg/BCPGInputStream.java)); `UnknownPacket` ([source](https://github.com/bcgit/bc-java/blob/r1rv86/pg/src/main/java/org/bouncycastle/bcpg/UnknownPacket.java)); RFC 9580 [section 4.1](https://www.rfc-editor.org/rfc/rfc9580.html).
- **Confirmed (D):** `readPacket()` returns `null` at end of input, throws "invalid header encountered" when bit 7 is clear, returns a typed object for each defined tag and an `UnknownPacket` (whole body read) for the rest. A truncated body ends in `EOFException` when a constructor reads past it. `PublicKeyPacket` throws `UnsupportedPacketVersionException` for versions outside 2 to 6 and `IOException` for an unknown v4 algorithm.
- **Inference (I):** every packet BC frames can be listed by tag, class, version and algorithm; unsupported and malformed packets surface as exceptions in an enumeration pass even though the ring reader hides some of them (section 11B).
- **Untested hypotheses (HY):** HY1 (absorbed bytes); whether packet constructors drain their bodies; behavior when the input ends inside a header or body.
- **Verdict:** **Unresolved.** Framing BC performs can be enumerated; accounting for every octet cannot be shown from BC objects, because consumed bytes per packet are not exposed.
- **Minimum future test:** feed a decoded certificate whose first key packet declares a length larger than its content (including `0xFFFFFFFF`) followed by a secret-key packet inside the next 8,192 bytes, and observe whether any BC object, exception or count reveals the secret-key packet.

#### Question 2: old-format, partial and indeterminate lengths

- **API and source:** `Packet.hasNewPacketFormat()`; `BCPGInputStream.readPacket()` (local variables `newPacket`, `partial`, `bodyLen`); RFC 9580 [section 4.2](https://www.rfc-editor.org/rfc/rfc9580.html).
- **Confirmed (D):** old versus new format is exposed. Partial and indeterminate lengths are consumed internally and not exposed. RFC 9580 section 4.2.1.4 says Partial Body Lengths MUST NOT be used for any packet type other than literal, compressed and encrypted data; section 4.2.2 says a Legacy packet with indeterminate length MUST NOT be generated but MAY be interpreted for historic data.
- **Inference (I):** a conforming certificate never contains partial lengths on tags 2, 6, 13 or 14, so rejecting them would exclude only non-conforming input. The legacy format is a different matter (Question 6).
- **Hypotheses (HY):** per-packet check of bytes pulled from a counting `InputStream` wrapper (standard Java, not OpenPGP code) against the length of `ContainedPacket.getEncoded(PacketFormat.ROUNDTRIP)`. A partial-length or indeterminate-length packet should pull a different number of bytes than its canonical re-encoding, and an absorbed-window packet (HY1) should pull far more. This uses only BC to decide framing, but it would also reject valid non-minimal length encodings and any packet BC re-encodes differently.
- **Verdict:** old format **Enforceable**; partial and indeterminate **Unresolved**. Reading header octets in application code is the other route and is custom framing; it is not proposed.
- **Minimum future test:** certificates with new-format partial lengths on a signature, user ID and key packet, an old-format indeterminate-length final packet, and valid non-minimal 2- and 5-octet lengths; record whether the byte-accounting check separates the first two groups from the third.

#### Question 3: secret-key packets anywhere in the input

- **API and source:** `BCPGInputStream.nextPacketTag()` (decodes both header formats without consuming); `Packet.getPacketTag()`; `PGPObjectFactory.nextObject()`; RFC 9580 [section 10](https://www.rfc-editor.org/rfc/rfc9580.html).
- **Confirmed (D):** a tag 5 or 7 seen at a packet boundary can be rejected before `readPacket()` decodes it. section 11B records the top-level behavior of `parseCertificates` for these tags.
- **Inference (I):** acceptance can be made conditional on a complete enumeration that never sees tag 5 or 7, with no ring construction or storage before that point.
- **Hypotheses (HY):** HY1 and HY2 could hide a later packet, so "anywhere" is not shown for bytes BC does not frame.
- **Verdict:** **Unresolved.** It becomes Enforceable if the Question 1 accounting check is shown to detect absorbed bytes and the HY2 loop stop is excluded by the enumeration pass.
- **Minimum future test:** negative cases N-P1 to N-P8 in section 11I plus N-HY1a to N-HY1c in part E, each with a tag 5 and a tag 7 placed after the suspected hiding point; the expected outcome is rejection as private material in each.

#### Question 4: reconciling counts without silent omission

- **API and source:** `PGPPublicKeyRing.size()`; `PGPPublicKey.getSignatures()`, `getSignaturesForID(...)`, `getSignaturesForUserAttribute(...)` and `getUserIDs()` (all used by `OpenPGPCertificate`); `OpenPGPCertificate.getKeys()`, `getSubkeys()`, `getIdentities()` and `getAllKeyIdentifiers()` (documented as including expired, revoked and unbound keys).
- **Confirmed (D):** BC silently skips marker and padding packets, unsupported-version signatures and unrecognizable subkeys inside a ring (section 11B). An enumeration pass sees all of them as separate tags or exceptions.
- **Inference (I):** comparing enumerated counts with ring contents detects those silent skips. It cannot detect HY1, because both passes share the same blind spot. `OpenPGPCertificate` stores components in maps keyed by component equality (`OpenPGPUserId.equals` compares the string), so duplicate identical user IDs may collapse at that layer; reconciliation should therefore use the ring-level accessors.
- **Hypotheses (HY):** whether the ring-level signature accessors return every signature packet including duplicates and third-party certifications.
- **Verdict:** **Enforceable** for the silent skips; the framing blind spot is Question 1.
- **Minimum future test:** certificates with one extra marker, one padding packet, one unrecognizable subkey, one unsupported-version signature, a duplicated user ID and a duplicated signature; confirm each produces a count mismatch or a parse exception.

#### Question 5: armor envelope and CRC24 within P0.4

- **API and source:** `ArmoredInputStream.builder()`, `getArmorHeaderLine()`, `setIgnoreCRC`, `setDetectMissingCRC`, `parseHeaders` and `read` ([source](https://github.com/bcgit/bc-java/blob/r1rv86/pg/src/main/java/org/bouncycastle/bcpg/ArmoredInputStream.java)); `PGPUtil.getDecoderStream` ([source](https://github.com/bcgit/bc-java/blob/r1rv86/pg/src/main/java/org/bouncycastle/openpgp/PGPUtil.java)); `ArmoredOutputStream` and its Builder; RFC 9580 [section 6.1](https://www.rfc-editor.org/rfc/rfc9580.html) and 6.2.1; P0.4 contract section 2 and 3.
- **Confirmed (D):**
  - RFC 9580 6.1: an implementation "MUST NOT reject an OpenPGP object when the CRC24 footer is present, missing, malformed, or disagrees with the computed CRC24 sum", and a v6 transferable public key MUST NOT carry a CRC24 footer.
  - BC rejects a wrong CRC by default; `setIgnoreCRC(true)` removes that. A malformed CRC line (`=` followed by something that does not decode to three bytes) still throws "malformed crc", because the shape check runs before the `crc != null` test.
  - `PGPUtil.getDecoderStream` accepts binary and headerless input and offers no CRC option, so the application must build `ArmoredInputStream` itself.
  - `ArmoredInputStream` skips text before the first line-leading dash and does not verify the label; `getArmorHeaderLine()` returns it.
  - Output: `Builder.clearHeaders()` and `enableCRC(false)` satisfy "omit nonessential headers" and "no CRC24 for v6". The line separator is platform-derived, with no Builder override, so LF is not guaranteed by the API (Android's value is not verified here, **U**). The label is derived from the first octet only, so a certificate whose first packet is a marker would be labelled `MESSAGE`. Armoring BC's re-encoding (`OpenPGPCertificate.getEncoded`, which strips trust packets and renormalizes lengths) would change packet bytes, contrary to "without changing cryptographic packet content"; armoring the validated input bytes avoids that.
- **Inference (I):** the envelope can be checked with `getArmorHeaderLine()` plus a bounded text check for "nothing but whitespace outside the block"; that text check is application code over ASCII armor lines, not OpenPGP parsing, but whether it is acceptable is an owner decision (section 11H item 1).
- **Conflicts with P0.4 text, not resolved here:** rejection of a malformed CRC line, and the marker-first label case. P0.4 is not modified; the owner must decide whether a pre-processing step, a documented deviation or a different library behavior is acceptable.
- **Verdict:** envelope **Enforceable with an owner-approved text check**; CRC clause **Unenforceable in full** with BC 1.86 as retrieved.
- **Minimum future test:** wrong, missing, malformed (short, over-long, non-base64), repeated and misplaced CRC lines; text before BEGIN, after END and between blocks; second block; `PRIVATE KEY BLOCK` label; first-packet marker; armor produced from the validated bytes read back through the same pipeline and compared byte for byte.

#### Question 6: would the recommendations exclude supported historical keys

| Rejected feature | What P0.4 already says | RFC 9580 position | Effect (this research cannot quantify real-world prevalence, **U**) |
|---|---|---|---|
| Trust packet (tag 12) | Not in the recognized list (6, 14, 2, 13, plus bounded 10 and 21), so already unsupported | [RFC 9580 5.10](https://www.rfc-editor.org/rfc/rfc9580.html): SHOULD NOT be emitted to other users; SHOULD be ignored except in local keyrings | No new exclusion from P0.4. Excludes keyring dumps; interoperable importers would ignore the packet instead. |
| User Attribute packet (tag 17) | Not in the recognized list; "unsupported attributes" are classified unsupported | RFC 9580 5.12 and 10.1.3 allow it in certificates; implementations SHOULD handle certifications on it | No new exclusion from P0.4, but it excludes certificates the RFC treats as valid (photo IDs). |
| Unsupported-version or malformed signature | P0.4 rejects unsupported packet structure | RFC 9580 5.2.5: MUST ignore for validation and MUST NOT halt processing | P0.4 is stricter than the RFC; BC's ring skips them and an enumeration pass would reject them. |
| Legacy (old-format) headers | **Not addressed** | RFC 9580 4.2: MAY be consumed; SHOULD NOT be generated | Rejecting them would add a restriction beyond the approved text; likely to affect historical keys. |
| Partial lengths on key, signature or user-ID packets | **Not addressed** | 4.2.1.4: MUST NOT be used for those types | Excludes only non-conforming input. |
| Legacy indeterminate length | **Not addressed** | 4.2.2: MAY be interpreted for historic data | Rare; excludes historic data. |
| Non-minimal length encodings | **Not addressed** | 4.2.1 defines the ranges and does not require the smallest encoding (**I**) | Would be rejected by any canonical re-encoding check; false-reject risk. |

- **Verdict:** **Unresolved** for prevalence. The packet-list part is settled by P0.4's own recognized list; the framing part is new policy that the owner would have to add explicitly, and no evidence was gathered on how common these framings are.
- **Minimum future test:** a corpus of real exported certificates from several generators and eras (including old-format headers, photo IDs, trust-bearing keyring exports and non-minimal lengths) with the acceptance outcome recorded per feature, before any framing rejection is adopted.

#### Question 7: retention without current usability

- **API and source:** `OpenPGPCertificate(PGPKeyRing, OpenPGPImplementation, OpenPGPPolicy)`, `getExpirationTime(Date)`, `getRevocation(Date)`, `getEncryptionKeys(Date)`, `getValidKeys(Date)`, `getAllKeyIdentifiers()`, `OpenPGPCertificateComponent.isBoundAt(Date)`; `OpenPGPSignatureChain.isRevocation()`, `isHardRevocation()`, `isValid()`; `Revocation.since()` ([source](https://github.com/bcgit/bc-java/blob/r1rv86/pg/src/main/java/org/bouncycastle/openpgp/api/OpenPGPCertificate.java)).
- **Confirmed (D):**
  - The constructor performs no time filtering or signature verification, so expired or revoked certificates construct normally.
  - A component is usable at a time only if it is bound at that time: the chain must be valid and not a revocation, a v6 key needs a valid Direct Key signature, an expired primary key makes its subkeys unbound, and a primary revocation propagates through subkey chains.
  - Subkey revocation is per component. Hard revocations are retroactive (`since()` returns epoch 0).
  - Everything takes an explicit evaluation `Date`, which allows the application to derive usability at evaluation time and never store a cached flag (P0.4 section 3).
  - `getAllKeyIdentifiers()` is documented as including expired, revoked and unbound keys.
- **Inference (I):** the screening rules in 11G neither read time nor revocation state, so retention and the screening are independent; the stored bytes are never re-encoded.
- **Gaps:**
  - `getRevocationAt` returns an effective revocation chain without verifying it, while `isBound` fails closed when the latest chain is invalid. The API alone cannot separate "verified revocation" from "corrupt or forged revocation"; the application would have to call `isValid()` per chain and map `PGPSignatureException` and `MissingIssuerCertException` to P0.4 outcomes (**I**).
  - `isBound` evaluates chains originating at the primary key only, so third-party (designated-revoker) revocations do not affect usability and have no issuer certificate to verify offline. P0.4 section 2 says an unresolved relevant revocation must not be ignored while declaring usability, so this case is Unresolved, as P0.4 already anticipates.
  - The v6 revocation-only certificate is handled by BC but has no direct-key signature; whether P0.4 accepts it is an owner question (section 11I P-R3).
- **Verdict:** retention and non-usability **Enforceable**; classification of invalid and third-party revocations **Unresolved**.
- **Minimum future test:** expired primary, expired subkey only, primary revoked, subkey revoked with another usable subkey, hard and soft revocation, forged revocation signature, third-party revocation, evaluation at several dates including a past date, v6 without a direct-key signature, and v6 revocation-only; record `isBoundAt`, `getEncryptionKeys` and chain validity results for each.

### D. Candidate accounting techniques (hypotheses, none selected)

| Technique | What it would detect | Cost and risk |
|---|---|---|
| T1: per-packet pulled-bytes versus canonical re-encoded length (counting `InputStream` wrapper plus `getEncoded(PacketFormat.ROUNDTRIP)`) | HY1 absorption, partial and indeterminate lengths, non-minimal lengths | Fidelity of BC re-encoding for each packet class is unverified; false rejects of valid non-minimal encodings; needs a counting wrapper (standard Java). |
| T2: whole-certificate canonical equality (re-encode the ring and compare to the decoded input) | The same, plus every silently dropped element | Also rejects trust, marker and padding packets, which the ring does not re-emit, so those must be accounted separately; higher false-reject risk. |
| T3: accept BC framing and rely on tag peek, allowlist and count reconciliation only | BC's silent skips and tag-level violations | Leaves HY1, HY2 and the framing differentials open. |
| T4: read header octets in application code | Anything | Custom framing; conflicts with the intent of the no-custom-parser rule. Not proposed. |

T1 and T2 are the only techniques that could close the Question 1 and 3 gaps using BC for all OpenPGP decisions; both are unverified, and both narrow acceptance to canonical encodings, which is a policy change the owner must approve.
