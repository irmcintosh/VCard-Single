# VCard Native — P0.5 Storage Architecture & Recovery Protocol Proposal

**Status: OWNER-ACCEPTED PROVISIONAL PREFERRED DIRECTION — NOT A FINAL STORAGE OR RECOVERY APPROVAL**  
**Date:** 2026-10-30  
**Decision coverage:** P0.5-04 (aggregate persistence), P0.5-05 (asset storage representation), P0.5-06 (recoverable backup/restore replacement)  
**Owner direction (2026-10-30):** immutable saved generations with immutable manifests and write-once app-private asset blobs, selected through a durable active-generation reference, are the provisional preferred architecture direction only. P0.5-04 remains **PENDING**; P0.5-05 remains **CONDITIONALLY APPROVED for ownership principles only**; P0.5-06 remains **PENDING**. The checksummed A/B pointer remains a candidate, not an approved or demonstrated durable commit mechanism. FG-02 remains **OPEN**.  
**Boundaries:** Documentation and architectural analysis only. No Android project, Gradle configuration, dependency, Kotlin code or test exists or was run. Nothing here selects a storage engine or authorizes implementation or a verification phase. Approved P0.1–P0.4 requirements and the owner's 2026-10-30 conditions ([approval record](P0.5_APPROVAL_RECORD.md)) are unchanged.

## 1. Summary

Three coupled designs were compared against the approved contracts: **(1)** immutable complete saved generations with one durable active-generation reference, **(2)** one serialized aggregate file holding metadata and asset bytes, and **(3)** transactional metadata (Room or DataStore) with separately owned assets and a recoverable journal.

**Owner-accepted provisional preferred direction (2026-10-30): approach 1, variant A2, at the architecture-direction level only: immutable saved generations with immutable manifests and write-once app-private asset blobs, selected through a durable active-generation reference.** This does not approve the final persistence engine, storage representation or recoverable commit protocol. The checksummed A/B active-pointer slot described in section 5 remains only one candidate mechanism. Reasons for the direction:

- Every Save and restore becomes "write new immutable objects, make them durable, then flip one small pointer". There is one commit domain, so no cross-resource transaction is needed and no separate journal has to be reconciled with a database.
- A text-only Save writes a new manifest (at most about 0.5 MiB) instead of rewriting up to about 16.6 MiB of assets (section 4).
- Old state stays complete and untouched until the pointer flips, which matches "old-or-complete-new" and the S02 rules.
- Immutability makes export captures, backup creation and garbage collection simple to reason about.
- Retain exactly one previously committed predecessor during normal operation, in addition to the active generation; this is not an unconditional maximum during interrupted operations, corruption investigation, or protected artifact lifetimes.

**What this does not establish.** No official Android document establishes crash-safe, durable multi-file commit. The design rests on documented POSIX file semantics (`fsync`, `rename`) plus explicit design assumptions about Android filesystems, directory durability and torn-write detection (section 3, assumption register A-1 to A-9). None has been tested. The A/B pointer, its checksums and the crash-state table do not prove durable commit or authorize startup rollback. Corrupted or incomplete saved state must not be silently reset, silently rolled back to an older generation, or exposed as valid. Unsaved editor drafts are not guaranteed to survive process death. FG-02 stays open.

**Decisions still open** are listed in section 11: exact pointer mechanism and durable write ordering; corruption detection/recovery and whether P0.2 can represent unreadable saved data; startup integrity depth; acceptable power-loss durability evidence; and bounded storage, cleanup and predecessor-retention details. Android automatic cloud backup and Android-managed device-to-device transfer are both excluded by owner policy; exact version-appropriate rule/configuration and verification for both remain future technical obligations.

## 5. The three approaches

### 5.1 Approach 1 — immutable complete saved generations with one active reference

Two sub-variants:

- **A1, self-contained generations:** every generation directory holds its own copy of all asset bytes.
- **A2, manifest generations over shared immutable blobs:** a generation is an immutable manifest; asset bytes live in write-once blob files referenced by random blob IDs. A generation is "complete" when its manifest and every blob it references are present and verified. Unchanged assets are reused by reference.

A1 is simpler to reason about but copies up to 16.56 MiB on every Save. A2 keeps the same old-or-new property with cheap Saves, and matches the owner-approved P0.5-05 principles (immutable IDs, generation-bound references, metadata derived from bytes). **A2 is the variant proposed.**

### 5.2 Approach 2 — single serialized aggregate file

One app-private file holds the profile data and the asset bytes; a Save writes a new file and renames it into place (for example through `AtomicFile`, which syncs before the rename **O**).

### 5.3 Approach 3 — transactional metadata with separately owned assets and a journal

Profile data lives in Room (or one DataStore object); asset bytes are separate immutable files; a durable operation journal records phases so startup can reconcile database, files and journal.

### 5.4 Comparison against the approved contracts

| Criterion | 1 (A2) | 2 (single file) | 3 (Room/DataStore + files + journal) |
|---|---|---|---|
| One saved profile, exact P0.4 schema | Manifest carries the AppData-shaped profile plus local metadata; schema owned by the app | Same, inside the container header | Room schema or DataStore object; schema owned by the library layer |
| Explicit Save; failed Save keeps draft and prior state | New objects staged, pointer flips last; failure before the flip leaves prior state intact | New file staged, rename last; same | Database commit and file commits are separate; the journal must order them |
| Exact-byte image and key retention | Blobs written once, hashed on write, never rewritten | Bytes embedded in the container; every Save rewrites them (copy risk, not alteration risk) | Files; same as 1 |
| Full backup captures one coherent state | Read active manifest, lease its blobs, stream from immutable files | Read one file (a stable inode if replaced mid-read) | Must read database and files under one lock to avoid mixing revisions |
| Validation before S02; candidate isolated | Candidate is staged blobs plus a candidate manifest, never visible | Candidate is a second whole file (up to about 16.6 MiB more) | Candidate files plus a candidate database state or journal entry |
| All-or-nothing replacement | Single commit domain (the pointer) | Single commit domain (the rename); durability of the directory entry still unproven | Two commit domains (database and journal/files); correctness depends on the journal protocol |
| Recovery logic | Choose by pointer; delete everything unreferenced | Choose file or leftover `.new`; delete the other | Three-way reconcile: database, files, journal |
| Stale S02 candidate | Compare pointer sequence under lock | Compare file identity under lock | Compare database revision and journal under lock |
| Export and share capture | Immutable manifest/blobs; leases protect them | Must copy asset bytes out of the container to files for sharing | Immutable files, but the database revision must be tied to them |

| Random access for display (portrait, cover) | Direct file reads | Needs an index and offsets inside a custom container | Direct file reads |
| Corruption handling | Manifest and slot checksums, blob lengths and hashes | Container checksum; one corrupt byte can affect everything | Database corruption plus file corruption; library-specific recovery |
| Schema evolution | New manifest per migration, crash-safe by the same protocol | Rewrite the container | Room migration tooling is a real advantage; files need their own versioning |
| Dependencies and API 31 | None beyond the platform | None beyond the platform | Room or DataStore (API floor and toolchain still unverified, FG-00) |

### 5.5 Findings

1. **Approach 2** is the simplest to explain but forces a custom container (index and offsets) to avoid loading about 16.6 MiB to show a card, rewrites everything on every edit, and still depends on an unproven directory-entry durability assumption for its single rename (the AtomicFile page does not state it).
2. **Approach 3** does not remove the cross-resource problem; it moves it into a journal. Every guarantee still rests on the file side, so the database adds a second commit domain without removing the first. Its one clear advantage is Room's migration tooling, which is little help for one row of data.
3. **Approach 1 (A2)** has one commit domain and makes the old state immutable. Its costs are custom code (pointer, manifest, blob layout, garbage collection) and a decision on corruption policy. Those costs exist for approach 3 as well.
4. None of the approaches is crash-safe merely because a primitive is "atomic". All three depend on A-1 to A-5.

## 6. Preferred candidate protocol (provisional, approach 1 / A2)

Everything in this section is a **proposal and an untested design**. It uses only plain files in app-private internal storage (**O**: private; encrypted on Android 10 and later).

### 6.1 On-disk layout and ownership

```text
<app-private root>/store-v1/
  INIT                      written once at the first commit; distinguishes "empty" from "damaged"
  ptr/slot-0                fixed-size checksummed pointer record (A)
  ptr/slot-1                fixed-size checksummed pointer record (B)
  gen/<manifestId>.manifest immutable generation manifest (profile data + asset table + checksums)
  blob/<blobId>             immutable, write-once asset bytes (JPEG, PNG or public-key armor)
  stage/<opId>/...          per-operation staging; never read as saved state
```

| Area | Written by | Read by | Rule |
|---|---|---|---|
| `ptr/` | Store coordinator only, at commit | Startup recovery and coordinator | Exactly two files; overwritten in place; each record is self-checksummed |
| `gen/` | Coordinator, once per manifest | Recovery, readers, backup creation | Never modified after the rename that publishes it; names are random manifest IDs, not counters, so an orphan cannot collide with a later Save |
| `blob/` | Coordinator, once per blob | Display, backup, export copy | Never modified or overwritten; names are random locally generated IDs, never archive names, user text or `assetId` (P0.4 asset IDs are untrusted input when they come from a backup) |
| `stage/` | Coordinator, per operation | Same operation only | Reclaimed only when demonstrably uncommitted, unreferenced and unprotected; never promoted except by rename into `blob/` and `gen/` |

Only one component (the store coordinator, within the approved P0.5-02 layering) touches these paths. The UI, picker results and export code never receive paths. Names carry no user text. Files are created with private modes.

**Manifest content (conceptual).** Store format version; random manifest ID; storage generation number; P0.4 `generationId` and `stateRevision`; the AppData-shaped profile (15 slots, visibility, appearance, `createdAt`/`updatedAt`); an asset table of `{assetId, role, blobId, mediaType, byteLength, sha256, plus existing ImageAsset/PublicKeyAsset descriptor fields}`; and a checksum over the whole manifest. The profile data is the same logical content as the backup `data.json`, so one serializer and one validator serve both.

**Pointer record (conceptual).** Magic; store format version; commit sequence number (strictly increasing); manifest ID; manifest length and SHA-256; P0.4 `generationId` and `stateRevision`; last committing operation ID and kind (save or restore); checksum over the record.

### 6.2 Commit point and durability assumptions

**Candidate A/B commit point:** the proposed protocol treats a successful durable write of a new pointer record (higher sequence number) into the inactive slot as its commit point. This is not approved or demonstrated as durable. A reader must not use a valid older slot as an automatic rollback when slot integrity leaves a newer commit uncertain.

- Before that write is durable, the previous slot still names the previous complete generation, whatever the staged files look like.
- If the new record is torn, its checksum fails and the previous slot wins (**A-3**).
- Success is reported to the UI only after the synchronous write of the record has returned successfully.

Why an in-place A/B slot rather than renaming a pointer file over the old one: the candidate was intended not to depend on rename-replace durability, and its failure mode may be detectable. It still depends on A-1 to A-4, and checksum validity alone does not establish which state is durably committed. The alternative (write a temporary pointer file, sync it, rename over `active`, sync the directory) has documented atomic naming (**S**) but needs A-2 for durability. The exact mechanism and ordering remain open (section 11, O-2).

### 6.3 Save sequence

Before Save, estimate the capacity needed for the complete new generation, all required temporary writes, the active and predecessor generations/assets and other protected data that must remain, active export/share pins, protected recovery evidence, and a safety reserve. Estimates inform admission/failure decisions but do not guarantee successful writes or durable commit; numerical reserve and calculation method remain open.

```text
validate draft (P0.4 rules)          -- no store lock held
acquire coordinator mutex
  compare (pointer sequence, generationId, stateRevision) with the draft's base; if changed, abort and refresh
  preflight space; on shortage fail before writing
  for each new or replaced asset:
      stream to stage/<op>/, hash while writing, check length and hash against the validated asset
      sync file; rename into blob/<blobId>
  sync blob/ directory
  write stage/<op>/manifest (new manifest ID, generation number + 1, stateRevision + 1, reused blobIds for unchanged assets)
  sync file; rename into gen/<manifestId>.manifest; sync gen/ directory
  re-read the manifest and check it (cheap check; not a durability proof)
  COMMIT: write pointer record to the inactive slot; sync
  publish new state to readers; report success
release mutex
schedule garbage collection
```

A cancelled or failed Save before COMMIT leaves the prior committed generation untouched. Its staging/new objects may be cleaned only after proving the operation did not commit and that each deletion is unreferenced and unprotected; otherwise preserve them for recovery.

### 6.4 Restore sequence (S02)

Before Restore begins writes, estimate capacity for the complete candidate generation, all necessary source/candidate staging and temporary writes, the active and predecessor generations/assets and other protected data, active export/share pins, protected recovery evidence, and a safety reserve. The estimate is advisory, not a guarantee of write or commit success; no threshold is selected.

```text
select source; stream into stage/<op>/ with bounds (no full copy of the archive needed)
validate ZIP framing, exact entries, actual sizes, CRC; strict JSON; hashes; asset relationships; image policy; key policy (P0.5-09/10 supply the validators)
write staged assets as stage/<op>/blob-*, hash while writing; sync them
build candidate manifest in stage/<op>/ (not published); record the base (pointer sequence, generationId, stateRevision) observed when S02 opens
S02 shows a summary derived from the candidate; Cancel or Back discards stage/<op> only when it is demonstrably uncommitted, safe to delete and not otherwise protected
on explicit confirmation:
  re-verify staged files (length and SHA-256) before taking the lock
  acquire coordinator mutex
    if the active pointer changed since S02 opened: do not commit; refresh the replace-target summary and require confirmation again
    rename staged blobs into blob/ under fresh blob IDs; sync blob/ directory
    finalize manifest: fresh generationId, stateRevision 1, backup timestamps retained; write, sync, rename into gen/, sync gen/
    COMMIT: pointer write to the inactive slot; sync
    publish new state; invalidate all previous export contexts (new generationId)
    report success only now
  release mutex
schedule garbage collection
```

An unsupported key format, any validation failure, cancellation or process death before COMMIT leaves the old state active (P0.4-11, policy B). No automatic pre-restore backup, history or undo is created.

### 6.5 Concurrent Save, restore, backup creation and export

- One **store coordinator** serializes every mutation and every state capture behind a process-local mutex (**A-6**; AtomicFile's documentation likewise puts mutual exclusion on the caller **O**).
- Mutations use **compare-and-set** on the pointer sequence. A Save from a stale base is refused and refreshed; a restore that finds a changed base is re-reviewed (section 6.4).
- Backup creation and export-artifact creation take the mutex only to read the active manifest and register a **lease** (an in-memory reference count) on its manifest and blobs, then stream without holding the mutex. Before any asset bytes are consumed or enter a backup/export artifact, they must pass Stage 2 validation (section 6.6); unverified bytes are never handed to UI, QR, vCard, Sharesheet, export or backup code. Blobs are immutable, so a concurrent Save cannot alter what is being read, and garbage collection skips leased objects.
- Nothing in the design supports a second process. DataStore has a multi-process mode **O**, but this design does not need it; adding an `android:process` component would invalidate A-6.

### 6.6 Active-generation identification and startup recovery

```text
1. A verified fresh-install/never-committed condition may be FIRST-RUN EMPTY. Absence of `store-v1/` or `INIT` alone is not sufficient after data may have been committed; if first-run cannot be distinguished from lost/corrupt saved data, state is DAMAGED/UNRESOLVED. The durable discriminator and its behavior remain undecided.
2. If INIT exists: read both slots and validate their format and checksums; do not infer an empty store from missing or invalid records.
3. Resolve the active reference only under a future approved mechanism that can establish the committed generation. A checksum-valid older slot is not by itself permission to roll back if another slot is invalid or commit ordering is uncertain.
4. Verify the selected manifest length and SHA-256; parse it strictly; validate its supported schema, required profile metadata, asset records (including expected sizes and SHA-256 values), and ownership/reference invariants. Check referenced blob presence as required for reference integrity; do not treat these metadata checks as proof of all blob bytes.
5. If the active reference, manifest, profile metadata and asset-reference records pass Stage 1, mark the generation **METADATA-VALID** only. Asset bytes not yet checked by Stage 2 remain unverified; do not label the complete profile fully verified. If reference selection is ambiguous, the schema/metadata/records are invalid, or required references fail: mark the store DAMAGED/UNRESOLVED and apply the provisional fail-closed policy in section 6.8. Do not reset, overwrite, silently select an older committed generation or expose invalid data as valid.
6. Recovery cleanup, idempotent: remove only staging artifacts demonstrably from an uncommitted operation and not protected by recovery or active-operation requirements; delete other manifests/blobs only when demonstrably unreachable from active/predecessor/protected roots and safe to reclaim. If commit status or protection is uncertain, preserve the data and fail closed.
7. Nothing is ever re-applied. A pointer candidate alone does not prove whether an interrupted operation committed.
```

**Truthful reporting after a crash.** To let the UI say what actually happened (P0.2-12), each operation writes a small intent record in its stage directory before COMMIT, and the pointer record names the last committing operation. On restart, if the active pointer names the interrupted operation it committed; otherwise it did not. This is a design need only; the exact UI behavior belongs to P0.2-12, unchanged.

**Provisional two-stage integrity policy (owner-approved 2026-10-30).**

- **Stage 1 — startup validation:** before treating saved profile metadata as valid, validate active-generation reference integrity/selection (subject to the unapproved pointer protocol), manifest structure and supported schema version, required profile metadata and structural validity, and referenced asset records including expected sizes, digests and ownership/reference invariants. Stage 1 validates metadata and references; it does not prove the integrity of referenced asset bytes.
- **Stage 2 — asset-use validation:** before an asset is consumed, displayed, exported, shared or otherwise used, verify its actual expected size and SHA-256 against the committed manifest, then apply any additional image or OpenPGP validation required by P0.4. No unverified asset bytes may enter UI, QR, vCard, Sharesheet, export or manual-backup workflows. A failed check blocks that asset's use and follows the provisional fail-closed corruption policy in section 6.8; do not reset, substitute an older committed generation or treat the bytes as valid.
- **Validity labels:** Stage 1 may establish **METADATA-VALID**. An asset becomes **ASSET-VERIFIED** only after Stage 2 passes. A profile is **FULLY VERIFIED** only after every asset referenced by its manifest has passed the required Stage 2 checks. Until then, do not claim full-profile verification.

**Implementation details remain unresolved.** The required stages do not select whether verification is synchronous, streamed, or cached; what binds a cached result to immutable bytes; how failures are surfaced and retried; how Stage 2 fits every asset access path; whether assets are verified lazily or all before a particular workflow; or how startup validation and use-time checks meet the 2-second warm-launch target. No cache may bypass a required Stage 2 check under this policy. The pointer protocol and durable commit remain unapproved; Stage 1 selection is conditional on a future approved mechanism.

### 6.7 Crash-state table

"Old" means the previously committed generation; "new" means the one being committed. The intended post-recovery invariant is one complete old or new generation; ambiguous states remain DAMAGED/UNRESOLVED and are not exposed as valid. No operation is re-applied. **All rows are design obligations; none has been tested.**

| # | Boundary | Possible on-disk state | State after restart | Recovery action |
|---|---|---|---|---|
| 1 | Before the mutex or during validation | Nothing written | Old | None |
| 2 | During blob write into `stage/` | Partial staged file | Old | Delete `stage/` |
| 3 | Blob synced, not yet renamed | Complete staged file | Old | Delete `stage/` |
| 4 | Blob renamed into `blob/`, directory not yet synced | New blob present, or absent | Old | Orphan blob (if present) is unreferenced; delete |
| 5 | Blob directory synced, manifest not written | Orphan blobs | Old | Delete orphans |
| 6 | Manifest partially written in `stage/` | Partial file | Old | Delete `stage/` |
| 7 | Manifest synced, not yet renamed | Complete staged manifest | Old | Delete `stage/` |
| 8 | Manifest renamed into `gen/`, directory not yet synced | Manifest present or absent | Old | Orphan manifest (if present) unreferenced; delete |
| 9 | Manifest and blobs durable, pointer not written | Complete unreferenced new generation | Old | Delete unreferenced new generation (not guessed as winner) |
| 10 | Pointer write in progress | Inactive slot torn, empty or complete | Candidate protocol intended old if the record is invalid and new if valid; actual durable outcome is unproven | Do not expose an older generation by checksum selection alone when commit state is uncertain; recovery behavior is unresolved |
| 11 | Pointer written, sync not yet returned | Record may be torn, absent or complete | Old or new may be present; actual durable outcome is unproven | Do not silently roll back or expose incomplete/ambiguous state; exact resolution requires an approved mechanism |
| 12 | Pointer sync returned (committed) | Committed | New | None |
| 13 | After COMMIT, before the UI is told | Committed | New | UI reconciles via the pointer's last operation (section 6.6); no success is replayed, no operation retried |
| 14 | During garbage collection | Some unreferenced files deleted | Same active state | Rerun; converges |
| 15 | Restore: during source copy, parsing or validation | Staged files | Old | Delete `stage/` |
| 16 | Restore: candidate built, S02 open | Staged candidate | Old | Delete `stage/`; S02 is gone |
| 17 | Restore: base changed while S02 open | Staged candidate | Old (newer saved state) | Refuse commit, refresh, require reconfirmation |
| 18 | Restore: blobs partly renamed into `blob/` | Some blobs moved | Old | Unreferenced blobs deleted |
| 19 | Restore: rows 7 to 13 | As for Save | As for Save | As for Save |

**Corruption and environment rows**

| # | Condition | Behavior |
|---|---|---|
| 20 | One slot corrupt, other valid | Do not silently use the valid slot as a rollback target if the corrupt slot could conceal a newer commit; mark unresolved and do not expose saved data as valid until an approved recovery rule establishes the active state |
| 21 | Both slots invalid, INIT present | DAMAGED; fail closed; never treat as empty |
| 22 | Active manifest missing or checksum mismatch | DAMAGED path (section 6.8) |
| 23 | Referenced blob missing or wrong length | DAMAGED path |
| 24 | Blob hash mismatch found on read | Treat as corruption of that asset; no use or export; DAMAGED path decision applies |
| 25 | `ENOSPC`, quota or `EIO` at any write, sync or rename | Operation fails before COMMIT (or at COMMIT, in which case it is not reported as success and recovery decides); delete staged files; state unchanged |
| 26 | Unknown newer store format version | Refuse to open or modify; state unchanged |
| 27 | Misconfigured/legacy cloud backup or Android-managed device transfer delivers an older or newer set of store files despite the approved exclusions | Treat only as a crash-state candidate; verify both exclusions for relevant Android versions (**A-8**, T-14) |

Rows 1-9 describe interruption before a new commit is established: continuing with the last demonstrably committed complete generation can be valid recovery, not an unauthorized rollback. Rows 10-11 leave commit outcome uncertain and do not establish which generation is durable. Neither case authorizes falling back to an older generation when the previously committed profile itself is corrupted.

Cleanup actions shown in the crash-state table are conditional on establishing that artifacts are uncommitted, demonstrably safe to delete, and not protected by recovery or active-operation requirements. In particular, row 25 does not authorize deleting protected staging, generations, artifacts or evidence when `ENOSPC`/`EIO` occurs at an uncertain commit boundary.

### 6.8 Low storage, cancellation, corruption and process death

- **Owner-approved provisional capacity-estimation policy (2026-10-30).** Before Save or Restore, estimate capacity for the complete new generation, all necessary temporary writes, protected existing generations/assets, active export/share pins, protected recovery evidence, and a safety reserve. Estimates are advisory, not guarantees of successful writes or durable commits. The section 4 figures are examples only and do not select numeric budgets, reserve thresholds or cleanup limits.
- **Fail-without-replacement under low storage (2026-10-30).** If Save cannot safely complete, fail without replacing the existing committed profile. If Restore cannot safely complete, fail without partially replacing it, preserving P0.4 all-or-nothing Restore and explicit Save behavior. Keep the active and protected predecessor throughout staging. Do not sacrifice protected roots to make space. A failed pre-commit operation leaves the last demonstrably committed profile authoritative; report success only after required durable commit establishment.
- **Write failures and open mechanics.** Handle storage exhaustion and I/O failure at every step. `ENOSPC`, `EDQUOT` or `EIO` at any write/sync/rename fails the operation; if commit is not demonstrably established, do not report success or replace the last demonstrably committed profile. Preserve protected roots even if that means retaining temporary data and returning a storage failure. Exact capacity calculation, filesystem overhead/reserve sizing and behavior at individual commit steps remain open.
- **Cancellation.** Before COMMIT, remove staging and newly written objects only when demonstrably uncommitted, safe to delete, and not protected by recovery or active-operation requirements. If COMMIT has begun or status is uncertain, preserve evidence and recover under the fail-closed policy; N06's approved progress state prevents dismissal once COMMIT begins, but does not prove durability.
- **Process death.** All in-memory state (mutex, leases, S02 candidate handle) is lost. Recovery may reclaim staging only when it is demonstrably uncommitted and unprotected; preserve ambiguous/protected artifacts. The pointer protocol remains unapproved and does not by itself prove commit durability.
- **Provisional owner policy (2026-10-30): fail closed for unreadable, corrupted, incomplete or invalid saved profile data.** Do not silently reset it to an empty profile, silently activate an older generation when the previously committed profile is corrupted, or expose invalid/incomplete data as a valid profile. Preserve affected data for potential recovery, subject to future explicit retention and storage limits. Require an explicit, user-controlled recovery or replacement process consistent with the approved P0.4 manual full-backup and restore workflow. This policy does not approve a recovery screen, dialog, navigation change or P0.2 change.
- **Interrupted Save distinction:** if evidence establishes that a Save was interrupted before committing, continuing with the last demonstrably committed complete generation may be valid recovery. This is not permission to fall back when the previously committed generation is corrupted or when the durable commit cannot be established.
- **Unresolved mechanics (O-3):** exact corruption detection/classification; how to establish the last durable commit; pointer-slot corruption/disagreement; recovery mechanics and preservation limits; whether existing P0.2 UI can display the condition and support user-controlled recovery, and whether P0.2 change control is required; startup integrity depth; and acceptable durability evidence. No predecessor fallback is authorized for committed-generation corruption. This document does not modify P0.2.

### 6.9 Stale S02 candidate handling

- A candidate carries an in-memory handle, its staged file list with lengths and SHA-256 digests, and the base (pointer sequence, `generationId`, `stateRevision`) recorded when S02 opened.
- Before commit: re-verify the staged files outside the lock (bounded by the approved sizes), then under the mutex compare the base with the active pointer. Any difference refuses the commit, refreshes the summary of what would be replaced and requires confirmation again (P0.4 backup section 5).
- Process death or dismissal discards the candidate; there is no persisted candidate. A candidate older than the active state is never promoted implicitly.

### 6.10 Export-snapshot and active-share retention

- Export artifacts (`.vcf`, QR PNG, key download) are **copies** made from an immutable captured snapshot into the cache area owned by P0.5-11. They do not point at store blobs, so garbage collection of store files can never break an active receiver, and the 24-hour unused-cache target is a separate matter for P0.5-11 (**I**). If P0.5-11 later chooses to serve a key or image directly from a blob, that artifact must hold a lease and this decision must be revisited.
- Every referenced asset must pass Stage 2 (size, SHA-256 and applicable P0.4 image/OpenPGP validation) before its bytes are read into the `.vcf`, QR, key-download, Sharesheet or manual-backup output path. A metadata-valid snapshot does not make unchecked asset bytes safe to expose.
- During the copy, the operation holds a lease on the manifest and blobs it reads; do not release protection while an export/share operation still requires the source assets. Generated artifacts remain protected while an active export or sharing operation requires them; exact pin/release conditions remain open under P0.5-11.
- Snapshot validity (P0.4 section 6 of the QR contract) uses `generationId` and `stateRevision`; a Save or restore advances them and invalidates in-app derived artifacts conservatively.
- This satisfies owner condition 3 for P0.5-05: cleanup never deletes a saved asset or one pinned by an active export (a pin exists only while a lease or the active/predecessor manifest references it).

### 6.11 Idempotent garbage collection

- **Roots during normal operation:** the active manifest and exactly one previously committed predecessor manifest. Also protect every manifest/blob and generated artifact needed by an active export or sharing operation, an in-flight Save/restore, or recovery evidence protected under the fail-closed policy. **Reachable blobs:** all blobs referenced by any protected root.
- **Sweep gate:** cleanup starts only after the new commit is established where applicable, all protected references/ownership are completely reconciled, and each deletion candidate is proven unreferenced and unprotected. Under the mutex, remove only data demonstrably safe to reclaim; delete unreferenced manifests before blobs, then eligible empty staging. Do not silently delete corrupted data or recovery evidence. Preserve additional generations or artifacts beyond the normal one-predecessor target while interruption, corruption investigation, or active protections require them; one predecessor is not an unconditional maximum.
- **Idempotence:** cleanup is interruptible, repeatable after process death and converges without touching the active generation, retained predecessor, pinned artifacts, protected recovery evidence, `ptr/`, `INIT` or any other protected root. Reachability uncertainty fails closed and postpones deletion.
- **Scheduling/bounds:** exact scheduling, normal-operation storage budget, low-storage behavior and preservation limits remain open. Cleanup may be considered after commit, during startup recovery or on low storage only subject to the sweep gate and protection rules; work is bounded by the eventual owner-approved limits. Low storage is not authority to delete or sacrifice the active generation, normal predecessor, pinned export/share artifacts, or protected fail-closed recovery evidence merely to make room for a new Save or Restore.
- No file name, path or content is logged.

### 6.12 Schema evolution and migration

Three versions are kept separate: the store format version (pointer and manifest layout), the AppData `schemaVersion` (P0.4, currently 1) and the backup `formatVersion`/`appSchemaVersion` (P0.4, currently 1).

- A migration is a **new generation**: read the old manifest, transform, write a new manifest through the normal Save commit protocol. It is crash-safe by construction and never rewrites a blob (no re-encoding, consistent with P0.4 and owner condition 2).
- A store with a newer format version than the app knows is refused without modification (row 26).
- The pointer records the store format version; a mixed-version store is never opened.
- Each future version keeps a golden fixture store for migration tests.
- P0.4 promises no deployed-backup migration for v1.0; this section covers only the app's own store.

## 7. Candidate comparison result

Approach 1 (A2) is preferred **provisionally** because it needs one commit domain, makes old state immutable, writes little on a text-only Save and supports leases and garbage collection simply. Approach 2 is the fallback if the owner prefers fewer moving parts and accepts the rewrite cost and a custom container. Approach 3 is not recommended because it adds a second commit domain without removing the file-side requirements.

**What would change this recommendation:** evidence that fsync or directory sync is unreliable on target devices (every design is then weakened; approach 2's single rename would not escape that); a measured startup cost that breaks the 2-second target; or an owner preference to accept a library for migrations over custom code.

## 8. Interaction with Auto Backup and device transfer

By default, files under `getFilesDir()` are in Auto Backup, the system stops the app first, the 25 MB cloud quota applies and restore occurs before first launch (**O**). The default behavior does not determine the owner's policy or exact implementation configuration.

**Owner-approved Android automatic cloud backup policy (2026-10-30):** exclude all VCard Native locally saved profile data from Android automatic cloud backup. This covers saved profile metadata and personal information; profile visibility and appearance settings; app-owned images and public-key assets; immutable generations and manifests; active-generation pointer records; retained predecessor generations; and draft, staging and recovery artifacts containing profile information. The approved manual full-backup and restore functionality in P0.4 is unchanged.

**Owner-approved Android-managed device-to-device transfer policy (2026-10-30):** exclude all locally saved profile data from Android-managed device-to-device transfer, covering the same profile metadata/personal information, visibility/appearance settings, owned images and public-key assets, generations/manifests/blobs, active pointers, retained predecessors, and profile-bearing drafts/staging/recovery artifacts listed above. This is a separate approved policy, not an inference from cloud-backup exclusion. Android automatic cloud backup: **EXCLUDED**. Android-managed device-to-device transfer: **EXCLUDED**. The supported cross-device migration method remains VCard Native's approved P0.4 manual full-backup and restore workflow.

The exact Android backup-rule and device-transfer configuration, including relevant Android-version-specific behavior, and evidence that every scoped artifact is excluded remain future technical obligations. No configuration is selected or implemented and no verification is performed here. Do not assume one Android configuration applies identically to cloud backup and device-to-device transfer.
