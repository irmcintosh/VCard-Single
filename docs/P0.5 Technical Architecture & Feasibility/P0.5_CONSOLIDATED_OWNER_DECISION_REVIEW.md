## 4. Decision reviews

### P0.5-01 — Platform and toolchain

- **Proposed choice:** Keep the section 2 baseline unchanged. `minSdk 31` stays a candidate. Do not select `targetSdk` or `compileSdk` from a research snapshot. Verify each selected Android API, library minimum SDK, bytecode and desugaring need, and AGP/JDK/Kotlin/Compose compatibility before the floor becomes final.
- **Alternatives:** A higher `minSdk` only with evidence and owner approval. A lower floor would contradict the owner's selection and needs explicit revision. Target and compile values are reasoned separately, not inferred from the floor.
- **Rationale and evidence:** Strong: Android documents Android 12 as API 31. Moderate: Room 2.8.5 declares minimum 23; Navigation 2.10.2 and ExifInterface 1.4.2 report floors below 31. These partial facts do not certify any used code path. None: the full dependency graph, BC 1.86, ZXing and the chosen UI libraries on API 31.
- **Relevant approved requirements:** P0.1 device/release and offline requirements (record model, OS and SDK; signed APK; test on a real Pixel); P0.1 FR-06; P0.4-12; P0.5 baseline approval of 2026-10-29.
- **Risks, dependencies, gates:** FG-00. The choice constrains navigation (03), OpenPGP (09), QR (08), vCard (07) and images (10). Android 17 results cannot stand in for API 31.
- **Recommended disposition:** **CONDITIONALLY APPROVE.**
- **Conditions:**
  1. Approval covers only the section 2 baseline and the compatibility-inventory method. `minSdk 31` becomes final only when FG-00 evidence shows every selected API and dependency supports API 31; otherwise the failing item returns to the owner.
  2. `targetSdk` and `compileSdk` are not selected by this approval and need separate owner approval with documented reasoning.
  3. No Android Studio project, Gradle configuration or dependency is created by this approval.

### P0.5-02 — Layering and dependency direction

- **Proposed choice:** A single app module with presentation, policy/projection, repository and Android-adapter boundaries. Keep Android `Context`, `Uri`, `Intent` and Compose types out of deterministic profile projection and validation rules where practical.
- **Alternatives:** Multi-module domain/data/platform; direct screen-to-storage calls; a broad service-locator or DI framework.
- **Rationale and evidence:** Strong: Android architecture guidance ([recommendations](https://developer.android.com/topic/architecture/recommendations), [UI layer](https://developer.android.com/topic/architecture/ui-layer)). App-specific fit is a proposal. A single profile does not justify the build cost of extra modules; separating projection from Android types protects the export-privacy rules.
- **Relevant approved requirements:** P0.1 FR-03; P0.4-02, P0.4-04, P0.4-05 (independent projections), P0.4-12.
- **Risks, dependencies, gates:** Low. Over-modularizing adds build burden; under-separating risks leaking hidden fields or partial restores. Traceability only under FG-07.
- **Recommended disposition:** **APPROVE.**
- **Conditions:** None beyond scope. This approves a direction, not code. Adding modules or a DI framework later needs owner approval.

### P0.5-03 — UI state, navigation and lifecycle

- **Proposed choice:** Compose with one-way data flow, immutable screen state, ViewModel/StateFlow and lifecycle-aware collection. Unsaved editor state stays separate from the durable saved profile. Navigation state carries route and caller context, never profile, key or image payloads.
- **Alternatives:** Navigation 2, Navigation 3, or a small custom back stack. No preference is recorded.
- **Rationale and evidence:** Strong guidance ([Compose state](https://developer.android.com/develop/ui/compose/state)); Moderate release metadata for Navigation 2.10.2 and Navigation 3 1.2.0. None for flow behavior against the six destinations, S01/S02, D01, Clarification B caller return, process recreation and predictive Back.
- **Relevant approved requirements:** P0.2-01 to P0.2-05, P0.2-07, P0.2-08, P0.2-10, P0.2-12; Clarifications A and B; P0.3-09, P0.3-11, P0.3-12; P0.1 FR-02.
- **Risks, dependencies, gates:** FG-00 (compile SDK, AGP, Kotlin), FG-06 (activity results). Navigation 3 continues to evolve on overlays and Back behavior.
- **Recommended disposition:** **CONDITIONALLY APPROVE.**
- **Conditions:**
  1. Approval covers only the state pattern and the rule that navigation state holds no payloads.
  2. The navigation framework is not approved. It is chosen after FG-00 resolves the toolchain, with a documented fit to the P0.2 flows, stable APIs only.
  3. No new route, Settings screen or dialog is introduced.

### P0.5-04 — Aggregate persistence

- **Proposed choice:** One saved aggregate with the exact P0.4 schema and explicit versioning. No storage engine selected.
- **Alternatives:** DataStore for one small typed object; Room for structured metadata; a serialized immutable generation.
- **Rationale and evidence:** Strong: [DataStore guide](https://developer.android.com/topic/architecture/datastore) describes single-object updates; Moderate: Room 2.8.5 and DataStore 1.3.0 snapshots. DataStore and Room transactions do not span separate asset files, so the engine cannot be chosen before the commit protocol (06).
- **Relevant approved requirements:** P0.4-01, P0.4-02, P0.4-03; P0.1 FR-06 and the persistence requirement (survives process and device restart).
- **Risks, dependencies, gates:** FG-02. Coupled to 05 and 06.
- **Recommended disposition:** **KEEP PENDING.**
- **Conditions to move:** Decide jointly with 05 and 06 once the commit protocol is specified.

### P0.5-05 — Owned asset storage and lifetime

- **Proposed choice:** App-private exact bytes with immutable identifiers; metadata derived and revalidated from bytes; generation-bound references; picker URIs are transient inputs and never persistent paths or backup references; saved, draft and in-flight export references have distinct lifetimes.
- **Alternatives:** Embed asset bytes in the aggregate; sidecar immutable files.
- **Rationale and evidence:** Strong: Android storage and FileProvider boundaries. The lifecycle protocol is unverified.
- **Relevant approved requirements:** P0.4-09, P0.4-10, P0.4-11; P0.2-04, P0.2-12; P0.1 FR-01.
- **Risks, dependencies, gates:** FG-02, FG-05, FG-06. The representation choice depends on 04 and 06.
- **Recommended disposition:** **CONDITIONALLY APPROVE.**
- **Conditions:**
  1. Approval covers the ownership principles only; embedded versus sidecar representation is deferred to the 04/06 decision.
  2. Stored public-key and image bytes are never re-encoded; the stored digest keeps identifying the retained bytes.
  3. Cleanup never deletes a saved asset or an asset pinned by an active export.

### P0.5-06 — Backup validation and recoverable replacement

- **Proposed choice:** Preserve strict P0.4 STORE-only ZIP32 validation. Evaluate a new immutable complete generation plus one durable active reference against a recoverable journal spanning metadata and files. No protocol selected; `AtomicFile` is single-file and not an aggregate transaction.
- **Alternatives:** Generation pointer; journaled metadata and files; one serialized aggregate.
- **Rationale and evidence:** Strong: [AtomicFile](https://developer.android.com/reference/android/util/AtomicFile) limits, [ZIP traversal guidance](https://developer.android.com/privacy-and-security/risks/zip-path-traversal). No evidence of whole-state recovery.
- **Relevant approved requirements:** P0.4-10, P0.4-11; P0.2-08; P0.1 FR-06; condition C (unsupported historical keys reject the whole candidate).
- **Risks, dependencies, gates:** FG-02, highest data-loss blast radius. Depends on 04, 05 and, for key screening, 09.
- **Recommended disposition:** **KEEP PENDING.**
- **Conditions to move:** A documented protocol with a durable commit boundary, an old-or-complete-new failure matrix, idempotent restart recovery, low-storage, cancellation and concurrency handling, delayed cleanup, and a fault-injection plan. No incomplete candidate may replace live data.

### P0.5-07 — Contact/vCard

- **Proposed choice:** Retain the P0.4 provisional vCard 3.0 mapping (`FN` plus empty `N`). Evaluate ez-vcard 0.12.2 against a narrowly allowlisted serializer. 4.0 remains a paired evaluation only.
- **Alternatives:** ez-vcard; allowlisted serializer; vCard 4.0 (only by explicit owner approval).
- **Rationale and evidence:** Strong: RFC 2426 and RFC 6350. Moderate: ez-vcard BSD-3-Clause is stated in the sharing draft, but a direct upstream license citation is still outstanding. None: Pixel and second-recipient import behavior, empty-`N` effects.
- **Relevant approved requirements:** P0.4-04, P0.4-05; condition B; P0.1 FR-03, FR-04; P0.2-06.
- **Risks, dependencies, gates:** FG-04; shares the projection with QR (08); API-31 suitability.
- **Recommended disposition:** **KEEP PENDING.** (The vCard 3.0 target is already approved provisionally under P0.4 condition B and is unaffected.)
- **Conditions to move:** The owner chooses a library or serializer after API-31 and byte-policy (UTF-8, CRLF, 75-octet folding, 64 KiB) evidence and a direct license citation. Any change to 4.0 needs explicit owner approval.

### P0.5-08 — QR encoding and rendering

- **Proposed choice:** ZXing core 3.5.4 (Apache-2.0) as the encoder candidate, keeping the Model 2 / level M / smallest fitting version 1–40 / ASCII without ECI / non-ASCII UTF-8 ECI 26 contract and the 4,096-byte guard (a resource limit, not a capacity claim).
- **Alternatives:** Another maintained encoder with the same controls; not yet compared.
- **Rationale and evidence:** Moderate: ZXing 3.5.4 [Encoder](https://raw.githubusercontent.com/zxing/zxing/zxing-3.5.4/core/src/main/java/com/google/zxing/qrcode/encoder/Encoder.java) and [QRCodeWriter](https://raw.githubusercontent.com/zxing/zxing/zxing-3.5.4/core/src/main/java/com/google/zxing/qrcode/QRCodeWriter.java) show version, error-correction and character-set hints and a matrix path. None: ECI assignment in practice, API-31 behavior, scanner recognition.
- **Relevant approved requirements:** P0.4-06, P0.4-07; P0.3-07; P0.2-05; P0.1 FR-04 and the 1-second QR target.
- **Risks, dependencies, gates:** FG-03; depends on 07 payload size and 01 compatibility.
- **Recommended disposition:** **CONDITIONALLY APPROVE** as a provisional candidate only.
- **Conditions:**
  1. It must provide Model 2, level M, smallest-fit version, ECI 26 only for non-ASCII, and an unscaled matrix. A miss returns to the owner; no truncation, correction downgrade or web fallback.
  2. API-31 compatibility and license notices are verified.
  3. No scan success is claimed without device and second-scanner evidence.
  4. If the candidate fails, alternatives are compared at that point.

### P0.5-09 — OpenPGP

- **Proposed choice:** **Direct Bouncy Castle 1.86** (`bcpg`, `bcprov`, `bcutil` `-jdk18on`, one aligned family) through the high-level `org.bouncycastle.openpgp.api` certificate API: **PROVISIONALLY PREFERRED** by owner direction. Not approved; no dependency pinned or installed. See section 5 for the preserved findings and the acceptance evidence that would eventually be required.
- **Alternatives:** PGPainless core 2.0.4 (declares BC 1.84, inside the CVE-2026-71886 range; blocked until a release declares BC 1.86 or later); GopenPGP v3.5.2 via Go Mobile (no published Android artifact; fallback). A custom parser is excluded.
- **Rationale and evidence:** Strong: RFC 9580 and RFC 4880. Moderate: BC 1.86 release notes and tagged source. See public-key feasibility sections 9, 10, 11 and 12. None: build, runtime, per-row and API-31 evidence.
- **Relevant approved requirements:** P0.4-08; condition C (five-row matrix, each **REQUIRES FEASIBILITY VALIDATION**; no silent reduction; no custom cryptographic parser); the settled retention and rejection policies; P0.2-11; P0.1 FR-01 and the no-private-key-export requirement.
- **Risks, dependencies, gates:** FG-01, with FG-00, FG-02 and FG-07. Section 5.1 lists every unresolved finding.
- **Recommended disposition:** **KEEP PENDING**, consistent with the owner direction.
- **Conditions to move to approval:** The section 5.2 evidence exists and the owner has decided the seven section 11H items.

### P0.5-10 — Image canonicalization

- **Proposed choice:** Bounded platform decode and encode plus ExifInterface 1.4.2; no decoder or encoder selected.
- **Alternatives:** `BitmapFactory` or `ImageDecoder` with platform encoders; a maintained third-party image library (not evaluated).
- **Rationale and evidence:** Strong: Android [supported formats](https://developer.android.com/media/platform/supported-formats), [ImageDecoder](https://developer.android.com/reference/android/graphics/ImageDecoder), [ExifInterface](https://developer.android.com/reference/androidx/exifinterface/media/ExifInterface). Sixteen million ARGB pixels nominally use 64 MiB before scratch buffers, so compressed limits do not bound memory. None: WebP alpha/lossless classification, orientation, sRGB and metadata-removal behavior.
- **Relevant approved requirements:** P0.4-09; P0.3-03; P0.2-07; P0.1 FR-01.
- **Risks, dependencies, gates:** FG-05 (memory, privacy). Feeds 05 and 12.
- **Recommended disposition:** **KEEP PENDING.**
- **Conditions to move:** The owner chooses a decode/encode path with a stated peak-memory bound, WebP and animation classification, orientation and color rules, and a metadata-removal rationale.

### P0.5-11 — Native handoffs and temporary artifacts

- **Proposed choice:** Activity Result APIs with SAF and Photo Picker for selection and destination; app-private temporary output; a dedicated FileProvider with narrow paths and temporary read-only grants; native Sharesheet and approved contact destinations.
- **Alternatives:** Platform contract variants; provider wrappers; exact API and subclass path not selected.
- **Rationale and evidence:** Strong: Android [FileProvider security](https://developer.android.com/privacy-and-security/risks/file-providers), [secure sharing](https://developer.android.com/training/secure-file-sharing/share-file), SAF documentation. None: provider cancellation, partial writes, receiver grant lifetime, cleanup.
- **Relevant approved requirements:** P0.4-05; P0.2-06, P0.2-09; P0.1 FR-04 and the privacy and security requirement.
- **Risks, dependencies, gates:** FG-06. Depends on 01 and 03; backup export (06) uses the same write path.
- **Recommended disposition:** **CONDITIONALLY APPROVE** (mechanism family only).
- **Conditions:**
  1. Exact artifact versions, manifest entries, provider subclass and paths are approved separately.
  2. An external return is never reported as delivery; unknown outcomes never trigger duplicate handoffs.
  3. No `.vcf` or contact-image artifact is created before the required S01 confirmation.
  4. No broad storage permission, and no claim that earlier external copies can be revoked.
  5. The 24-hour unused-retention target never breaks active receiver access.

### P0.5-12 — Cross-cutting safeguards

- **Proposed choice:** Bounded streaming work off the main thread where needed, cooperative cancellation, checked arithmetic, an explicit error taxonomy, redacted logging, minimum permissions, and deterministic seams for later verification.
- **Alternatives:** Per-operation limits and handlers versus shared policy utilities.
- **Rationale and evidence:** Strong: product requirements. None: worst-case CPU and memory, race and restart behavior, accessibility and performance measurements.
- **Relevant approved requirements:** P0.4-12; P0.1 performance, reliability, accessibility and privacy requirements; P0.3-11, P0.3-12.
- **Risks, dependencies, gates:** FG-07. Each parser and codec limit depends on 07, 08, 09 and 10.
- **Recommended disposition:** **CONDITIONALLY APPROVE** (principles only).
- **Conditions:**
  1. The threading and concurrency model, per-parser and per-codec limits, permission inventory and measurement method are not approved by this decision.
  2. No personal content, key material or file path is logged.
  3. The P0.1 targets (usable card within 2 seconds of warm launch; QR within 1 second) remain targets, not measurements.
  4. A fixed constraint that proves infeasible is escalated to the owner.

## 5. P0.5-09 provisional direction

### 5.1 Unresolved findings preserved from the final OpenPGP investigation

All of these remain open. None is claimed resolved. Tags refer to public-key feasibility sections 11 and 12 (**HY** = untested hypothesis from source reading).

| # | Finding | Source section |
|---|---|---|
| U-1 | The seven packet-handling policies (rules R1 to R10 and the seven section 11H decisions) are **not approved**. | 11G, 11H, 12 |
| U-2 | Complete packet accounting is **unresolved**. A declared body length longer than the packet content may make BC absorb following packets, up to the 8,192-byte buffer (**HY1**). | 12B, 12C Q1 |
| U-3 | Secret-key rejection "anywhere" is **unresolved**, not demonstrated. HY1 and the early certificate-loop stop on a null return (**HY2**) could hide a later packet. | 12C Q3 |
| U-4 | Two BC passes share the same framing blind spot, so count reconciliation cannot detect HY1. | 12B |
| U-5 | Partial and indeterminate lengths are not exposed by BC; only old-format detection is available. | 12C Q2 |
| U-6 | The malformed-CRC clause **cannot be met** with BC 1.86 as retrieved (a malformed CRC line throws even with the CRC ignored); the wrong-CRC default requires `setIgnoreCRC(true)`; `PGPUtil.getDecoderStream` offers no CRC option. This conflicts with P0.4 and RFC 9580 section 6.1 and is not resolved. | 12C Q5 |
| U-7 | Armor leading and trailing text is skipped leniently; the label is not verified by BC; header limits are global defaults. An envelope text check is an unapproved owner decision. | 11B, 12C Q5 |

| U-9 | BC's ring reader silently drops markers, padding, unsupported-version signatures and unrecognizable subkeys; single-certificate methods ignore trailing content; top-level tags 13, 17 and 19 swallow the rest of the stream; padding at top level throws. | 11B |
| U-10 | Key packets accept versions 2 to 6 and unknown v5/v6 algorithms as unknown keys; BC does not enforce the 64 KiB, 128-packet, 4-subkey and 8-user-ID limits. The application must. | 11B, 11F |

| U-12 | Revocation classification is **unresolved**: the API alone cannot separate a verified revocation from a forged one; third-party and designated-revoker revocations cannot be verified offline and do not affect usability; v6 revocation-only handling needs an owner ruling; clock uncertainty remains. | 12C Q7 |
| U-13 | `OpenPGPCertificate` may collapse duplicate user IDs at its map layer; reconciliation must use ring-level accessors. | 12C Q4 |
| U-14 | None of the five matrix rows has independent test vectors, and none is demonstrated for BC. | 10, 12 |
| U-15 | No API-31 build, R8 or desugaring result exists; BC license notices and the transitive closure are unaudited; advisories were checked only as of the access date (CVE-2026-71886 covers BC 1.81–1.85.2, not 1.86). | 9, 10 |
| U-16 | PGPainless is blocked until a release declares BC 1.86 or later; GopenPGP has no published Android artifact. | 9, 10 |

## 7. Cross-decision conflicts, sequencing dependencies and blockers

**Dependencies**

1. **01 gates the rest.** `compileSdk`, AGP, Kotlin and Compose determine which navigation option (03) is available and whether BC 1.86 (09), ZXing (08) and the others build and run on API 31.
2. **04, 05 and 06 are one coupled design.** The commit protocol (06) drives the storage engine (04) and the asset representation (05). Approving any one in isolation could constrain the others.
3. **09 and 06 share a pipeline.** Restore must apply the same key screening as import, and key bytes must be stored and restored verbatim. HY1 matters here: absorbed bytes would be retained in the stored asset, so a screening gap becomes a data-retention gap.
4. **07 and 08 share the projection.** The vCard output size feeds the QR guard (4,096 bytes) and the ECI decision.
5. **03 and 11 share lifecycle handling** for activity results, caller return and process recreation; 11 and 06 share the SAF write path for backup export.
6. **10 and 05** share the canonical image bytes; **10, 09 and 12** share the memory and CPU budget, so limits must be set together (12).

**Conflicts and blockers**

- **B-1 No authorized path to runtime evidence.** Every gate needs build or device evidence, but implementation is not authorized and no further OpenPGP investigation is authorized. The owner's partial approval of 2026-10-30 did not authorize a verification phase. The gates cannot leave OPEN until the owner separately decides on one. This review does not request it.
- **B-2 P0.4 text conflicts for 09** (U-6, U-8; also U-11 on legacy framing). P0.4 cannot be changed here. If BC cannot meet a clause, the owner must decide under change control; the clause must not be silently weakened.
- **B-3 Possible need for custom framing.** If no BC-only technique accounts for every byte (E-3), the remaining options are a different library, a documented limit, or application-level packet framing. P0.4 condition C prohibits a custom cryptographic parser; whether application packet framing is covered by that prohibition is an owner interpretation that this review does not presume.
- **B-4 Unselected `targetSdk` and `compileSdk`** block dependency resolution and the navigation choice.
- **B-5 The 07 license citation and the 08 alternative comparison** are minor documentary gaps. They do not block an approval sequence but must be closed before the related decisions are finalized.

No conflict with approved P0.1–P0.4 requirements was found in the decision descriptions, apart from the P0.4 clause conflicts listed under B-2.
