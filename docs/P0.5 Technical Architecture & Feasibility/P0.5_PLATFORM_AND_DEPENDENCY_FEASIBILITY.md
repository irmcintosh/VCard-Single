Official Android platform documentation maps Android 12 to API level 31. This establishes the OS/API mapping, not the feasibility of the app's dependency graph or used API paths. The Pixel 9 Pro XL/Android 17 is the primary research target only; the OS/device facts are owner-supplied and no device query or test has been performed.

P0.5 must check each selected API, direct and transitive Android artifact, Java/Kotlin bytecode/library API, desugaring requirement, Android Gradle Plugin (AGP), Kotlin/Compose compiler compatibility and manifest behavior against the API 31 floor. An AAR's declared `minSdk` below 31 is necessary evidence but does not prove that every code path used by VCard Native is safe on API 31. Conversely, API-specific media parsing or platform APIs may require conditional paths even when an AndroidX artifact supports API 31. The supported OS/device range and distribution channel requirements must be explicit before final SDK recommendations.

## 2. Evidence categories

This research separates four kinds of evidence:

- **Platform fact:** Android version-to-API mapping or an API's documented introduction level.
- **Artifact metadata:** publisher-declared version, license and `minSdk`/`compileSdk` metadata for a specific artifact revision.
- **Build evidence:** a resolved dependency graph compiles and packages with the selected JDK, AGP, Kotlin, Compose compiler, `compileSdk` and `minSdk`.
- **Runtime evidence:** the exact used paths execute correctly on API 31 and the declared device range, including process death, provider behavior, codecs, memory and UI behavior.

Only the first two are partly available here. No VCard Native build or runtime evidence exists. A README statement, artifact release, API floor or source-level Java compatibility must not be presented as end-to-end Android compatibility.

## 4. Architecture topics to compare, not decide here

Official Android guidance aligns with a Compose-first, unidirectional UI state model: UI emits events, state holders coordinate UI logic, repositories separate data access and observable state is collected lifecycle-aware. Candidate decomposition for evaluation is:

```text
Compose screens / approved navigation
              | user events and immutable screen state
              v
ViewModel or screen state holder
              | explicit commands / observable state
              v
Profile policy and projection boundary
       | aggregate repository       | platform handoff adapters
       v                            v
metadata + owned assets       picker / SAF / Sharesheet / FileProvider
```

This is a conceptual candidate, not an approved architecture diagram or class/module prescription. P0.5 must compare whether one app module with clear package boundaries is sufficient versus multiple modules; how saved state, transient draft state and one-shot outcomes are separated; where immutable QR/vCard export snapshots are created; and how N04/N05 Save, D01 dirty guard, S01 confirmation, S02 review, N06 restore progress and caller return are represented without leaking Android types into policy/data code.

Do not put profile values, full key material, images, archives, paths or serialization blobs into `SavedStateHandle`/saved-instance bundles. Treat process-restorable UI state as small navigation/editor context only; source image/document URIs are temporary grants, not durable identifiers. No automatic-save behavior can be inferred from ViewModel or repository guidance. The approved explicit-save flows govern.

### Navigation comparison questions

| Requirement | Navigation 2 | Navigation 3 | No framework / small custom state |
|---|---|---|---|
| Six fixed destinations, two sheets, one dialog | Established Compose navigation APIs may map directly; verify dialog/sheet ownership and Save guards. | Flexible back-stack state and Compose-first scenes/overlays; verify lifecycle, overlay and state restoration fit. | Lowest dependency surface but requires explicit back stack, restoration and predictive Back behavior. |
| Return to prior caller for Clarification B | Verify route/result semantics and process restoration. | Verify key/result/overlay semantics and entry state. | Must implement and test the same semantics explicitly. |
| Predictive Back/accessibility | Verify selected version and custom guard behavior. | Release history shows active changes to predictive Back/overlays; verify exact stable API behavior. | Significant custom responsibility. |
| API 31/toolchain fit | Verify resolved min/compile metadata. | Verify resolved min/compile metadata; current release-line compile requirements may move. | Fewer navigation artifacts, not zero Activity/Compose toolchain constraints. |

No preference is finalized here. The recommendation must be driven by P0.2 flows, API/toolchain fit and lifecycle correctness, not by framework novelty.

## 5. SDK and dependency feasibility checklist

Before finalizing P0.5-01 or any dependency decision, record for each direct and transitive Android artifact:

- exact group/artifact/version, source URL, release date, license and security advisories;
- declared `minSdk`, `compileSdk`/AGP/JDK/Kotlin requirements and Java bytecode/API requirements;
- any API-specific calls used by this app and their guards/fallbacks at API 31;
- R8/shrinking, core-library desugaring, duplicate classes/provider conflicts and manifest contributions;
- maintenance/release cadence and whether the selected version has a supported upgrade path;
- a later build-matrix and API-31 runtime evidence obligation.

The proposed minSdk 31 is not final until every selected API and maintained dependency has documented support at API 31 and unresolved cases are owner-reviewed. A compileSdk higher than 31 may be required to consume a maintained artifact; this is a build-tool fact to verify, not a reason to raise minSdk or change target behavior automatically. `compileSdk` permits compiling against APIs; `targetSdk` opts into platform behavior and policy; `minSdk` controls installation floor. They are separate decisions. No number for any is selected in this document.

Android 12 behavior changes also need compatibility review when choosing `targetSdk`, including exported-component declarations and pending-intent mutability rules where applicable. These are manifest/intent implementation concerns for later; no manifest is authorized now.

## 6. API-31 conclusion

**Documentary result:** Android 12 corresponds to API 31. Candidate Room 2.8.5 declares a min SDK below 31, and the identified native platform facilities such as SAF/FileProvider/AtomicFile have API availability below 31. This is partial evidence only.

**Unresolved:** the complete selected artifact graph; Compose/Kotlin/AGP/Gradle/JDK compatibility; Navigation choice/version; DataStore metadata; exact Core/Activity/ExifInterface versions; PGPainless/Bouncy Castle Android behavior; all used API calls/codec paths; app target SDK obligations; and actual behavior on Android 12/API 31. Therefore this research does not finalize `minSdk 31` and does not claim that every candidate is API-31-compatible.
