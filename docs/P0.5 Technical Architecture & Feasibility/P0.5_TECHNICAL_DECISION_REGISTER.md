## Owner-approved Milestone 1.11 protocol extension — 2026-11-01

The owner authorized the Step 2 design for Step 3 implementation: external checksummed durable intents for explicit unavailable-profile backup recovery and resumable confirmed deletion, preserving existing A2 and backup schemas. This is a persistence-protocol change affecting P0.5-04/05/06, not a dependency change or blanket closure of their historical feasibility obligations.

Approved safeguards: one coordinator/root lock; startup reconciliation before live-store initialization and staging cleanup; atomic same-filesystem rename plus file/directory sync and verification; no copy-and-delete replacement; explicit recovery confirmation; intact private recovery evidence with no automatic expiry; blocked malformed/contradictory intents; exact scoped deletion; no silent fallback/reset/resurrection; verified completion before success/onboarding. Deletion includes associated retained evidence and unissued owned staging, but excludes external backups, recipient contacts, unrelated app data, and protected issued share files. Secure physical erasure and downgrade safety are not claimed. Storage retained for recovery evidence cannot be sacrificed to make space. Future evidence-cleanup UI requires separate approval.

## 1. Status rules

- **APPROVED** in P0.5 means the planning baseline and research-only authorization; it does not mean these technical decisions are approved, except the partial owner dispositions of 2026-10-30 recorded in section 4.
- **PROPOSED** means a candidate direction under evaluation. Candidate versions are evidence snapshots, not pins.
- **PENDING** means owner review/approval of the individual technical decision and final architecture. Implementation remains prohibited until separately authorized.
- **FEASIBILITY UNRESOLVED** means evidence does not establish a safe/compatible capability. It must not be relabeled as supported or solved by silently weakening P0.1–P0.4.

Each decision must be finalized only with requirement traceability, researched alternatives, rationale, risks, primary-source evidence/access date, exact artifact/license/API metadata where applicable, residual runtime checks, and owner approval. Current register rows are **APPROVED** (P0.5-02), **CONDITIONALLY APPROVED** (P0.5-01, 03, 05, 08, 11, 12) or **PROPOSED — PENDING** (P0.5-04, 06, 07, 09, 10), as recorded by the owner on 2026-10-30. A conditional approval covers only the scope and conditions stated for it and passes no feasibility gate.

**Alternatives:** Later `minSdk` above API 31 only with evidence and owner approval; lower floor would contradict current owner selection and requires explicit revision. Target/compile values should be separately reasoned, not inferred from the min floor.

**Evidence:** Android maps Android 12 to API 31. Room 2.8.5 declares min SDK 23; Navigation 2.10.2 stable release metadata reports a below-31 floor; these partial facts do not certify every used code path. Compose, lifecycle, Navigation3, PGP and codec dependency graph remains unresolved.

### P0.5-02 — Layering and dependency direction

**Candidate direction:** A small native Android app with clear presentation, policy/projection, repository and Android-integration boundaries. Start by evaluating a single Gradle app module; add modules only if they materially improve ownership/testing/build constraints. Keep Android `Context`, `Uri`, Intent and Compose types out of deterministic profile projection/validation rules where practical.

**Alternatives:** Multi-module domain/data/platform structure; direct screen-to-storage calls; broad service-locator/DI framework. Compare operational complexity and test seams without creating abstraction for its own sake.

**Risk:** Over-modularizing one profile adds build/tooling burden; under-separating policy risks leaking hidden fields into exports or making restore partial.

**Approval:** APPROVED by the owner on 2026-10-30 as an architectural direction (see [P0.5_APPROVAL_RECORD.md](P0.5_APPROVAL_RECORD.md)). It creates no module, code or dependency, and adding modules or a DI framework later needs owner approval.

### P0.5-03 — UI state, navigation and lifecycle

**Alternatives:** Navigation 2, Navigation 3, or small custom state. Compare the exact six destinations, `S01`/`S02`, `D01`, Clarification B caller return, activity results, process recreation, predictive Back and overlay lifecycle. No separate Settings route or new dialog.

**Risk:** Current Navigation3 releases continue to evolve overlays/back behavior and may affect compile-SDK/AGP requirements. Use stable APIs only if they fit verified requirements; no default preference is recorded.

**Approval:** CONDITIONALLY APPROVED by the owner on 2026-10-30, limited to the state pattern and the rule that navigation state holds no payloads, subject to the exact conditions in section 4 of the [consolidated review](P0.5_CONSOLIDATED_OWNER_DECISION_REVIEW.md). The navigation framework (Navigation 2, Navigation 3 or custom) is not approved.

No further OpenPGP investigation cycle is authorized. The evidence that would be needed before final technical acceptance is listed in the consolidated review, section 5.2.

### P0.5-10 — Image canonicalization

**Binding contract:** JPEG/PNG/WebP still input only, <=20 MiB, side<=8,192, <=16,777,216 pixels; portrait<=1,024, cover<=2,048, retained<=8 MiB.
