# VCard Native — P0.5 State, Storage & Recovery

## Milestone 1.11 implementation authorization — 2026-11-01

**Later Step 4E authorization:** AppData schema 3 adds optional explicit name components and export preferences, retaining schema-1/2 readers. This is additive saved-data evolution, not another A2/operation-intent protocol change: immutable generations, checksums, pointers, shared locks, explicit recovery, retained evidence, durable deletion and backup container format remain unchanged. Recovery/restore carry all name fields and privacy; deletion scope includes them with the rest of the aggregate. Old APKs reject schema 3; no downgrade guarantee.

The owner approved the Step 2 recovery/deletion design and authorized Step 3 implementation. This later, bounded authorization supersedes the historical "not selected/not authorized" statements below only for the following protocol. It does not close P0.5 feasibility gates, Milestone 1.11, or authorize Milestone 1.12.

- Retain the existing A2 profile representation and schema-1/schema-2 backup compatibility. Add an external, strictly parsed, checksummed operation-intent coordinator under app-private `noBackupFilesDir`. This is explicitly a **persistence-protocol change**, despite unchanged A2 and backup data formats.
- Coordinate all managed repository operations, exports, and profile-bearing staging access under one process-local root lock. Reconcile intent before constructing/initializing the live A2 directory or cleaning disposable staging.
- Publish intent through a new record, file sync, atomic rename, containing-directory sync, and readback verification before destructive work. Same-filesystem atomic directory replacement must not be substituted with copy-and-delete. Directory-entry durability is a separate boundary from file-content sync.
- Unavailable data remains fail-closed. Backup validation and review are independent of its readability. Only explicit recovery confirmation authorizes building and verifying a separate complete A2 replacement, preserving the unavailable directory intact as private evidence, and installing the recorded candidate. Revalidate exact backup bytes and recovery context at confirmation.
- Resume only a valid, previously confirmed operation. Contradictory or malformed operational evidence blocks profile use and replacement; missing or corrupted files never imply deletion authorization. Obsolete path-level uncertainty can be cleared only after verified replacement.
- Recovery evidence is not an ordinary profile, predecessor, backup history, export source, or user-visible card. It cannot feed normal display, QR, vCard, sharing, or full-backup paths. Do not automatically expire it. It consumes internal storage; insufficient capacity must fail without sacrificing it. Future user-controlled evidence cleanup needs separate owner approval.
- Confirmed deletion includes active profile generations/assets, associated private recovery evidence, unissued app-owned profile-bearing staging, and applicable operation metadata after verified completion. It excludes external backups, recipients' contact records, unrelated app data, and issued share files within their existing protected lifetime.
- Before durable deletion intent, failure preserves the readable profile. After intent, block profile use and new-profile creation and resume idempotent deletion on retry/startup. Report pending status when storage prevents completion; expose onboarding only after verified target absence and required directory synchronization.
- Logical app-managed deletion is **not secure physical erasure**. No recipient-copy removal or downgrade safety is promised. Older APKs do not understand pending intents and must not be used to access a store during an operation.

See [Milestone 1.11 implementation evidence](../legacy/M1.11_RECOVERY_DELETION_EVIDENCE.md) for actual validation and explicit limitations. Simulated failures, process kills, emulator reboots, and hardware power loss are separate evidence categories.

This does not select a final persistence engine, storage representation or recoverable commit protocol. P0.4 manual full backup and restore remain unchanged and are the supported cross-device migration method. Implementing and verifying both exclusions, including relevant Android-version-specific behavior, remains a future technical obligation.
**Provisional owner recovery policy (2026-10-30):** fail closed for unreadable, corrupted, incomplete or invalid saved profile data. Do not silently reset, fall back from a corrupted committed generation, or expose invalid data as valid; preserve it for potential recovery and require explicit user-controlled recovery/replacement. A proven interrupted, uncommitted Save may continue from the last demonstrably committed generation; this is distinct from rollback. Detection, commit classification, recovery mechanics, preservation limits and P0.2 UI/change-control questions remain open.
**Provisional predecessor-retention policy (2026-10-30):** retain exactly one previously committed predecessor alongside the active generation during normal operation. This is not an unconditional maximum during interrupted operations, corruption investigation, or protected artifact lifetimes. Cleanup must wait for an established new commit, reconciled references and identified protections; never delete active/predecessor, pinned, otherwise protected, corrupted or fail-closed recovery-evidence data.
**Provisional low-storage policy (2026-10-30):** if Save or Restore cannot safely complete for lack of storage, fail without replacing or partially replacing the existing committed profile. Do not sacrifice active/predecessor generations, pinned export/share artifacts or protected recovery evidence to make space. A failed pre-commit operation leaves the last demonstrably committed profile authoritative; report success only after the required durable commit is established. Staging cleanup is allowed only when demonstrably safe and unprotected. Exact capacity thresholds and step-specific behavior remain open.
**Provisional capacity-estimation and cleanup policy (2026-10-30):** before Save or Restore, estimate complete new-generation needs, all necessary temporary writes, protected existing generations/assets, active export/share pins, protected recovery evidence and a safety reserve. Estimates are advisory, not guarantees; no numerical budget/reserve/threshold is selected. Cleanup only after successful commit where applicable, complete reconciliation of protected references, and proof each candidate is unreferenced and unprotected. Cleanup is idempotent, interruptible and repeatable after process death; all protected data remains preserved.

## 1. Decision summary

The product has one saved profile aggregate, optional owned images and a public-only OpenPGP certificate. N04 edits drafts; explicit Save commits the entire profile; S02 validates and explicitly replaces the entire saved aggregate. Hidden fields and supported historical keys remain in full backups. A restore failure must leave the previous complete profile and its owned assets available.

### Two-stage integrity validation

The owner-approved provisional policy separates three statuses. **Metadata-valid** means startup Stage 1 has validated active-reference integrity/selection (subject to the unapproved pointer protocol), manifest structure and supported schema, required profile metadata, and referenced asset records including expected sizes, digests and ownership/reference invariants. It does not prove the bytes of referenced assets are intact. An individual asset is **asset-verified** only after Stage 2 verifies its actual size and SHA-256 against the committed manifest and applies any additional image/OpenPGP validation required by P0.4. The profile is **fully verified** only after every referenced asset passes Stage 2; never label a metadata-valid profile fully verified while any referenced bytes remain unchecked.

Before any asset is consumed, displayed, exported, shared or otherwise used, Stage 2 must pass. Unverified bytes must not be exposed through UI, QR, vCard, Sharesheet, export or manual backup. A Stage 2 failure follows the provisional fail-closed policy: do not reset, use an older committed generation or treat the asset/profile as valid. Verification timing, caching and invalidation, failure/retry behavior, access-path coverage and startup/per-use performance remain open implementation questions; no verification or implementation is authorized here.

A database transaction, DataStore update, or Android `AtomicFile` operation alone does not establish an atomic transaction across profile metadata and separate image/key files. The owner provisionally prefers immutable saved generations/manifests and write-once app-private blobs selected through a durable active-generation reference. The exact commit boundary and protocol that make profile, appearance, visibility, metadata and referenced asset bytes switch together after process death or device restart remain undecided and unproven; a recoverable journal and other storage representations remain alternatives. No pointer mechanism or durability claim is approved. Any future protocol must be validated by interruption/fault testing before it can support a safety claim.

## 2. Binding contracts

The approved requirements are in [P0.4 data model](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_DATA_MODEL_SPECIFICATION_DRAFT.md), [P0.4 backup/restore specification](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_BACKUP_RESTORE_SPECIFICATION.md), [P0.4 public-key and image contracts](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_PUBLIC_KEY_AND_IMAGE_CONTRACTS.md), and the [P0.4 approval record](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_APPROVAL_RECORD.md).

- Persist one complete saved profile: exact 15-slot inventory, mandatory fullName, independent visibility settings, appearance, metadata, and typed app-owned asset references. Optional contact fields default private; fullName visibility remains locked true.
- Draft edits are not saved state. Explicit N04 Save is the commit action. Cancel/back/discard follows the approved guard; do not introduce autosave or promise durable in-progress drafts.
- A valid backup is STORE-only ZIP32, 2-5 allowlisted entries, maximum 24 MiB archive / 20 MiB actual entry bytes, with strict UTF-8 JSON, exact schemas, per-entry SHA-256, canonical asset checks and semantic key validation. Complete backups include hidden values and supported owned assets/key bytes.
- S02 is a whole-profile replacement. Validate the entire candidate before review/commit. Cancel, invalid input, unsupported key formats, and any pre-commit failure preserve the old saved profile and assets unchanged.
- Supported data-valid expired or verifiably revoked public certificates are retained; their active actions are unavailable. Unsupported historical key material rejects the whole candidate; no partial restore, key deletion, conversion, stripping or substitution.
- Successful replacement advances the saved generation/revision and invalidates prior export snapshots. An external write/intent return is not proof of delivery.
- Resource limits, metadata privacy and no-content/key/path diagnostic logging remain binding. No user-visible recovery history, undo, cloud sync, encryption option or alternate import route is added.

## 3. Aggregate and asset invariants

Represent saved state conceptually as one immutable generation:

```text
SavedGeneration = {
  schemaVersion,
  profile[15 slots + visibility + typed asset refs],
  appearance,
  metadata,
  owned asset bytes and validated asset descriptors
}
```

This is a conceptual transaction boundary, not a chosen Kotlin type or serialized format. Every saved-state read must resolve to one generation that passes Stage 1; each asset is withheld until it passes Stage 2. “Metadata-valid” is not synonymous with “fully verified.” The following must always hold:

1. Exactly one active generation is identified, or a verified first-run state is explicitly empty. Corrupt or ambiguous saved state is preserved for potential recovery, never treated as empty, silently replaced with a predecessor, or exposed as valid. There is no state where profile metadata points at a missing or partially written image/key.
2. A draft can reference temporary draft-owned image bytes, but a failed/cancelled save must not overwrite saved-generation bytes. The exact persistence/lifetime of a draft across process death is not promised by P0.2/P0.4.
3. Asset metadata is derived/checked against exact retained bytes: logical assetId, allowlisted internal location, actual MIME/codec, byteLength, dimensions or key version/algorithm/fingerprint, and SHA-256. A digest is byte-integrity metadata, not identity trust.
4. A generation becomes active only after every required metadata and asset byte is durably prepared and validated. Old-generation bytes remain available until activation/recovery proves the new generation is the active complete state.
5. Retain the active generation and exactly one previously committed predecessor during normal operation. This target is not a hard maximum during interruption, corruption investigation or protected artifact lifetimes. Cleanup is reachability-based, idempotent, interruptible and repeatable after process death. Where cleanup follows a successful operation, wait until commit is established, all protected references are reconciled, and each deletion candidate is proven unreferenced/unprotected. Never delete active/predecessor data, assets or artifacts pinned by active export/sharing operations, S02 candidates still under review, corrupted data, or fail-closed recovery evidence.
6. Restored assets are copied byte-for-byte after validation. Restore never re-encodes JPEG/PNG or rewrites OpenPGP packets; the stored digest continues to identify the restored bytes.

Profile ID, asset IDs, backup timestamps and ZIP-entry paths are untrusted input. Validate shape and relationships before using any value to construct a filesystem path. Use generated internal names/IDs rather than concatenating an archive basename into a destination path.

## 4. Candidate storage patterns

### A. Immutable generation plus one active reference

Stage each new saved profile as a complete immutable generation in app-private storage. Validate/sync its metadata and assets, then update one small active-generation reference as the commit point. Keep the prior generation until reference activation is durable and restart recovery can identify one complete winner.

**Potential strengths:** natural old-or-new visibility; immutable snapshots simplify QR/vCard export consistency; assets can be garbage-collected by generation reachability; restore validation/staging is isolated from live state.

**Questions requiring evidence:** atomicity and durability of reference replacement on supported Android filesystems; directory-entry durability; API-level behavior; concurrent writers; cleanup after process death/low storage; staging-space headroom; backup/restore of large generation assets; and how corrupted/missing active references recover without guessing.

### B. Metadata transaction plus coordinated asset journal

Store metadata transactionally (candidate Room or another store), write new immutable asset files to staging, and use a durable operation journal/commit marker to recover a cross-resource switch. Before startup exposes state, reconcile incomplete operations and verify references.

**Potential strengths:** database constraints/queries may suit profile metadata; explicit journal phases can describe crash recovery.

**Questions requiring evidence:** database transactions do not include arbitrary files; exact ordering and durability of file writes, database updates and journal markers; idempotent restart handling; stale journal cleanup; and whether every crash point yields old or complete new state.

### C. Single serialized aggregate file

Serialize the complete profile and all asset bytes into one app-private aggregate file and replace it through a single-file atomic-write mechanism.

**Potential strengths:** a single replacement object is easier to reason about than independent metadata and asset commits.

**Questions requiring evidence:** bounded-memory streaming under 20 MiB actual asset data, migration/versioning, random-access asset decode/export, transaction cost, temporary disk amplification, corrupt aggregate recovery, and whether a whole-file replacement satisfies performance constraints.

The immutable-generation family is the owner-accepted provisional preferred direction only; these patterns do not constitute a selected final architecture or commit protocol. A hybrid that writes some state in Room/DataStore and some into files still needs a defined aggregate commit boundary and restart protocol.

A process-local mutex does not automatically cover another process, OS recovery, external provider writes or directory durability. The exact coordination mechanism is unresolved.

## 6. Restore validation and commit phases

The approved order is conceptually:

```text
select source
  -> bounded stream into app-private staging
  -> validate ZIP framing, exact entries, actual sizes and CRC
  -> parse exact UTF-8 JSON schema; reject duplicates/unknowns/invalid values
  -> verify hashes and every asset-reference relationship
  -> validate image bytes/policy and public-only OpenPGP structure/cryptography
  -> create immutable validated candidate generation
  -> show S02 summary from that exact candidate
  -> recheck candidate identity and whether saved state changed
  -> require explicit replacement confirmation
  -> commit one complete generation
  -> verify active generation and publish success
  -> only then reclaim now-unreachable old/staging data
```

Any validation error before S02, user cancellation/dismissal, or failure before commit leaves saved state untouched. If saved state changes while S02 is open, the summary and replacement target must be refreshed and confirmed again. No commit may use stale candidate bytes or a stale export/profile snapshot. After commit begins, N06's approved progress state may prevent dismissal; background cancellation and process death still require recoverable behavior.

Backup creation has a related consistency requirement: capture one immutable saved generation, then serialize its data and exact asset bytes. Do not mix profile revision N with image/key bytes from N+1. A backup may complete from the captured generation after later saves, but its timestamp must truthfully describe the capture. Exported artifacts should likewise be derived from one immutable snapshot whose included-field projection and revision are stable through confirmation and output start.

## 7. Crash/recovery obligations

The implementation protocol must define and later test each boundary below. This list is a design obligation, not a claim that the current platform primitive has already met it.

| Interruption point | Required post-restart invariant |
|---|---|
| During source copy/archive parsing | Old saved state remains active; incomplete source staging is rejected/reclaimable. |
| During candidate metadata or asset staging | Old saved state remains active; incomplete candidate is never visible. |
| After candidate is complete but before S02 confirmation | Old saved state remains active; candidate may be safely discarded or revalidated, but no implicit replacement. |
| While S02 is visible / saved state changes | No stale candidate silently replaces the newer state; review must be revalidated and reconfirmed. |
| During active-reference or journal commit | Startup deterministically recovers exactly the complete old or complete new generation; never a hybrid, dangling asset or ambiguous guessed winner. |
| After commit but before success UI | Startup recognizes the committed generation; do not reapply a second time or report false failure/success. |
| During old-generation/staging cleanup | Active/new generation remains intact; cleanup can resume idempotently. |
| Low storage, permission/provider loss or cancellation | Save/Restore fails without replacing the committed profile; do not sacrifice active/predecessor/pinned/recovery-protected data. Explain the actual outcome and report success only after durable commit is established. |

Under the provisional fail-closed policy, if startup cannot establish whether a complete generation was durably committed, it must not guess or expose a generation as valid. Recovery to the last demonstrably committed generation is allowed only when evidence establishes that the attempted Save was interrupted before commit; it is not predecessor fallback after corruption of committed data.

An operation journal must itself have a defined durable transition protocol, bounded recovery work and idempotent replay. Merely adding a journal does not prove correctness. Crash consistency of filesystem/database ordering, flush/sync semantics and directory-entry durability must be supported by authoritative platform evidence and fault-injection tests on API 31 and the primary Pixel device.

## 8. Boundedness, privacy and cleanup

Enforce the approved archive/input bounds on streamed actual bytes, not just ZIP headers. Count entries and packets before expensive allocation. Bound JSON nesting, decoded image work, OpenPGP packet counts and verification work. Avoid loading entire archive entries or decoded image dimensions into memory without an explicit allocation budget. Android ZIP traversal guidance warns against trusting entry paths; use a fixed basename allowlist and generated internal destinations.

App-private staging contains potentially sensitive names, contact details, public-key user IDs and images. Do not log paths, profile contents, key bytes/fingerprints or backup JSON. Rejected, cancelled and abandoned candidates should be reclaimed safely; defer deletion of assets reachable by live or in-flight snapshots. No external `content://` grant is a persistent storage reference. Owner policy excludes saved profile data and profile-bearing operational artifacts from both Android automatic cloud backup and Android-managed device-to-device transfer. Implement and verify the appropriate exclusions separately for relevant Android versions; they are not technically enforced by this documentation. Manual full backup/restore follows P0.4 unchanged and remains the supported migration method.
