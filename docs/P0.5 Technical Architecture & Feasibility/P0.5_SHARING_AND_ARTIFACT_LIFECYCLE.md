# VCard Native — P0.5 Sharing & Artifact Lifecycle

**Status: PROPOSED — FEASIBILITY DOCUMENTATION; NO LIBRARY OR PLATFORM INTEGRATION SELECTED**  
**Date:** 2026-10-30  
**Decision coverage:** P0.5-07, P0.5-08, P0.5-11  
**Owner boundary:** P0.2 navigation/flows and approved P0.4 vCard, QR, privacy and artifact contracts are binding. This is documentary evaluation only; no export implementation, manifest, provider, SDK or dependency has been created/configured.

## 1. Scope and conclusion

This document evaluates the native path from one saved-state snapshot to four distinct artifacts: an on-screen offline contact QR, an optional configured hosted-URL QR, a contact-only `.vcf`, and an exported QR PNG. It also examines incoming backup/image/key selection and outbound native handoffs. The decisive constraints are privacy-filtered projection, action-specific confirmation, snapshot invalidation, bounded encoding/rendering and correct ownership/grant lifetimes.

ZXing 3.5.4 exposes QR version, correction, character-set/ECI and raw matrix capabilities in its upstream source; this is a plausible encoder candidate, not an Android/API-31 support claim or dependency selection. ez-vcard 0.12.2 is a plausible vCard-library candidate, but its release/license metadata does not establish the exact VCard Native profile or Android behavior. Native Android Storage Access Framework (SAF), Activity Result contracts, FileProvider and Sharesheet APIs are platform candidates; exact API/library versions and device/recipient behavior remain unverified.

## 2. Binding projection and confirmation rules

The approved inputs are [P0.4 vCard & Contact Export](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_VCARD_AND_CONTACT_EXPORT.md), [P0.4 QR Payload & Sharing](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_QR_PAYLOAD_AND_SHARING.md), [P0.4 privacy/validation](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_FIELD_VALIDATION_AND_PRIVACY.md), [P0.2 flows](../P0.2%20UX%20Flow%20%26%20Navigation/P0.2_USER_FLOWS.md), and the [P0.3 screen specifications](../P0.3%20Visual%20UI-UX%20Design/P0.3_SCREEN_DESIGN_SPECIFICATIONS.md).

- Contact QR is default, offline, and appears immediately from a valid saved/export-enabled contact projection. It uses the complete approved provisional vCard 3.0 payload, not a smaller fallback subset. Show the included-data summary. Voluntary S01 before QR presentation is allowed but does not block initial display.
- `.vcf` creation/sharing and contact QR image save/share require S01 plus explicit confirmation for the specific action **before** creating the file/image or handing it to Android. Confirmation binds to the displayed snapshot and action. A changed saved generation/visibility set invalidates it and requires updated review/confirmation.
- Hosted-URL QR contains only the configured normalized HTTPS URI, no contact payload, tracking suffix or hosted-content fetch. It is separate from the local offline contact QR. No URL does not trigger a fallback.
- Contact projection emits fullName as `FN` and the approved empty structured `N:;;;;`; it does not invent name parts. Optional text/URI values are included only when present, valid and explicitly export-enabled. Images and OpenPGP keys never enter the contact QR or `.vcf`; hostedProfileUrl and appearance are excluded from contact projection.
- Appearance-only changes may conservatively invalidate derived artifacts. Restore creates a new generation and invalidates prior previews/artifacts. Unsaved drafts never export. Existing contact/website/file actions are not expanded into new routes.

## 3. vCard serialization feasibility

### Approved target profile

The owner-approved provisional target is vCard 3.0 for both contact QR and `.vcf`, conditioned on recipient compatibility. vCard 4.0 remains an evaluation alternative; changing to it requires explicit owner approval before implementation. This is a conservative compatibility hypothesis, not a measured superiority claim. Current Pixel Contacts import fidelity, other Android apps and QR scanners are unknown.

Approved 3.0 projection/mapping:

| Input | vCard property | Policy |
|---|---|---|
| `fullName` | `FN` | Required; full identity string, no parsing into invented parts |
| No name-part inputs exist | `N:;;;;` | Five empty structured components; retain as a known recipient risk |
| `organization` | `ORG` | One component; escape text, no invented department |
| `professionalTitle` | `TITLE` | Only if valid and export-enabled |
| `phone` | `TEL` | Canonical number; no guessed HOME/WORK/CELL type |
| `email` | `EMAIL;TYPE=INTERNET` | Validated single mailbox |
| `website`, eligible professional links | Repeated `URL` | Fixed approved category order; no private hosted profile URI |
| Eligible location and/or biography | One `NOTE` | Independently filtered labeled lines in approved order |
| Framing | `BEGIN:VCARD`, `VERSION:3.0`, `END:VCARD` | UTF-8 bytes, CRLF delimiters and final CRLF |

Use the exact P0.4 mapping and exclusions; do not serialize the profile object wholesale. TEXT escaping and URI serialization are different: escape backslash/comma/semicolon/newline for TEXT, while validated absolute URIs are serialized as URI values, not TEXT-escaped. Fold only at UTF-8 character boundaries and preserve escape/percent triplets. The approved profile uses a maximum 75-octet physical line (excluding CRLF), including the continuation space in the continuation-line budget. The complete `.vcf` output has a 64 KiB resource cap. Over-limit/invalid output fails; never truncate, silently omit a selected supported field or switch format.

### Candidate serializer comparison

| Candidate | Evidence | Unresolved fit |
|---|---|---|
| ez-vcard 0.12.2 | [Maven Central metadata](https://repo1.maven.org/maven2/com/googlecode/ez-vcard/ez-vcard/maven-metadata.xml) lists 0.12.2; project license is BSD 3-Clause. | Verify maintained release history, Android/API-31 dependency/runtime compatibility, 3.0 escape/fold/unfold behavior, URI handling, control-character injection defenses, output bounds and ability to preserve exact approved property order. It may add flexibility/features the app must deliberately constrain. |

No dependency has been selected. Whether a maintained library can be safely constrained to the exact approved field projection and byte policy is open. vCard 4.0's FN-only/N-optional semantics are a useful paired test alternative, not a fallback selector.

## 4. QR encoding and physical rendering

The approved QR contract is ordinary QR Model 2, correction M, smallest fitting version 1-40, byte mode, ASCII without an ECI marker and non-ASCII UTF-8 with ECI 26. The application rejects contact payloads above 4,096 actual serialized UTF-8 bytes before encode, but this is a resource bound, not a promise that all 4,096 bytes fit. The chosen encoder must still test actual capacity including mode, ECI, correction and terminator overhead. No truncation, structured append, compression, correction downgrade or automatic web-mode substitution is allowed.

ZXing source evidence for 3.5.4:

- [QR `Encoder`](https://raw.githubusercontent.com/zxing/zxing/zxing-3.5.4/core/src/main/java/com/google/zxing/qrcode/encoder/Encoder.java) accepts `CHARACTER_SET`, `ERROR_CORRECTION`, `QR_VERSION`, emits an ECI segment for a specified byte-mode charset when the charset maps to an ECI assignment, and returns a `QRCode` with its raw module matrix.
- [QR `QRCodeWriter`](https://raw.githubusercontent.com/zxing/zxing/zxing-3.5.4/core/src/main/java/com/google/zxing/qrcode/QRCodeWriter.java) exposes a rendering path with a configurable margin and integer scaling. It renders to a `BitMatrix`; the public `Encoder` matrix path can be evaluated when VCard Native needs exact module-level control.
- Maven Central lists `com.google.zxing:core:3.5.4`; ZXing is Apache-2.0. Core artifact metadata/source does not establish Android API-31 runtime support, actual ECI scanner compatibility, or target-device performance.

The approved rendering rules remain binding: intact four-module quiet zone; an additional 16dp outer white pad; square P0.3 panel; black modules on white; no smoothing/overlay/tint. Display modules must be integer-sized, at least 2dp and at least 3 physical pixels, centered. Prefer 280dp panel and use the existing 320dp cap only if required and space allows. Determine actual physical pixels/dp and measured panel bounds; do not assume the preferred panel is available. If no version fits geometry while meeting the module floor, show the approved inline failure/edit/.vcf path.

Export PNG is lossless `image/png`, rendered at 8 physical pixels per module and must preserve the quiet zone, with no identity text or private metadata. For version $v$, the symbol is $(17+4v)$ modules per side and the quiet-zone-inclusive bitmap side is $(25+4v)\times 8$ pixels; version 40 would therefore be 1,480 pixels. That is a geometry calculation, not scan evidence. Export image creation remains gated by S01 for contact mode. The contact QR already displayed onscreen is not permission to export it.

P0.4 reports DENSO WAVE's version/correction guidance and a manufacturer-source corroboration for ECI 26; the complete ISO/IEC 18004:2024 standard and authoritative ECI registry were not inspected. Therefore, P0.5 must verify selected encoder details and P0.6 must test actual scanner handling of UTF-8/ECI and real physical conditions. No QR library is selected and no QR was generated or scanned.

## 5. Snapshot, confirmation and invalidation model

A candidate lifecycle is:

```text
saved generation
  -> privacy-filtered immutable projection (contact vCard bytes OR hosted HTTPS URI)
  -> validate bytes/resource limits and derive renderable QR (if applicable)
  -> display contact QR + inclusion summary (no blocking S01)
  -> explicit export action
  -> action-specific S01 (contact .vcf / contact-image save / contact-image share)
  -> revalidate generation + action + projection digest
  -> generate immutable output bytes
  -> local SAF write OR temporary content-URI read grant to Sharesheet
  -> truthful outcome / cleanup when no receiver needs the bytes
```

This is a proposed lifecycle, not selected state-holder or locking implementation. Bind confirmation to saved generation/revision, contact-projection contract version, mode and action; keep the exact reviewed serialized bytes immutable through output creation. If relevant saved data changes before output starts, invalidate the preview, refresh it and require new confirmation. Serialize restore/Save against capture/start, or detect revision change and fail stale. Do not reread mutable fields after confirmation and accidentally create a different file. When OS handoff outcome is unknown, reconcile before offering another handoff; no automatic duplicate intent/write after restart.

A successful local profile save or restore invalidates derived QR and pending confirmations. External copies cannot be recalled by local invalidation. Returning from a picker/Sharesheet is not evidence that the file was saved, contact imported or message delivered. Report only observable outcomes: complete URI creation, successful local write/close where observable, or “opened chooser”/“handed off” rather than recipient success.

## 6. Native file and URI integration candidates

| Workflow | Platform candidate | Constraints / unresolved behavior |
|---|---|---|
| Choose a backup/image/key input | SAF `ACTION_OPEN_DOCUMENT`/`ACTION_GET_CONTENT` via an Activity Result contract; Photo Picker for image selection | Keep access temporary; copy and validate bytes into app-private storage while permission is available. Cancellation leaves saved state unchanged. Do not assume URI path, filename, declared MIME or remote-provider availability is trustworthy. |
| Save backup, `.vcf` or QR PNG | SAF `ACTION_CREATE_DOCUMENT` / Activity Result `CreateDocument` contract | User chooses destination. The provider may be local/offline or cloud/online; cancellation/failure can leave partial output. Write/close success needs a truthful result. Avoid silent overwrite; names remain generic and non-identifying. |
| Share private-cache `.vcf` / QR PNG | A dedicated AndroidX `FileProvider` subclass and native Sharesheet with `content://` URI and read-only temporary grant | Evaluate subclassing explicitly: Android's reference says using the library class directly is not reliable and can crash on some devices. Use `android:exported=false`, `grantUriPermissions=true`, narrow XML path under a dedicated app-private share-cache subdirectory, `FLAG_GRANT_READ_URI_PERMISSION`, correct MIME type and safe display name. Never use `file://`, `<root-path>`, a broad `.`/`/` path, or external storage for sensitive PII. |
| Add recipient contact | Existing P0.2 native handoff intent/destination | The receiving contacts app controls import and result. Do not add a direct Contacts Provider write/permission or claim an import succeeded merely because the activity returned. |

Android's [FileProvider reference](https://developer.android.com/reference/androidx/core/content/FileProvider) says grants in an intent are temporary and tied to the receiving activity/service lifetime; Android's [secure sharing guide](https://developer.android.com/training/secure-file-sharing/share-file) documents read grants and content URIs. The [FileProvider security guidance](https://developer.android.com/privacy-and-security/risks/file-providers) requires narrow paths/minimum grants and warns against broad roots. P0.5 must select the exact Core/Activity dependency and verify behavior on API 31 and the Pixel; citations do not establish receiver compatibility.

The app's approved 24-hour unused-cache retention is a maximum cleanup target, not a timer that can invalidate an active recipient grant. Keep bytes until no active handoff needs them; after process death or unknown grant state, use a conservative cleanup/reconciliation rule. Invalidation blocks new app reuse but does not revoke a file already saved/shared externally. No public external cache, transfer history or new file-management screen is introduced.

## 7. Cancellation, errors and boundaries

| Event | Required behavior |
|---|---|
| QR no-fit / encoder error / geometry no-fit | No stale active QR; explain the specific limitation and offer approved N04 edit/.vcf route. Never silently omit included fields or switch to hosted URL. |
| S01 dismissed / caller changes snapshot | Do not create the gated `.vcf` or contact QR image; refresh and reconfirm if the saved generation changes. Initial contact QR display remains immediate. |
| SAF picker cancelled | No profile mutation and no success claim. Return to the invoking screen/caller. |
| Provider permission/read failure | Preserve previous asset/state, explain, allow deliberate re-selection. Never treat a URI as a durable owned asset. |
| SAF output failure/full storage/cancellation | Report unknown/failed/incomplete truthfully; best-effort remove partial data when supported; do not claim a valid artifact. |
| Sharesheet dismissed / return from native contact app | Return to caller and state only that handoff was offered; do not claim delivery, import or successful saving. |
| Stale generation / process interruption | Invalidate and reconcile before retry; no automatic duplicate external handoff/write. |
| Cache cleanup | Preserve bytes needed by active receivers; remove only safely unreachable unused app-owned artifacts. |

No profile field, key bytes/fingerprint, exported payload, source/destination path or raw provider exception is logged. User-facing diagnostics remain bounded and actionable.

## 9. P0.6 verification obligations

Later authorized verification must round-trip each vCard field/visibility combination and compare 3.0/4.0 using the same fixtures; inspect serialized bytes for excluded fields; exercise Unicode/ECI 26, escaping, folded lines, empty N, output cap and hostile newline input. Test QR fit/geometry at API 31 and actual supported densities, scan/import on the Pixel and a second device, low brightness/glare/angle/distance, PNG quiet zone and exact pixels. Exercise stale S01, saved-state changes, restore invalidation, provider denial/cancellation/full storage, active URI grants versus cache cleanup, process death, external handler absence and truthful no-delivery results. Record device/app/OS and provider versions. These checks are obligations, not results; none has been run.
