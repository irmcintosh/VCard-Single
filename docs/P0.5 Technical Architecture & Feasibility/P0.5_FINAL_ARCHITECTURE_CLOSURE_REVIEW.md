## 2. Consolidated Recommendation

**Recommended and conditionally endorsed target for future verification:** one app-private file-backed saved aggregate using immutable generation manifests over shared immutable, write-once asset blobs (A2), selected by one durable active-generation reference. The owner endorsed this consolidated direction conditionally on 2026-10-30; it is not final architecture approval. Keep one previously committed predecessor in normal operation, with additional generations/artifacts retained while interruption, corruption investigation, active operations or recovery evidence require protection. Continue the approved two-stage integrity, fail-closed corruption, advisory capacity-estimation, fail-without-replacement, and reference-safe cleanup policies.

This is the single recommended target. Do not split profile metadata into a separate Room/DataStore commit plus a file journal, and do not recommend a monolithic serialized aggregate as a parallel fallback. Those remain comparison alternatives in the proposal, not co-equal closure recommendations.

**Preferred pointer candidate for owner consideration:** two fixed-size checksummed A/B pointer slots, each carrying a monotonically increasing sequence and the immutable manifest identity/hash plus logical generation/revision and operation identity. Stage and verify new blobs, publish and verify the immutable manifest, then write/sync the inactive pointer slot last. This is the preferred candidate because it avoids replacing one active pointer pathname and makes a torn record detectable in principle. It is not approved, proven durable, or sufficient by itself to determine recovery precedence. `AtomicFile`, `fsync`, directory-entry behavior, slot checksums, and sequence selection have not been demonstrated as an aggregate power-loss commit protocol.

This recommendation does not select Room, DataStore, a final serialization format, a final representation, or a production commit protocol. It does not approve any P0.2 UI change, automatic fallback, storage threshold, Android configuration, dependency, or implementation.

## 3. Recommended Storage and Recovery Rules

### Representation and commit boundary

- Treat the profile, visibility, appearance, asset records and referenced bytes as one logical saved generation. Each generation manifest is immutable; image/key blobs are immutable write-once app-private bytes addressed by generated internal IDs. Reuse an unchanged blob only while all referring roots remain protected.
- Keep P0.4 `generationId`/`stateRevision` separate from any storage-generation or pointer sequence. Backups continue to use the exact approved P0.4 schema/ZIP32 contract.
- For a Save or Restore, stage all new bytes and the candidate manifest without exposing them as saved state. Do not alter the active committed generation. The pointer change is the candidate commit boundary, not a proven durable commit.
- Candidate ordering: preflight an advisory whole-operation capacity estimate; write/hash/sync new blobs; publish and verify the immutable manifest; reconcile the complete candidate and protected roots; write/sync the inactive pointer slot last; publish success only after the selected commit protocol establishes the new active generation. Exact file/directory sync semantics and cross-restart durability remain unverified.

### Pointer selection and recovery precedence

1. Recommend A/B slots with a strict format/version check, checksum, monotonic sequence, manifest ID/hash, logical generation/revision, and operation identity. Require exactly one highest sequence when both records are valid; tied/conflicting records are ambiguous.
2. A pointer is usable only if the selected manifest passes Stage 1 and all required references/ownership invariants pass. Stage 1 metadata validity does not prove all asset bytes.
3. If a slot is invalid, records conflict, a higher commit may be hidden, or a referenced generation is incomplete/corrupt, fail closed. Preserve the slots, generation data and recovery evidence. Do not choose an older committed generation merely because it is readable.
4. Recovery to the last demonstrably committed generation is permissible only when evidence establishes that a Save was interrupted before its commit began/was established. If the commit boundary is ambiguous, do not claim success or expose an assumed winner. The exact proof/precedence mechanism is an owner decision and later technical obligation.
5. Corruption of an already committed generation never triggers automatic predecessor activation. Preserve corrupt data for potential recovery and require explicit, user-controlled recovery/replacement using the approved manual full-backup/restore workflow.

### Integrity verification

- **Stage 1 at startup:** validate active-reference integrity/selection under the future approved pointer protocol; manifest structure/schema; required profile metadata; asset records, expected sizes/digests and ownership/reference invariants. Label only as metadata-valid. Do not claim a profile fully verified while any referenced asset bytes remain unchecked.
- **Stage 2 before asset use:** verify actual size and SHA-256 against the committed manifest and perform applicable P0.4 image/OpenPGP validation before consuming, displaying, exporting, sharing, or using the bytes in a QR, vCard, Sharesheet, or backup. No unchecked bytes are exposed.
- A profile is fully verified only after every referenced asset passes Stage 2. The previously approved fail-closed behavior applies to Stage 2 failures. Verification cache/timing/invalidation and access-path coverage remain unselected.

### Capacity, failure and cleanup

- Before Save/Restore, estimate the complete candidate generation, all temporary/source writes, filesystem overhead, active and predecessor generations/assets, active export/share pins, protected recovery evidence, and a safety reserve. Estimates are advisory, not write-success or durability guarantees. No numeric budget, reserve, threshold, or hard storage limit is recommended without later evidence and owner review.
- Insufficient capacity or I/O failure at any step fails without replacing or partially replacing the committed profile. Do not sacrifice active/predecessor generations, pinned artifacts or protected recovery evidence to make space. Report success only after the required durable commit is established. Preserve ambiguous temporary data if its safety for deletion is not proven.
- Normal operation retains exactly one previously committed predecessor, in addition to the active generation. This is not an unconditional maximum during interrupted operations, corruption investigation, active export/share lifetime, or protected recovery-evidence retention.
- Cleanup is allowed only after applicable commit establishment, complete reconciliation of protected references/ownership, and proof that each deletion candidate is unreferenced and unprotected. Include active/predecessor manifests and blobs, pins, generated export/share artifacts, staging ownership and corruption/recovery evidence in reachability analysis. Cleanup is idempotent, interruptible, repeatable after process death, and never silently deletes corrupted data or recovery evidence.
- Storage budgets, reserve size/filesystem overhead, failure behavior at each pointer/write/sync step, cleanup scheduling/retry, pin-release conditions, preservation limits and verification evidence remain open.

### P0.2 implications and migration policy

Use existing approved N03 “saved profile unavailable,” C13 inline feedback, N04 creation/editor and N04-to-N06 restore entry points only if they can clearly communicate unreadable/corrupt saved data and offer explicit recovery without presenting stale data or silently creating an empty profile. N06 retains its existing progress/error behavior for low-storage failures. If those approved surfaces cannot represent the condition or make “no replacement occurred” clear, P0.2 change control and explicit owner approval are required before any UI change. No new route, sheet, dialog, or navigation behavior is approved here.

Android automatic cloud backup and Android-managed device-to-device transfer remain separately excluded for all locally saved profile data and profile-bearing operational artifacts. Their version-specific configuration and enforcement are not implemented or verified. The approved P0.4 manual full-backup and restore workflow remains the supported cross-device migration method.
