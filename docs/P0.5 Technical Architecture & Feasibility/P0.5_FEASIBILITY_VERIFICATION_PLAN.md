## 2. Evidence Method

For each later authorized activity, retain the requirement reference, exact test identifier, procedure revision, host/emulator/physical-device classification, OS/API, device model, toolchain/dependency versions, fixture identity/hash, expected and actual output, logs/artifacts, pass/fail/block rationale, reviewer and owner disposition. Redact personal data, keys, payloads, paths, URIs and secrets. Never use production personal data as a fixture.

Separate evidence classes:

- **Desktop/static:** source/API/metadata inspection, pure bounded fixture processing, dependency/license inventory, serialization calculations. Does not prove Android API behavior.
- **Emulator:** Android behavior on an explicitly recorded system image/API. Does not prove Pixel hardware, recipient behavior or power-loss durability.
- **Physical device:** owner-approved Pixel and any specifically approved second device/provider/scanner. Record model, OS/build, app version and external app versions. Android 17 does not substitute for API 31.

For every gate, classify evidence as **NOT EXECUTED**, **PASS**, **FAIL**, or **BLOCKED**. Use **PASS** only when all stated criteria for that test are met. A failed candidate is not permission to relax P0.1–P0.4; return the decision to the owner. Feasibility and architecture approval remain distinct.

## 4. FG-01 — Modern OpenPGP

The seven packet-handling questions in public-key section 11H remain unresolved; input-screening findings/hypotheses are source-read, not executed. **Proposed activities:** After explicit owner authorization of test scope and applicable 11H policies, use the existing five-row matrix and section 11I/12E fixtures to verify exact version/algorithm/fingerprint, required self/direct/binding signatures/key flags, complete input accounting, public-only rejection anywhere, malformed/unsupported/critical cases, revocation/expiry/time behavior and 64 KiB/packet/subkey/UID bounds. **Fixtures / tools / dependencies:** Existing documented positive/negative vectors and synthetic non-personal key fixtures; only the candidate selected by owner for an isolated feasibility harness; exact aligned artifacts/licenses/advisories; API-31 image and authorized Pixel. **Environment split:** Desktop: inspect pinned candidate APIs/metadata and run bounded fixture tests in a separately authorized isolated harness. Emulator: API-31 build/run and resource/error behavior. Physical: Pixel/API 31 if available and owner device, plus no third-party identity claims; crypto correctness vectors must be deterministic and separately recorded from device UI behavior.

**Expected outputs / pass-fail:** Per-row result matrix, full-input/private-material negative results, cryptographic verification/usability classifications, byte-exact backup fixture comparison, resource measurements, dependency/license inventory and reproducible logs. Pass requires all five P0.4 rows and every settled policy to behave as specified. **Dependencies / risks / owner decisions:** FG-00 toolchain first; FG-02 backup round trip and FG-07 bounds/logging intersect. ## 5. FG-02 — Recoverable Whole-Aggregate Restore

**Purpose / approved requirements:** Verify the approved P0.4 STORE-only ZIP32 format, complete validation-before-S02, explicit whole-profile replacement, and fail-without-replacement recovery across all commit boundaries. Manual full backup/restore is the supported migration method. P0.5-04/06 remain PENDING. See [P0.4 backup/restore](../P0.4%20Data%20Model%20%26%20Sharing/P0.4_BACKUP_RESTORE_SPECIFICATION.md) and [storage proposal](P0.5_STORAGE_RECOVERY_PROTOCOL_PROPOSAL.md).

**Current evidence / assumptions:** P0.4 format/limits and the required old-or-complete-new invariant are documented. Immutable A2 generations and A/B pointer are proposed; A/B, write ordering, sync, directory durability and recovery precedence are unapproved/unproven. Owner policies require fail-closed corruption handling, two-stage integrity, one normal predecessor, advisory capacity estimates and fail-without-replacement. No commit protocol or fault test exists.

**Proposed activities:** Only after owner selects a concrete protocol and authorizes an isolated harness, exercise valid/invalid archive fixtures, exact entry/hash/schema/key/image checks, stale S02 state, each blob/manifest/pointer/write/sync/rename/cleanup boundary, `ENOSPC`/I/O errors, cancellation, concurrent operations and process death. Verify no partial restore, no success before established commit, no automatic fallback from committed corruption, and cleanup only after protected-root reconciliation/proof. Distinguish proven pre-commit interruption (last demonstrably committed generation remains authoritative) from corruption of already committed data. Any capacity estimates must include full candidate, temporary writes, protected generations/assets/pins/recovery evidence and reserve, and are advisory.

**Fixtures / tools / dependencies:** P0.4 approved synthetic backup fixtures and corrupted/oversized/path/duplicate-entry variants; exact image/key-byte fixtures; owner-approved pointer/commit harness; API-31 filesystem and authorized Pixel. No numerical reserve threshold is set here. Do not modify the crash-state table or P0.4 format.

**Environment split:** Desktop: schema/ZIP parsers and deterministic state-machine/fault-injection harness after approval. Emulator: API-31 process kill/storage exhaustion/restart tests. Physical: Pixel filesystem/provider behavior and authorized forced-restart evidence; application-level simulation does not prove true power-loss durability. Hardware power-cut evidence and acceptable residual risk remain owner decisions.

**Expected outputs / pass-fail:** Per-boundary state ledger showing old/new/unknown, authoritative pointer/reference observation, preserved roots, user-visible outcome and artifacts. Pass requires exact complete old or new profile when commit is established, fail-closed/no-valid-data claim when ambiguous/corrupt, no protected data deleted, and exact-byte backup round trip. Any hybrid, partial replacement, silent reset/fallback, false success, unprotected cleanup or missing evidence is FAIL/BLOCKED. FG-02 remains OPEN until owner disposition and required later evidence.

**Dependencies / risks / owner decisions:** FG-00 required; FG-01 and FG-05 validators feed restore; FG-06 provider behavior and FG-07 recovery/diagnostics intersect. Owner must approve representation, pointer, ordering, recovery precedence and power-loss evidence before this gate executes. P0.2 UI changes require separate change control.
