# VCard Native — P0.5 Technical Architecture Draft

**Status: PROPOSED — OWNER REVIEW REQUIRED; NOT A FINAL ARCHITECTURE**  
**Date:** 2026-10-30  
**Milestone:** P0.5 IN PROGRESS  
**Binding baseline:** [P0.5 planning baseline](P0.5_PLANNING_BASELINE_DRAFT.md), approved October 29, 2026 for architecture documentation/feasibility research only.  
**Requirements:** Approved P0.1–P0.4 documents; see the baseline's input inventory.  
**Implementation:** Not started; no module, SDK, dependency, manifest or runtime result is implied.

## 1. Purpose and status

This document synthesizes an evidence-based architecture direction for owner review. The only approved architectural facts are the product/UX/data contracts and owner-confirmed planning baseline. Kotlin/Jetpack Compose, state-management patterns, navigation, persistence, cryptography, image processing, QR/vCard libraries, SDK/toolchain values and module boundaries remain **PROPOSED** until individual decisions and the final P0.5 architecture are approved.

The central architectural invariant is one coherent saved profile aggregate. Screen state, export projections and owned assets must all resolve from an identified saved generation. Draft edits remain distinct until explicit Save. S02 restore validates and stages a complete replacement before an explicit user confirmation; interruption must recover the complete old or complete new profile, never a mixture.

## 2. Scope and fixed product boundary

The architecture maps only the approved v1.0 product: one profile, six navigable screens (`N01`–`N06`), two sheets (`S01`/`S02`), one dirty-state dialog (`D01`), offline Contact QR by default, separate configured hosted-URL QR, action-specific contact export confirmation, optional public-key input/download, app-owned images, full-app backup/restore and native external handoffs. No Wallet/NFC, account, cloud sync, WebView, key generation/keyserver, extra routes, field inputs, format selector, partial restore or extra confirmation flow is proposed.

Hard contracts include mandatory fullName with locked visibility defaults, exactly 15 approved field slots, independent card/contact-export visibility, 3.0 provisional vCard mapping, bounded QR v1-40/M/ECI rules, canonical JPEG/PNG image bytes, bounded public-only OpenPGP compatibility and STORE-only full backup. See P0.4 as source of exact schema/limits; this architecture does not restate it as a new authority.

## 3. Proposed responsibility boundaries

```text
┌─────────────────────────────────────────────────────────────┐
│ Compose presentation candidate                              │
│ N01-N06 · S01/S02 · D01 · accessibility/insets/Back        │
└──────────────────────────────┬──────────────────────────────┘
                               │ events / immutable screen state
┌──────────────────────────────▼──────────────────────────────┐
│ Screen state holders / ViewModels candidate                 │
│ caller context · draft lifetime · operation outcomes        │
└──────────────┬────────────────────────────────┬─────────────┘
               │ commands/queries               │ platform results
┌──────────────▼──────────────────────┐   ┌─────▼───────────────┐
│ Domain policy / projection          │   │ Android adapters    │
│ field privacy · validation          │   │ Activity Results    │
│ vCard · QR · key/image policy       │   │ SAF / Photo Picker  │
│ backup validation / snapshot rules  │   │ FileProvider/Intents│
└──────────────┬──────────────────────┘   └─────────────────────┘
               │ repository interfaces
┌──────────────▼──────────────────────────────────────────────┐
│ Data / asset implementation candidate                      │
│ active saved generation · immutable owned bytes · staging   │
│ recoverable commit/reconciliation · strict backup streams   │
└─────────────────────────────────────────────────────────────┘
```

This is a conceptual ownership diagram, not a package tree or finalized module diagram. Proposed principles:

- UI consumes immutable screen state and emits user intents; rendering does not serialize contacts or decide key usability.
- A policy/projection boundary owns allowlisted fields, validation, contact projection, QR payload rules, key status, image canonicalization decisions and backup semantics. It must not depend on Compose widgets.
- A repository boundary owns saved-profile reads/writes, owned asset bytes and generation/revision consistency. The actual engine is unresolved; see [state/storage/recovery](P0.5_STATE_STORAGE_AND_RECOVERY.md).
- Android-specific selection, URI access, Sharesheet/contact intents, clipboard and system results stay in adapters. External app return does not become a domain-level delivery-success event.
- Avoid introducing multiple Gradle modules or dependency-injection frameworks unless P0.5 shows a concrete ownership/build benefit. A one-app-module arrangement with package boundaries is a candidate, not an approved layout.

## 4. UI state and navigation candidates

Official Android guidance favors unidirectional data flow, state holders/ViewModels, immutable observable state and lifecycle-aware collection. A candidate screen state holder exposes a `StateFlow<ScreenState>` and handles explicit events. Compose collects it lifecycle-aware. This is a proposed pattern; exact ViewModel, lifecycle and Compose artifact versions are unselected.

Candidate state split:

- **Saved state:** immutable snapshot identified by a local generation/revision, containing one `AppData` profile, appearance, visibility, metadata and owned-asset references.
- **Editor draft:** temporary copy in N04/N05 until explicit Save; does not mutate repository saved state. Do not promise process-death persistence of unsaved drafts beyond approved requirements.
- **Operation state:** bounded UI status for validation, picker, S01/S02, write progress, cancellation and honest success/failure/unknown result. Do not persist raw paths, payloads, key bytes or personal data in saved UI state.
- **Export snapshot:** immutable projection and bytes bound to generation, mode, action and policy version. S01 confirmation is action-specific; a generation change invalidates/requires fresh review.

Navigation is unresolved: compare stable Navigation 2, stable Navigation 3 and a deliberately small custom back-stack state against the exact six destinations, sheets/dialog, caller return (Clarification B), process recreation and predictive Back. Newer API surface is not itself a reason to migrate. Verify selected release compile SDK/AGP/minSdk metadata and Dialog/overlay lifecycle behavior. N04/N05 dirty Back remains D01; no primary-tab escape bypasses it. N02 fresh entry defaults to Contact QR; returning from external flow retains the current still-valid mode.

P0.3 tokens/components and screen geometry remain authoritative. Use the approved UI library/custom components after UI implementation is separately authorized; do not let an architecture candidate change visual tokens, screen count, routes or action placement.

## 5. Data and projection boundaries

A candidate domain model has exactly one nullable saved profile, with the approved 15 slot keys, visibility matrix, two appearance settings, timestamps and typed references to zero or more owned image/key bytes. Exact fields/schema stay governed by P0.4. No duplicate contact-model copy is created for export.

Projection is an explicit pure transformation from a saved generation plus approved action context:

```text
SavedGeneration + Action + VisibilityPolicy
  -> ValidatedProjection + IncludedDataSummary + SnapshotIdentity
```

For contact QR and `.vcf`, the same filtered projection feeds the provisional vCard 3.0 serializer. Excluded values never appear in payload bytes, NOTE composition, preview or logs. Web QR is a separate projection containing only the validated hosted HTTPS URI. Public key/image bytes are not contact-export fields. Backup is a different full-data projection and includes hidden saved fields and approved assets.

No network service is required for core card, contact QR, `.vcf`, image or key operations. Web QR generation is local; browser connectivity and hosted content are external dependencies. No background sync or remote profile resolver is included.

## 6. Save, assets and recoverable restore

### Explicit Save

N04/N05 loads a saved snapshot into a draft. Save validates the entire proposed profile and all draft-owned asset references, commits as one coherent generation, then publishes refreshed saved state and invalidates derived export snapshots. Failure retains the prior saved generation and keeps recoverable draft values. An image/key URI is temporary access only; saved ownership must be app-private bytes. Exact persistence mechanism and schema migration are P0.5-04/05 proposals.

### Restore

S02 flow is whole-aggregate, not merge:

```text
untrusted archive -> bounded stage -> validate structure/hashes/schema/assets/key
                  -> immutable candidate -> S02 review -> explicit confirmation
                  -> durable whole-generation switch -> confirm active generation
                  -> refresh UI / invalidate old exports / delayed cleanup
```

Malformed/unsupported/private-key input or any semantic/hash/reference error rejects the candidate before replacement. Supported data-valid expired/revoked keys remain retained but unusable as defined by P0.4; unsupported historical formats reject the entire restore. Commit/restart protocol must recover one complete old or new generation. `AtomicFile`, DataStore or Room alone cannot be claimed to provide this cross-resource transaction. See [P0.5 state/storage/recovery](P0.5_STATE_STORAGE_AND_RECOVERY.md).

### Asset processing

The candidate image boundary validates bounded still JPEG/PNG/WebP input, dimensions/pixel work, orientation, sRGB, alpha and canonical output format before a draft can save. It produces opaque JPEG quality 90 or PNG under approved branch rules, strips arbitrary inherited metadata and stores/hash-validates exact bytes. Restore does not re-encode. OpenPGP validation is a maintained parser/verifier feasibility gate; never implement custom packet/cryptographic validation as an architectural shortcut. See [image feasibility](P0.5_IMAGE_PIPELINE_FEASIBILITY.md) and [public-key feasibility](P0.5_PUBLIC_KEY_FEASIBILITY.md).

## 7. Export and Android handoff lifecycle

- Contact QR is generated from a coherent saved export projection, immediately displayed when it fits, with included-data summary. No blocking S01 before initial presentation.
- `.vcf` creation and contact QR image save/share require S01 plus explicit action-specific confirmation before file/image creation. If generation changes before output start, refresh and reconfirm.
- Hosted QR contains only the configured HTTPS URL; there is no automatic web fallback, URL append, profile fetch or internet requirement to render it.
- Incoming photo/key/backup bytes use user-mediated selection and are copied/validated into app-private storage. Outgoing file/image artifacts use SAF destination selection or app-private cache plus narrow FileProvider read grants, whichever is later selected.
- FileProvider path exposure must be narrow, non-exported, grant-only, read-only where possible; no `file://`, root path or broad directory exposure. Keep generic non-identifying filenames and correct MIME types.
- Handoff cancellation/return is not recipient delivery, contact import or successful write. Unknown results must be reconciled before retry. Invalidation blocks new app reuse but cannot revoke external copies.
- Unused cache retention is capped at the approved 24-hour target when safe. Do not delete bytes needed by an active receiver; restart cleanup behavior remains a feasibility/design question.

Exact package APIs, intent shapes, grants, providers, picker contracts, cleanup and supported receiver behavior remain unselected; see [P0.5 sharing/artifact lifecycle](P0.5_SHARING_AND_ARTIFACT_LIFECYCLE.md).

## 8. Error and security boundaries

- Validate at trust boundaries: external file bytes, field drafts, URI values, public-key packets, backup archives and provider results.
- Separate structure/cryptographic validity/current usability/identity trust for keys. Successful parsing or fingerprint calculation is not identity verification.
- Every resource cap applies to actual streamed/decoded work, not only declared sizes. Use checked arithmetic and bounded recursion/cardinality.
- User-facing errors identify repairable action without leaking raw data. Never log profile fields, key material, vCard/QR payloads, archive JSON, content URIs or filesystem paths.
- Keep full backups distinct from contact privacy filters; hidden values are intentionally present only in complete backup.
- Treat write/restore interruption as unknown until active generation/output is reconciled. Do not report success early or automatically repeat external actions.

Security review must cover exported components, minimum permissions, provider paths, ZIP traversal/duplicate entries, malformed image/resource exhaustion, key parser limits, URI injection and logging. P0.1/P0.4 constraints are binding; this architecture makes no security certification claim.

## 10. Explicitly unresolved decisions

1. `minSdk 31` only becomes final after every selected API and maintained dependency is verified to support API 31. `targetSdk` and `compileSdk` remain unselected.
2. Navigation 2 vs Navigation 3 vs custom state is undecided; compare exact back/overlay/return behavior and build requirements.
3. Compose BOM/Kotlin/compiler/AGP/Gradle/JDK versions are undecided; no project setup should precede owner approval.
4. Persistence engine, schema and the cross-resource commit/recovery protocol are undecided; single-file atomicity is insufficient evidence.
5. vCard serializer, QR encoder and OpenPGP stack are unselected. The OpenPGP matrix cannot be reduced without explicit owner approval.
6. Image decoder/encoder, safe WebP branch classification, metadata verification and memory envelope remain unresolved.
7. Provider/picker contract versions, exact FileProvider paths/grant duration and cleanup after restart remain unresolved.
8. Measured performance on Pixel 9 Pro XL/API 31 and the supported device range is absent; PRD targets remain targets, not achieved results.

Any recommendation must include alternatives, requirements traceability, primary-source URLs/access date, exact release/license/API evidence, disadvantages, runtime obligations and owner approval status. P0.5 remains in progress; this draft is not final architecture approval.
