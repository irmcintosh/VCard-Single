### FG-01 — Modern OpenPGP: high security/compatibility risk

P0.4 contains standards research and Bouncy Castle/PGPainless candidates, not proven Android support. Preserve all five authoritative matrix rows: v4 RSA and legacy EdDSA/ECDH Curve25519 combinations; v6 RSA/Ed25519/native X25519 combinations. All remain **REQUIRES FEASIBILITY VALIDATION**. Signing-only algorithms do not provide encryption capability.

Research exact maintained APIs/source behavior for each row, v4 40-hex/v6 64-hex fingerprints versus asset SHA-256, required self-certifications/direct-key signatures, bindings/key flags and verified revocations. Can a candidate preserve expired/revoked data while evaluating current usability independently? Can it inspect the entire input and reject secret packets, malformed/mixed material and unsupported critical semantics within the existing 64 KiB/packet/cardinality bounds? Examine authorized-revoker and clock ambiguity without inventing acceptance behavior.

Exit evidence: a per-row capability/limitation record, primary-source/API evidence, licensing/transitive obligations, current maintenance/advisory review, Android/provider/API suitability and bounded-work analysis. A limitation affecting an approved pairing must be escalated; any matrix reduction requires explicit owner approval. No custom crypto parser, dependency selection or verified support claim is made here.

### FG-02 — Recoverable whole-state replacement: high data-loss risk

Approved targets are strict STORE-only ZIP32/JSON, per-entry hashes and semantic validation, at most 24 MiB archive/20 MiB entry bytes, validation before S02 and complete old-or-new state after interruption. No persistence or commit protocol has been selected.

Compare persistence/asset coordination options, including an aggregate-generation approach versus transactional metadata with coordinated immutable assets. Identify the durable commit boundary/reference, staging, startup reconciliation, cleanup and ownership of actual bytes. Do not treat a metadata transaction or single file operation alone as proof of whole-state durability. How are concurrent Save/restore/export, low storage, cancellation, first-run restore, process termination and incomplete staging handled?

Exit evidence: a documented protocol and failure-boundary analysis demonstrating how all metadata/settings/visibility and owned assets remain coherent, with later fault-injection obligations. Unsupported key formats reject the entire candidate before replacement. No silent key deletion, hybrid state, automatic pre-restore backup, user-visible history or partial recovery feature is authorized. Crash recovery remains untested.

### FG-03 — QR encoding/rendering: high recipient/geometry risk

Keep Model 2/M, versions 1–40, the 4,096-byte serialized UTF-8 resource guard and smallest actual fitting version. ASCII omits ECI; non-ASCII uses UTF-8 ECI 26. The guard is not a claim of encodable capacity. Encoding capacity, resource safety, physical rendering and scanner recognition remain separate gates.

Research candidates' mode/ECI/overhead/version controls and unscaled matrix output. Specify integer modules at least 2dp and 3 physical pixels using actual density/panel width, four-module quiet zone plus 16dp outer white pad, 280dp preferred panel and existing 320dp cap. Preserve exported PNG at 8px/module; no smoothing, overlay or theme tint.

Exit evidence: exact encoder API behavior and rendering/fit design with explicit failure paths and later device/scanner obligations. No truncation, omitted included fields, correction downgrade or automatic web substitution. Independent .vcf remains available when QR fails. Mathematical fit does not prove scanning.

### FG-04 — vCard: medium/high recipient-fidelity risk

Keep initial vCard 3.0 FN/empty-N mapping, UTF-8/CRLF, 75-octet physical-line policy and 64 KiB output bound. Existing paired 3.0/4.0 compatibility cases remain mandatory; Pixel/scanner behavior is unverified.

Evaluate bounded serializer/library and independent-checking options for escaping/unfolding, injection resistance, URI values, repeated URLs and independently filtered NOTE provenance. Retain 4.0 optional-N and correct TEL/EMAIL considerations as an evaluation alternative, never a runtime fallback.

Exit evidence: exact mapping/byte-policy capability and traceability to every included/excluded field, plus preserved recipient obligations. Any change to 4.0 requires explicit owner approval before implementation. Standards conformance or an API claim is not recipient evidence; no selector or extra name fields.

### FG-05 — Images: high memory/privacy and medium quality risk

Keep still JPEG/PNG/WebP input, <=20 MiB source, side<=8,192px and <=16,777,216 pixels. Canonical opaque JPEG/lossy-WebP becomes JPEG quality 90; alpha/PNG/lossless-WebP/uncertainty becomes PNG. Portrait longest edge<=1,024px, cover<=2,048px and retained asset<=8 MiB. Codec/device behavior remains untested.

Research bounded inspection/decode/allocation, animation/polyglot rejection, orientation/sRGB conversion, downsampling without upscaling and reliable alpha/source classification. Can fresh encoding remove EXIF/GPS/IPTC/XMP/comments/source URI while retaining only necessary normalized format/color data? Check encoder availability and work/memory bounds; do not assume compressed byte limits bound decoded work.

Exit evidence: supported decode/encode and metadata policy, resource analysis, actual codec/MIME/geometry/policy/hash validation plan and later quality/Pixel checks. No source-file passthrough, canonical WebP output, crop/filter controls or new route. Validation is deterministic for retained bytes/policy, not a cross-encoder byte-identity promise. Backup/restore never re-encodes assets.

### FG-06 — Native handoffs/artifacts: high privacy/lifecycle risk

Keep native file/photo/communication handoffs, app-owned scoped content URIs and narrow temporary read grants. Preserve the approved 24-hour unused-cache retention target without breaking active receiver access; an external return never proves delivery.

Research platform/API behavior for local offline destinations versus external cloud providers, chooser cancellation, provider/grant loss, incomplete output and receiver lifetime. Bind confirmations/snapshots to mode/action and revalidate before output starts; no .vcf/contact-image export creation before required S01 confirmation. How can cleanup reconcile stale invalidation, unused retention, active grants and restart? Unknown outcomes must not trigger duplicate handoffs/writes.

Exit evidence: documented result/grant/cache state transitions, minimal access/exposure rationale, cancellation/partial-output handling and later provider/recipient obligations. Do not claim earlier external copies can be revoked or cloud providers work offline.

### FG-07 — Integrated safeguards: cross-cutting release risk

Keep offline core, minimal access, no content/key logging, accessible semantics/large-text/inset/motion intentions and unchanged PRD targets: usable warm-launch card within 2 seconds and QR generation within 1 second for supported payloads. These are targets, not measurements.

Exit evidence: scheduling/cancellation/error and exposure analysis, approved-requirement traceability, observable verification seams and explicit unresolved constraints. Measurement procedures remain P0.6 work. Infeasible fixed constraints or genuine design conflicts require owner review.

The authoritative algorithm matrix and complete limits remain in the approved P0.4 files. Summaries above do not broaden accepted algorithms, packets, formats or defaults. Historical storage eligibility still requires supported structure and required cryptographic relationships; neither fingerprints nor matching backup digests establish identity trust or sufficient key validation.
