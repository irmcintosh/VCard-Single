## 1. Executive summary

The current user-visible application label is **VCard Native**. The implemented application ID and Android namespace are both **`com.mackseoul.vcardnative`**. The latter was an owner-confirmed P0.5 planning decision and is the established application ID; the older `com.vcardnative.app` entry in the legacy decision log is explicitly a placeholder, not the current identity.

The launcher uses an existing blue business-card/contact graphic with a QR motif, a black adaptive-icon background, and density-specific PNG resources. The two adaptive icons have no monochrome layer. Their final brand approval and artwork provenance are not established by the reviewed documents; their presence alone does not establish that they are placeholders. The app has no separate custom splash screen in the inspected source: its launch theme supplies a dark window background and the system supplies launch behavior.

The approved visual direction is dark-first, with an optional light appearance and Sapphire, Jade, and Amethyst accent choices. The approved PRD and current implementation use the name VCard Native, but the reviewed records do not establish a separate final-brand, trademark, or logo approval. Final user-visible naming and visual identity remain for owner decision.

**Recommendation:** retain the established application ID and namespace. After owner approval, limit any implementation to the approved display name/copy and any expressly approved icon or splash assets. Do not rename backup-format identifiers, shared-file contracts, source packages, versions, or signing settings as a cosmetic branding exercise.

## 4. Branding consistency findings

1. **Current name:** the approved PRD, Android label, and active hosted-profile guidance consistently use VCard Native. A final public-facing brand name is not separately established in the reviewed decisions.
2. **Historical ID mismatch:** legacy D-010 lists placeholder `com.vcardnative.app`; the later P0.5 owner-confirmed value and current Gradle configuration are `com.mackseoul.vcardnative`. Treat D-010 as history, not an instruction to switch IDs.
3. **Status snapshot:** development progress still says M1.13 has not started because it predates the owner's new authorization. This report records the current OPEN / Step 1 status; existing documentation is intentionally unchanged.
4. **Name-bearing compatibility strings:** changing only the launcher label would leave `VCard Native` in hosted guidance and a second string resource, while `vcard-native` remains in export filenames and the backup format marker. The marker must be treated differently from user-facing copy.
5. **Launcher and themed icons:** current launcher artwork is present, but its final approval/provenance is not documented in the reviewed sources. Both adaptive definitions omit a monochrome layer; the optional themed-icon appearance remains a decision, not an automatic change.
6. **Visual direction versus icon:** the in-app dark/light palettes and restrained accents have owner-approved P0.3 evidence. The bright blue launcher graphic is separately observable; the reviewed approval record does not explicitly approve or reject it as the final launcher brand.

## 5. Technical and release impact

| Potential change | Risk and boundary |
|---|---|
| Display label or user-visible copy | Generally cosmetic and low risk if the application ID, signing identity, data formats, and behavior stay unchanged. Review in-app literal strings and launcher/Settings truncation and accessibility. An actual update still must be signed with a compatible signing identity. |
| Launcher artwork / optional monochrome layer | Primarily visual, but affects adaptive masking, density, contrast, launcher shape, and themed-icon appearance. Preserve existing behavior until the owner approves a direction and authorized validation. Do not assume a new asset is licensed or approved. |
| Splash styling | Changes startup presentation and potentially visual continuity/accessibility. There is no custom branded splash to rename in the current source; any new splash design or dependency requires separate approval. |
| Application ID | **Potentially disruptive:** Android treats a changed ID as a different app, not an in-place rename. Existing app-private profile data, images, operation/recovery data, and cache are not automatically transferred to the new app. [`MainActivity.kt`](../../android/app/src/main/java/com/mackseoul/vcardnative/MainActivity.kt) uses `noBackupFilesDir` for managed data and backup staging; the manifest disables Android backup. A user-directed compatible backup/restore may be a migration option only if separately designed and verified; no automatic migration is established. Changing the ID also changes package-derived authorities/permissions and can invalidate prior shared-URI/grant expectations. |
| Kotlin namespace or source packages | Separate from Android application ID. Changing them need not change the installed ID, but affects generated `R` imports, manifest component resolution, source imports, and tests. It offers no necessary benefit for a display-name change. |
| Backup marker and filenames | Changing `vcard-native-backup` in [`BackupArchive.kt`](../../android/app/src/main/java/com/mackseoul/vcardnative/data/backup/BackupArchive.kt) without a compatible reader would reject existing backups. Changing suggested backup, VCF, or public-key filenames can affect external handoffs, documentation, and tests even when payload bytes are unchanged. Preserve them unless separately approved and verified. |
| Signing and distribution | Same-ID updates require compatible signing; changing only the label does not require changing the signing identity. The M1.12 APKs were signed with a disposable test identity and are not production-distributable. Production credentials must remain isolated from Gradle build workers; production signing/distribution remains outside this step. |

## 6. Recommended minimal implementation scope

After the owner approves specific choices, and only under a subsequent implementation authorization:

1. Retain `com.mackseoul.vcardnative`, the current namespace and source packages, version, provider authority contract, backup format, export payloads/filenames, privacy behavior, and signing settings.
2. If the display name changes, update `app_name` and review the two name-bearing string resources without changing sharing or hosting behavior.
3. Change launcher/monochrome or splash assets only if explicitly approved; use owner-authorized artwork and preserve the approved P0.3 in-app visual direction unless a separate revision is approved.
4. In a later authorized verification step, check launcher/Settings labels and icon rendering on isolated devices, plus relevant build/lint and sharing/backup regression coverage. No such testing was run here.
