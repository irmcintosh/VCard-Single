# M1.12 Step 4A — Final Security and Release-Gate Assessment

**Assessment status:** Read-only review completed from the available source, build reports, and prior verification evidence.  
**Milestone status:** Milestone 1.12 remains **OPEN**. Milestones 1.13–1.16 have not started.  
**Scope boundary:** No application, Gradle, manifest, dependency, signing, or approved documentation changes were made for this assessment. This report is the only new file.

## 1. Executive summary

The current debug and release machine-readable lint reports each contain **59 warnings and zero errors**. They have the same inventory. None is a security/privacy or accessibility warning. Most are unused strings and advisory tool/version recommendations. Three `Recycle` warnings are false positives for streams closed with Kotlin `use`; the storage-capacity recommendation is not a release blocker. No warning alone establishes an exploitable vulnerability.

The Step 3B evidence remains strong for the tested configuration: 187 JVM tests passed; the focused sharing, public-key, backup, and recovery instrumentation suite passed 19 tests on each isolated API 31 and API 37 emulator; debug/release builds and lint passed; and a disposable test-signed release installed and launched on both API levels as non-debuggable. This did not exercise the entire product workflow using the release APK, enable R8/resource shrinking, or prove chooser grant revocation after recipient use.

The Kotlin Gradle plugin issue GHSA-r937-wjx7-w2jp / CVE-2026-53914 was addressed by Kotlin and matching Compose compiler plugins 2.4.21. The recorded targeted OSV queries found no additional advisory for the queried Kotlin coordinates. **The complete resolved transitive build-plugin graph was not assessed**, and no complete supply-chain clearance is claimed. In this execution environment, the available Android Studio JBR is Java 25.0.3; a fresh Gradle dependency query failed before configuration, so the prior Step 3B resolution and advisory results are used as historical evidence, not represented as a new scan.

The Gradle wrapper distribution checksum is configured and repositories are centralized, but Gradle dependency-verification metadata and dependency locking are absent. Introducing reviewed, enforced dependency verification is recommended before production release. The app intentionally presents a digital business card and QR; a blanket `FLAG_SECURE` policy would undermine that use. The owner should decide whether to retain current screenshot behavior or approve a narrowly scoped preview-redaction approach.

**Release gate recommendation:** Keep M1.12 open. Prioritize a verified plugin/dependency integrity process and release-APK workflow regression using synthetic data, then record owner decisions on screenshot privacy and production distribution/signing. No dependency upgrade, warning cleanup, shrinking, or product behavior change is proposed as part of this assessment.

### Evidence and coverage

* Step 3B recorded successful resolution of Kotlin Android Gradle plugin **2.4.21** and Compose compiler Gradle plugin **2.4.21** from configured Maven Central repositories, using their `gradle811` variants. AGP remains **8.10.1**, wrapper **8.11.1**, and the recorded build JBR was **21.0.11**.
* The earlier dependency inventory recorded 88 unique app runtime module names and an OSV batch query across 92 app/plugin/test coordinates. The Step 3B targeted OSV checks for KGP 2.4.21, Compose compiler plugin 2.4.21, queried KGP API/compiler artifacts, and selected Kotlin runtime coordinates found no additional published advisory in those queries.
* The reviewed GHSA-r937-wjx7-w2jp / CVE-2026-53914 affects the Kotlin Gradle plugin versions before the advisory’s fixed threshold (the Step 3B report records `< 2.4.20-Beta1` as affected and 2.4.20-Beta1 or later as fixed). The resolved 2.4.21 plugins are beyond that threshold. The vulnerable build-cache deserialization concern is a build-environment risk; it is not evidence that the packaged APK has a runtime vulnerability.

AGP 8.10.1 and the full AGP/KGP/Compose implementation/transitive graph therefore remain **unverified for complete advisory coverage**. No advisory was identified for AGP 8.10.1 in the recorded targeted lookup, but that is not proof of absence.

## 4. Dependency integrity and reproducibility

### Current controls observed in project configuration

* `android/gradle/wrapper/gradle-wrapper.properties` pins Gradle 8.11.1 and has `distributionSha256Sum=f397b287023acdba1e9f6fc5ea72d22dd63669d59ed4a289a29b1a76eee151c6`; distribution URL validation is enabled.
* `android/settings.gradle.kts` centralizes plugin repositories (`google()`, `mavenCentral()`, `gradlePluginPortal()`) and dependency repositories (`google()`, `mavenCentral()`). `FAIL_ON_PROJECT_REPOS` prevents project-level repository additions.
* No `gradle/verification-metadata.xml` or dependency lockfiles/locking configuration were found in the reviewed project.
* `android/gradle.properties` sets `org.gradle.configuration-cache=false`. This is distinct from Gradle’s task build cache. No project remote-cache configuration or `org.gradle.caching=true` was found in the recorded review; the Step 3B tasks explicitly used `--no-build-cache`. User/CI environments outside the reviewed machine are not covered.

### Recommendation

Introduce Gradle dependency verification metadata in a separately reviewed change before production release. It should cover plugin and application configurations, tests, and all resolved variants; use strict verification in CI and ordinary release builds. Bootstrap from a trusted, clean environment; independently validate artifact hashes against authoritative publisher or repository evidence where available, review signer fingerprints rather than blindly accepting downloaded signatures, and keep metadata changes reviewable in source control. Gradle’s automatic metadata generation is a starting point, not proof that the initially resolved artifacts are trustworthy. A checksum pins bytes but does not prove that the bytes are benign or author-approved; signatures also depend on correctly established signing-key trust.

Dependency locking is a complementary reproducibility control, not a replacement for verification. Pinning transitive versions makes resolution changes visible, while checksums/signatures detect artifact substitution. Adopt both through a scoped build-hardening change and validate normal, test, and plugin configurations. Do not add or generate metadata as part of this assessment.

References: [Gradle dependency verification](https://docs.gradle.org/current/userguide/dependency_verification.html), [Gradle build security best practices](https://docs.gradle.org/current/userguide/best_practices_security.html), and [Gradle Wrapper verification](https://docs.gradle.org/current/userguide/gradle_wrapper.html).

## 5. Screenshot, task-switcher, and screen-recording privacy

No `FLAG_SECURE` use was found in the reviewed activity. Sensitive profile fields and QR content can therefore be exposed through user screenshots, screen recording, or recent-app/task-switcher previews according to Android/system behavior. This is a **privacy exposure inherent in the current display behavior**, not a confirmed unauthorized data access vulnerability: the app intentionally displays a digital business card and QR for sharing.

`FLAG_SECURE` asks Android to block screenshots and non-secure display capture and can suppress sensitive activity content from recent-task snapshots. Its cost here is material: it would prevent the intended act of capturing/sharing a displayed QR through screenshots, may interfere with accessibility/support workflows, and cannot prevent photography by another device. A blanket activity-wide flag is therefore **not recommended without owner approval**.

Recommended owner choice:

1. Retain the current behavior and document that displayed card/QR data can be captured; or
2. Approve a narrowly scoped lifecycle redaction of the recent-task preview, while keeping normal foreground display and offline QR/VCF sharing intact. Validate on supported Android versions before adoption.

No privacy-control change was made. Reference: [Android guidance for securing sensitive activities](https://developer.android.com/security/fraud-prevention/activities).

## 6. FileProvider and temporary sharing assessment

### Confirmed source/configuration facts

* The source manifest declares `ContactFileProvider` non-exported with URI grants enabled; its authority is `${applicationId}.contact-files`.
* `android/app/src/main/res/xml/contact_file_paths.xml` exposes only the contact and public-key payload subdirectories under app cache. The provider accepts only mode `"r"` and denies delete.
* `NativeContactSharing.shareBytes()` uses a UUID-named temporary file, adds `FLAG_GRANT_READ_URI_PERMISSION` to the send/chooser intent and includes the URI in `ClipData`. It does not grant write access. There is no explicit `revokeUriPermission()` after chooser completion.
* `TemporaryContactFiles` writes a lease before publishing the URI, syncs file writes, checks symlinks and expected directory/file names, and uses cache storage. A lease from an older boot is removed because non-persistable grants do not survive reboot. Same-boot or uncertain leases are retained because the app has no complete grant inventory; unleased directories receive 24-hour retention.
* Step 2/3B focused tests covered read-only sharing, unauthorized access, write denial, provider path boundaries, explicit revocation behavior, and temporary-file handling. Step 3B ran 19 focused tests on each isolated API 31 and API 37 emulator.

### Remaining uncertainty and tests

The chooser/recipient grant lifetime after the receiver completes is not established by the current evidence. The absence of app code explicitly revoking a URI is not by itself proof that an unauthorized app can access it: Android applies URI grants to the receiving component/task. Conversely, cache retention means the backing bytes may remain in app-private storage after sharing; the URI is not intended to be a permanent public URL. Retention and deletion are best-effort filesystem behavior, not secure physical erasure.

Before M1.12 acceptance, use two isolated test apps or a controlled recipient harness to verify: intended recipient can read; unrelated UID cannot read; read grant cannot be upgraded to write/delete; grant behavior after chooser cancellation, recipient completion, task removal, and reboot; repeated shares use distinct payloads; interrupted handoff cleanup remains safe; and same-boot lease retention does not break intended sharing. Do not shorten cleanup or revoke grants before recipient access without owner approval. Preserve existing offline QR and VCF flows.

Android references: [FileProvider API](https://developer.android.com/reference/androidx/core/content/FileProvider) and [provider URI permission grants](https://developer.android.com/guide/topics/manifest/provider-element#granturipermissions).

## 7. Sensitive data, backup, and cryptographic boundaries

* Project evidence identifies profile data and image variants as app-managed local data. App-private storage restricts access by Android sandboxing but **is not encryption at rest**. A compromised/unlocked device, privileged access, or forensic access may expose data.
* The manifest sets `allowBackup=false`; full-backup and data-extraction rules exclude app data domains. This excludes Android-managed backup/transfer, not the user-directed backup workflow.
* User-directed backups remain intentionally plaintext. Their integrity checksum can detect some accidental corruption/tampering but does not authenticate the author or provide confidentiality. Do not represent checksum validation as authenticity.
* The reviewed OpenPGP path supports public-key validation/storage/export. Prior source review identified no private-key generation, storage, or export path. Public-key material is intentionally sharable; no private key should be placed in profiles, logs, backups, or temporary share files. No cryptographic algorithm or provider change is recommended by this assessment.
* Temporary sharing and backup staging files are app-private/cache or no-backup paths and use bounds/cleanup logic. Their existence is not encryption. External backup files and recipients’ copied contacts are outside app deletion control.
* The recorded Step 2 sampled startup-log review found no synthetic profile/private-key pattern, but it was not a complete runtime data-flow proof. Release-specific end-to-end checks should confirm no profile or key material appears in logcat, crash output, or unexpected cache/temp locations.
* Deletion messaging correctly avoids promising secure physical erasure. Recovery evidence may persist without automatic expiration; this is intentional preservation behavior, not a retention guarantee of deletion.

**Google Play distribution:** Google Play App Signing keeps the app-signing key under Play’s management (or an owner-controlled supported arrangement), while the developer uses an upload key to authenticate uploads. Decide Play enrollment, account ownership, upload-key custody/recovery, and artifact/bundle pipeline before a production upload.

**Direct APK distribution:** production APKs must be signed with a durable app-signing key. Protect the private key offline or in a properly controlled signing service, restrict authorized use, maintain secure encrypted backups and recovery procedures, and record certificate fingerprints. Future in-place updates must retain a compatible signing identity; losing the key can prevent ordinary update continuity.

Do not create a key, alter signing configuration, publish, or distribute as part of M1.12 Step 4A. Branding/package identity/version and release-channel decisions belong to Milestones 1.13/1.14; production key custody and distribution approval must be explicit owner decisions. No production readiness should be inferred from a test-signed artifact.
