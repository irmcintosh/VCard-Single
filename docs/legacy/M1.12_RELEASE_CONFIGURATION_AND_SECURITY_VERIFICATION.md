## 3. Manifest and Android-component verification

Inspected source manifest, merged release manifest, FileProvider paths, backup rules, and data-extraction rules.

* Source exports only `MainActivity`, for the launcher intent. No app deep links or browsable intent filters were found.
* The merged manifest adds `androidx.profileinstaller.ProfileInstallReceiver`, exported but protected by `android.permission.DUMP`; it is dependency-provided, not an app-created unprotected entry point.
* `ContactFileProvider` is non-exported, has URI grants enabled, and resolves to `com.mackseoul.vcardnative.contact-files`.
* Its configured paths are limited to cache subdirectories `contact-share/payload/` and `public-key-share/payload/`.
* The merged manifest contains a signature-protected dynamic-receiver permission. No dangerous runtime permissions, `INTERNET` permission, cleartext-network opt-in, or app network stack were found.
* Application `allowBackup=false`; full-backup and cloud/device-transfer extraction rules exclude the app’s data domains. This excludes Android-managed backup/transfer, not the user-directed archive workflow.
* The merged release manifest preserves app ID, version, label, min/target SDK, and backup metadata. It has no `android:debuggable="true"` attribute. On API 31 and API 37, `run-as com.mackseoul.vcardnative` was denied with “package not debuggable,” corroborating the release flag.

### Sharing checks

`ContactFileProvider.delete()` denies deletion. `NativeContactSharing.shareBytes()` grants read access, not write access. Focused instrumentation coverage exercised exact shared payloads, unauthorized access, write denial, provider path traversal/boundary rejection, explicit revocation, and temporary-file handling.

Chooser grant lifetime after the receiving chooser/activity closes is not established by these checks. Runtime behavior for every third-party recipient is not claimed. Keep share files in app cache, and preserve the existing offline QR/VCF flows.

### Sensitive-data and integrity conclusions

* Profile data in app-private storage is protected from ordinary cross-app filesystem access by Android’s sandbox, but is not thereby encrypted at rest. Device/root compromise, unlocked-device access, and forensic extraction are outside that guarantee.
* The user-directed backup is plaintext. Its checksums detect accidental corruption but do **not** authenticate origin or prevent a deliberate replacement. This remains the approved design; do not describe the checksum as a signature or MAC.
* No private OpenPGP key handling was identified. The application validates and uses public key material. Random key-generation behavior is not applicable to the current app implementation.
* Static search found no profile/key logging calls or clipboard writes. The sampled test-signed release startup logs contained none of the synthetic profile/private-key patterns checked. This does not substitute for exhaustive runtime instrumentation or dependency logging review.
* Backup restore staging and recovery/deletion files remain subject to the existing Milestone 1.11 durability protocol; no changes were made to that protocol.

1. On a dedicated API 31 and current-target emulator, test the exact signed release APK: clean install, launch, metadata/manifest assertions, `run-as` denial, signature-certificate comparison, and artifact SHA-256 recording.
2. Exercise FileProvider read-only access, an unrelated UID’s denial, write/delete denial, URI traversal and provider-root boundary, grant revocation/expiry after chooser completion, and orphan temporary-file cleanup.
3. Feed restore isolated malformed and oversized ZIPs, duplicate and unexpected names, CRC/hash failures, unsupported schema, traversal names and truncated framing; verify every failed restore preserves the exact prior profile and recovery evidence.
4. Run process-kill cases only in the dedicated harness and only for the specific approved scenario.
5. ## 8. Backup schema and known issues

The implementation’s `AppData` codec uses schema 3. Readers accept schemas 1, 2, and 3; the outer backup container remains `formatVersion=1`. The backup specification’s stale schema-2-current wording was corrected to schema 3. Historical decisions, format, and old-reader behavior were not rewritten. Older APKs cannot read schema-3 profiles/backups; downgrade safety is not claimed.

Carry-forward limitations remain:

* Android Camera QR import may display literal `\n` in Notes.
* Older APK versions cannot read schema-3 profiles.
* Physical testing of the updated structured-name exporter is incomplete.
* Existing lint warnings and test-runner deprecation/limitations remain documented.
* M1.11’s accepted recovery/deletion guarantees and its documented limitations remain unchanged. No indiscriminate process-kill scenario was run.

## 9. Recommended corrections, in priority order

1. **Owner decision before release:** select a fixed, compatible Kotlin Gradle plugin version for the build-time advisory; then run the full build/test/lint/instrumentation matrix and repeat the dependency scan. Do not rely on or consume untrusted build-cache metadata in the meantime.
2. **Before production distribution:** establish owner-controlled production signing, sign only the reviewed release artifact, verify the certificate and APK/AAB signature, and record artifact hashes/provenance.
3. Resolve the 57 lint warnings deliberately; do not treat “newer available” as an automatic upgrade.
4. Decide whether sensitive UI should redact screenshots/task-switcher snapshots. If approved, scope and test the behavior without disrupting intentional share/QR workflows.
5. Add Gradle dependency verification metadata and complete a separate scan of the resolved build-plugin transitive graph; keep repositories restricted and wrapper checksum verification enabled.
6. Add a release-configuration instrumentation smoke suite for backup/restore and sharing, chooser grant expiry, and runtime symlink/target ownership cases in dedicated test storage.

## 10. Signing and artifact-verification recommendation

For production, use a dedicated release identity that is never committed to source control. Prefer Play App Signing if distributing through Google Play; otherwise keep the upload/release key offline or in a protected signing service with tightly limited access and encrypted recovery backup. Inject secrets only into a controlled signing job; never put passwords or key bytes in Gradle files, chat, logs, or the APK repository. The test-only certificate in this report must never be reused.

For every candidate: record the source revision and toolchain; build from a clean, trusted environment; verify APK with `apksigner verify --verbose --print-certs` (or validate an AAB with bundletool and verify the eventual store-signed artifact); compare the signing-certificate fingerprint to the owner-approved value; compute and archive SHA-256; inspect the final merged manifest; install and smoke-test the exact signed artifact; and retain build logs plus provenance. A successful unsigned build is not a release signature.
