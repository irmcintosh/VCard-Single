# M1.12 Step 4C — Build-Tool Advisory Triage

**Status:** Milestone 1.12 remains **OPEN**. This report is read-only triage; it does not authorize or perform dependency remediation. Milestones 1.13–1.16 have not started.  
**Advisory query date:** 2026-11-01  
**Project baseline:** AGP 8.10.1; Gradle 8.11.1; Kotlin Android and Compose plugins 2.4.21; JBR 21.0.11.  
**Scope:** The 3 Critical and 21 High OSV version matches recorded in [Step 4B](M1.12_STEP4B_DEPENDENCY_INTEGRITY_AND_RELEASE_TEST_REPORT.md).

## 1. Executive summary

The Step 4B scan identified **24 unique Critical/High advisory IDs** matching versions in the resolved build/plugin inventory. The vulnerable versions are transitive build-tool/test-tool dependencies; none are directly declared at those versions by this project. The Android Gradle Plugin (AGP) and its Android test tooling are the principal observed source. The Kotlin Android and Compose compiler plugins were in the inventory, but none of the 24 affected coordinates was traced to their published plugin dependency paths.

The findings are **confirmed version-range matches**, not proof that vulnerable behavior is reachable or exploitable in this project's build. The affected components are build-time dependencies and were not found in the release app's runtime dependency graph. The app directly resolves Bouncy Castle 1.86; the advisory-matched Bouncy Castle 1.79 is a separate build-tool dependency. Build-time-only exposure still matters: Gradle plugins execute with the build user's permissions and can affect produced artifacts.

Evidence establishes concrete paths for several components, including:

* `com.android.tools.build:gradle:8.10.1` → `com.android.tools:sdk-common:31.10.1` → `org.bouncycastle:bcprov-jdk18on:1.79`
* AGP 8.10.1 → `com.android.tools.build.jetifier:jetifier-processor:1.0.0-beta10` → `org.jdom:jdom2:2.0.6`
* AGP 8.10.1 → `com.android.tools.build:bundletool:1.18.0` → `org.bitbucket.b_c:jose4j:0.9.5`
* AGP 8.10.1 → `io.grpc:grpc-netty:1.69.1` → Netty 4.1.110.Final modules
* Android test/UTP tooling also resolves Netty 4.1.93.Final and protobuf 3.24.4. The exact UTP root configuration for all these artifacts was not exposed by the standard project dependency report; the evidence and limitation are detailed below.

No evidence supports an immediate transitive override. The safest remediation path is to identify an upstream AGP/Android test-tool release whose *resolved* plugin graph contains fixed, mutually compatible dependency families, then verify the exact toolchain tuple and repeat the release test matrix. Do not make a release build with production signing credentials available to a potentially affected Gradle build worker. Existing restricted repositories, wrapper checksum, and strict dependency checks are useful integrity controls, but they do not make a vulnerable library safe or establish initial artifact authenticity.

## 2. Evidence and method

The report uses:

1. Step 4B's Gradle-generated [verification metadata](../../android/gradle/verification-metadata.xml), which records the resolved plugin/build/runtime/test artifact coordinates.
2. The actual configured plugin declarations and repositories in [build.gradle.kts](../../android/build.gradle.kts) and [settings.gradle.kts](../../android/settings.gradle.kts).
3. Cached Maven POM/Gradle module dependency metadata for path reconstruction, and fresh Gradle `dependencies` output for `releaseRuntimeClasspath`, `debugRuntimeClasspath`, and `debugUnitTestRuntimeClasspath`.
4. OSV vulnerability records retrieved by ID on 2026-11-01. The OSV pages link to the corresponding GitHub-reviewed advisory records. Each GHSA link in the inventory opens the authoritative OSV record.

The standard `:app:dependencies` configurations describe app/test dependency graphs, not the plugin DSL's implementation classloaders. A project's `buildEnvironment` report must not be used to conclude those plugin classpaths are empty. Step 4B deliberately resolved plugins by executing the build with their `plugins {}` declarations applied. However, the available output does not preserve a complete named-configuration edge report for every plugin/UTP resolution. Therefore, a path below is called **confirmed** only where the cached published metadata supplies the edge; associations to Android test tooling are explicitly marked less certain where a root edge is not established.

## 5. Applicability summary

* **Confirmed:** OSV's affected ranges include the recorded vulnerable coordinates. The components were resolved into build/plugin or Android test tooling.
* **Not confirmed:** Any advisory-specific vulnerable function was reached with attacker-controlled data in a Step 4B build, release, or instrumentation run.
* **Not an app-runtime finding:** The affected versions are not in the queried packaged runtime graph; the app's separate Bouncy Castle 1.86 is not affected by these listed version ranges.
* **Potential build risk:** Build plugins execute during compilation and tests with the build worker's privileges. A malicious or attacker-controlled artifact, XML, certificate, network peer, serialized object, compressed body, or protocol frame could change applicability. This audit did not establish those inputs or exploit paths; it also did not prove they are impossible.
* **Coverage caveat:** Exact UTP consumer configuration names and complete transitive edges for every plugin classloader were unavailable in the retained dependency report. The findings remain unresolved until the dependency paths and upstream fixes are verified against a candidate toolchain.

These are **upstream advisory fixes**, not approved Gradle overrides. Android's published build plugin may pin or test specific versions, and related artifacts must remain aligned (Netty modules; Bouncy Castle modules; protobuf artifacts). A forced transitive override can cause linkage errors, runtime test-tool failures, or unsupported AGP behavior even if the override version is individually patched.

No exact AGP/UTP version was validated in this read-only triage as containing all needed fixes. Therefore:

1. Prefer an Android-published AGP/tooling update whose published dependency metadata resolves the affected families to fixed versions.
2. Confirm its required Gradle wrapper and JDK using Google's AGP compatibility table before selecting it.
3. Confirm KGP and Compose plugin compatibility with that AGP/Gradle tuple; keep the Kotlin and matching Compose plugin versions aligned unless a documented compatibility requirement says otherwise.
4. Re-run dependency insight on plugin/build/test classpaths and rescan the actual resolved versions. Do not infer remediation from AGP's version number alone.
5. Do not force transitive versions or update app libraries as a substitute for updating the introducing build tool.

The current AGP 8.10.1 / Gradle 8.11.1 / Kotlin and Compose 2.4.21 / JBR 21.0.11 tuple has passed the Step 4B verification matrix. The project's current build reports that a future KGP 2.5.0 will require Gradle 8.14.4 or newer; that warning is not a reason to change the current wrapper in this triage. Any AGP update can change Gradle/JDK requirements, Android test orchestration, variant APIs, lint output, and plugin resolution. The change would require a separately authorized compatibility and regression assessment.

## 7. Build-environment mitigations

### Existing controls confirmed

* Plugin repositories are restricted to Google Maven, Maven Central, and Gradle Plugin Portal in [settings.gradle.kts](../../android/settings.gradle.kts); project dependency repositories are Google Maven and Maven Central, with `FAIL_ON_PROJECT_REPOS`.
* The Gradle 8.11.1 wrapper retains `distributionSha256Sum` and `validateDistributionUrl=true` in [gradle-wrapper.properties](../../android/gradle/wrapper/gradle-wrapper.properties).
* Strict checksum dependency verification is enabled by [verification-metadata.xml](../../android/gradle/verification-metadata.xml). It protects subsequent artifact resolution against byte changes relative to the reviewed checksums, but is not an independent proof of initial artifact authenticity.
* No remote build cache is configured. `org.gradle.caching` is not enabled in [gradle.properties](../../android/gradle.properties); the local Gradle artifact cache is distinct from the build-output cache. `--no-build-cache` disables use of the build cache, not necessarily Gradle's local dependency cache.
* The verified build uses a local JBR 21.0.11 installation; Gradle Java auto-download is disabled.
* Release testing used a disposable key. Production signing credentials were not accessed or stored in the Gradle project.

### Interim controls recommended pending owner decision

1. Run release builds only from a controlled, patched, single-purpose build host with pinned source and reviewed dependencies. Avoid building untrusted branches or arbitrary projects under a user's logged-in account.
2. Keep production signing credentials completely unavailable to Gradle workers. For Play distribution, keep the app-signing key in Play App Signing and use a separately controlled upload-signing step. For direct APK distribution, sign the verified artifact in a protected separate signing environment. Never place production key material in the repository, local developer environment, or general CI job.
3. Keep remote build caching disabled until a separately reviewed cache trust model exists. Continue strict dependency verification; do not turn off verification to unblock builds.
4. Treat the current checksum metadata as integrity pinning, not vulnerability remediation. A verified vulnerable JAR remains vulnerable.
5. Use disposable isolated build/test environments for dependency remediation experiments; do not expose release secrets or owner data.

These are mitigations, not a substitute for an upstream fixed toolchain. They reduce the consequence of a compromised build dependency but do not prevent vulnerable build code from executing.

## 8. Prioritized remediation and owner decisions

### Priority order

1. **High priority — owner decision:** authorize a separate, targeted AGP/Android test-tool remediation assessment. Preserve AGP/Kotlin/Gradle versions until that assessment identifies a vendor-supported combination with verified fixed transitive dependencies.
2. **High priority — protect signing boundary immediately:** retain the current rule that production credentials are not available to the Gradle build process. Do not produce or distribute a production-signed release from this unresolved graph without explicit owner risk acceptance and an isolated signing design.
3. **Next — validate all plugin graphs:** retain actual `dependencyInsight`/resolution evidence for AGP, plugin DSL, UTP, instrumentation, and runtime variants; record root configuration paths and exact resolved versions. Re-run OSV/GHSA against those exact coordinates.
4. **Next — regression-gate any authorized update:** compatibility review for AGP, Gradle, JBR, KGP, Compose plugin, and SDK; then JVM tests, lint, debug/release builds, release-target instrumentation on isolated API 31/API 37, APK manifest/signature/hash inspection, and dependency-verification metadata review.
5. **Do not** change application libraries, cryptographic algorithms, product behavior, repositories, signing configuration, or dependency verification exceptions as part of this triage.

### Decisions requiring owner approval

* Whether to authorize a targeted toolchain/Android testing-tool update assessment.
* Whether Milestone 1.12 can remain open until all Critical/High build-only version matches are resolved, or whether the owner will formally accept any residual match with documented mitigations.
* Whether to require exact plugin/UTP classpath path output as a release gate before remediation.
* Whether to require an isolated protected signing workflow before any production-signed build.
