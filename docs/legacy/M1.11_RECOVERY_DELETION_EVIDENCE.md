# Milestone 1.11 - Recovery and Deletion Reliability

**Status: OPEN for owner acceptance.** Step 3 implementation was authorized on 2026-11-01 after owner review of the baseline audit and Step 2 design. Milestone 1.10 remains owner-approved/closed; Milestone 1.12 is unstarted.

## Scope and protocol

External strict, checksummed operation intents are a persistence-protocol extension. Existing A2 profile bytes, schema-1/schema-2 data compatibility, manual backup archive format, vCard 3.0, and issued-share lifetime policy remain unchanged. No dependency upgrade is included.

Recovery independently validates a selected backup, rechecks its staged digest and unavailable-state context, and requires explicit confirmation in the existing restore sheet. A separate complete A2 candidate is verified before durable intent publication. The unavailable directory is preserved intact as private evidence; only the recorded candidate can replace it. Evidence is not an ordinary backup/export/display source and does not automatically expire. Storage exhaustion cannot justify deleting protected evidence.

Deletion keeps the existing row and popup. Before durable intent, failure leaves the readable profile unchanged. After durable intent, pending deletion blocks viewing, editing, exporting, recovery replacement, and new-profile creation. Retry/startup resumes that already-confirmed operation. Onboarding follows verified target absence and required synchronization.

Deletion is limited to active profile data/assets, associated recovery evidence, unissued owned staging, and applicable operation metadata. External backup files, recipient contacts, unrelated app-private data, and issued shares within their protected lifetime are excluded. Logical deletion is not secure physical erasure.

## Final operation transitions

All managed calls reconcile under the shared, reentrant root lock. Records publish as generated temporary file -> file sync -> atomic no-replace rename -> directory sync -> strict readback; they are never overwritten.

| Observed durable state | Transition / allowed outcome |
|---|---|
| No records | Require no orphan candidate/trash; ordinary A2 verification. Empty and unavailable remain distinct. |
| Delete intent | Recheck live fingerprint, atomically rename exact live directory to recorded trash, sync both parents, remove exact approved trash/evidence/generated backup stages, verify absence and sync, retire intent. Failure stays pending; replay never resurrects a confirmed deletion. |
| Recovery intent only | Preparatory state without durable confirmation: remove the owned candidate/intent, preserve live unchanged. |
| Matching recovery intent + confirmation | Preserve live under exact recorded evidence path; sync parents; atomically install exact verified candidate; sync parents; verify fingerprints, full replacement and confirmed token; clear obsolete path uncertainty; retire intent then confirmation. |
| Confirmation only | Verify the already-finished replacement/evidence state before retiring confirmation. |
| Retired records with unsynced removal | Re-sync operation directory before allowing ordinary operations. |
| Malformed/contradictory/orphan state | Block with no recovery token; preserve evidence and refuse destructive guesses. |
| I/O failure during confirmed replay | Pending delete/recover; block ordinary use and replacement; retry/startup resumes only that authorized operation. |

Recovery candidate construction precedes destructive replacement. Cancellation, validation failure, stale token, or staged-byte modification does not authorize a replacement. Save failure that makes A2 unavailable routes to the unavailable-profile choices instead of leaving a stale editor. The approved in-memory draft/prior-snapshot retention is preserved for ordinary save failure; unavailable gating prevents display, editing, or export, and reload clears that snapshot. Pending deletion clears profile projections.

## Failure-test interpretation

The JVM durable model commits file content only after file sync and directory entries only after directory sync; atomic rename commits when either parent is synced. `crash()` reverts volatile state. Deletion and recovery iterate each recorded operation boundary with before/after IOException and abrupt Error followed by crash and fresh repository; these are model guarantees, not proof of a physical filesystem's power-loss ordering. A real `java.nio` test verifies directory renames, and Android API 31/37 process-kill/reboot tests verify actual adapter behavior at the selected boundaries.

Best-effort legacy A2 cleanup faults are not counted as transaction failures. Separate-process concurrent writers and physical power-loss testing are not covered. The atomic adapter's no-replace check relies on the approved single-process root lock; no copy-and-delete fallback is used.

Expanded managed tests cover the complete restored snapshot (identity, portrait/cover/key bytes, hidden biography, visibility, normalized phone, GB region, country-code formatting flag, theme/accent); byte-for-byte evidence after model crash; zero-capacity candidate refusal and later retry; unavailable PENDING/torn/missing pointers/corrupt manifest/INIT/interrupted initialization/unknown entry; and two managed instances sharing a lock, including a two-thread same-revision race. The free-space model does not simulate decrementing capacity: mid-operation ENOSPC is represented only by generic injected IOException boundaries.

The initial missing-asset test was too permissive (accepted Ready or Unavailable). It was tightened and passed against the original coordinator: A2 pointer verification already checks all referenced asset blobs. Missing-all, missing-one, and corrupted-one asset cases now require Unavailable, a recovery token, exact preserved evidence, complete explicit recovery, and replay rejection. No additional double-reading asset check was necessary.

## Process-kill procedure

Do not run `OperationRestartTest` in an unattended all-tests invocation: selected methods intentionally call `Process.killProcess` and terminate instrumentation without teardown.

Invoke these host-selected phases in order:

1. `testSeedAndKillDuringSave`: seed disposable original/backup, then kill after actual pointer file sync during A2 save.
2. `testVerifySaveAndKillDuringConfirmedRecovery`: confirm unavailable state and recovery token, record original bytes, then kill after preservation of the unavailable live directory.
3. `testVerifyRecoveryAfterProcessDeath`: start a new process, reconcile, verify the complete replacement and exact preserved evidence bytes.
4. Reboot the isolated emulator and verify boot completion.
5. `testVerifyAfterEmulatorRebootAndKillDuringDeletion`: verify recovered profile after reboot, then kill after deletion within the durably recorded trash target.
6. `testVerifyDeletionReplayAndNoResurrection`: restart and verify deletion replay, repeated empty reads, absent profile/evidence, and preserved external fixture backup.
7. Reboot again; `testCleanVerifiedDisposableFixture` verifies no resurrection and removes only that test fixture.

Expected kill-phase instrumentation termination is not counted as a passing JUnit test. A phase marker and the next process's assertions establish the observed boundary/outcome. These checks are not proof of power-loss durability.

## Limits and remaining acceptance

- Persistent filesystem errors can leave an operation pending; retry does not promise completion while storage stays unavailable.
- Malformed/contradictory intents are blocked and preserved, not authorization to reset. Additional manual resolution UI is outside this approved scope.
- Retained evidence increases internal storage consumption. Future user-controlled evidence cleanup needs separate approval.
- Older APK versions do not understand pending intents. Downgrade safety is not claimed.
- Simulated synced/volatile state, injected I/O failures, abrupt simulated termination, real Android process kills, emulator reboots, and physical power loss must be reported separately.
- Physical power-loss behavior and physical-device filesystem behavior are not established by emulator/JVM tests.
- Actual Android/iPhone QR scanning and contact import compatibility, comprehensive TalkBack checks, and remaining Milestone 1.11 baseline compatibility gaps remain separate owner-acceptance work.
- No Version 2.0 multiple-card functionality or Milestone 1.12 work is included.
