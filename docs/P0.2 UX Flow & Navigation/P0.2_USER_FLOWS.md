# VCard Native — P0.2 User Flows

**Date:** 2026-10-29 · **Status:** APPROVED  
**Approval authority:** Project owner · **Approval date:** October 29, 2026 · **Milestone:** P0.2 APPROVED / COMPLETE.  
All interactions record approved UX direction within P0.1 scope, including Clarifications A and B; unresolved technical mechanisms are not approved. P0.3 and implementation are not authorized. Read with the [specification](P0.2_UX_FLOW_AND_NAVIGATION_DRAFT.md), [map](P0.2_NAVIGATION_MAP.md) and [decision register](P0.2_DECISION_REGISTER.md). Destination IDs and Back rules are shared across these documents.

## Shared flow contracts

Only saved data is presented/shared. Edits are drafts until explicit successful Save. Revalidate previews/artifacts after saved data changes; never include export-excluded fields in contact payloads. Required fields, formats and supported payload limits remain P0.4 decisions. External returns do not prove delivery. Each flow inherits the specification's keyboard, screen-reader, large-text and interrupted-operation behavior. Success below describes the intended eventual app behavior, not a tested result.

## F01 — First-time profile creation

**Entry:** Launch with no saved profile → N04 guided creation mode. **Decisions:** P0.2-03/P0.2-04.

1. User opens app; system presents the standard editor with concise setup guidance and no account flow.
2. User supplies identity/contact data, optional links/images/public key/hosted URL as desired; system marks applicable validation feedback using later approved rules. Required-field selection is not settled here.
3. User adjusts supported display/export controls independently; system explains that they do not govern hosted content.
4. User selects Save profile; system validates, retains errors/draft when invalid, otherwise persists one profile and opens N01.

**Success:** Saved profile appears on My Card and survives restart as required. **Cancel:** Clean Back exits; dirty Back opens D01; Discard exits with no profile created; Keep editing resumes. **Failure/recovery:** Failed save keeps entered values and offers retry. Photo-picker cancel changes nothing. Restore backup instead opens N06 (F10); returning without restore reopens creation. Interrupted creation follows F12; no persistent-draft guarantee is assumed.

## F02 — View and edit a saved profile

**Entry:** Launch → N01; Edit via N03 → N04, or from an S01 visibility correction link. **Decision:** P0.2-04.

1. User views N01; system renders saved display-enabled data and valid available actions.
2. User selects Profile then Edit Profile; system opens the one reusable editor with saved values copied into an editable draft.
3. User changes fields/links, public-key input or image selection (E03), and separately changes card/export switches.
4. User selects Save; system validates and persists before returning to the caller (normally N03; N02 after preview correction; N05 after its image link).
5. User returns to My Card or Share; system refreshes from saved data and invalidates stale exports.

**Success:** One updated profile; separate visibility settings retained. **Cancel:** Clean Up/Back returns; dirty departure opens D01. Discard leaves saved values intact; dialog dismissal keeps editing. **Failure/recovery:** Invalid input focuses the relevant field without clearing other entries. Missing image/file permission retains previous valid image and draft. Save failure keeps draft; retry is explicit. See F11/F12.

## F03 — Call, SMS, email and website actions

**Entry:** N01 with relevant valid, display-enabled saved field. **Decision:** P0.2-09.

1. User selects Call, Message, Email or a website/professional link.
2. System prepares the corresponding value and opens E04 dialer, E05 SMS composer, E06 email composer or E07 external browser.
3. User completes or cancels the action in that external activity and returns using Android navigation.
4. System restores N01 without altering profile data or claiming the call/message/visit succeeded.

**Success:** Requested external handler opens with the intended data; actual communication is controlled externally. **Cancel:** External Back returns to N01; no app confirmation is needed. **Failure/recovery:** Missing/hidden data produces no active action; missing handler produces a readable explanation and retry after configuration changes. Browser/network failure does not disable offline card/contact QR. No internal WebView is used.

## F04 — Display and share offline contact QR

**Entry:** N01 QR action or primary Share → N02. **Decisions:** P0.2-05/P0.2-06.

1. User enters Share; system selects Contact QR by default and immediately displays the offline QR when valid saved/export-enabled contact data can be encoded, without a blocking initial confirmation.
2. System shows a readable summary of included contact information. User may voluntarily open Review contact data → S01 before presenting the QR, then dismiss it to continue. Contact-export-excluded fields are never included; relevant saved-profile/visibility changes invalidate stale previews/artifacts before regeneration.
3. Recipient scans with a compatible device/scanner without installing VCard Native; recipient contact-save behavior is external.
4. To share the QR image, user selects Share contact QR; S01 is required and shows the actual supported data and action. User explicitly confirms Share contact QR before image generation/sharing.
5. System creates the reviewed QR image and opens E02 Sharesheet. Return restores contact mode.

**Success:** QR displayed or image handed to Android; no universal scan/import support is promised. **Cancel:** S01 dismissal performs no image export; Sharesheet dismissal returns without a delivery claim. Root Back goes to N01. **Failure/recovery:** Generation errors show no stale QR. Unsupported/oversized data offers export-selection editing or return, never silent truncation or automatic web mode. Actual limits await P0.4. No connectivity needed for generation; third-party delivery may depend on its chosen app.

## F05 — Optional web-profile QR and URL actions

**Entry:** N02; configured valid hosted URL required for active web mode. **Decisions:** P0.2-05/P0.2-09.

1. User selects Web-profile QR. With no valid URL, system explains the condition and offers Configure URL → N04; it does not show a fake code. Canceling edit returns to N02 in Contact mode.
2. With a valid URL, system displays a URL QR, destination address, recipient-internet label and hosted-content/local-visibility independence notice. No website fetch occurs.
3. User presents the QR, copies the profile URL or shares the URL through E02. Clipboard success is reported only after copying.
4. User can switch back to Contact QR explicitly; returning from E02 retains web mode, while a fresh root entry resets to Contact mode.

**Success:** Correct configured URL presented/copied/handed to Android; reachability and current site contents are not certified. **Cancel:** External dismissal or mode switching makes no profile changes. **Failure/recovery:** Invalid URL requires correction under future rules; stale but syntactically valid URL requires owner editing. If connectivity or browser fails, user can return to offline contact sharing. Local visibility never changes the website or revokes shared URLs. QR image actions follow F07.

## F06 — Preview and share a .vcf contact file

**Entry:** N02 → Share contact file → S01. **Decision:** P0.2-06.

1. User requests a contact file; system requires S01's .vcf-context preview and explicit action-specific confirmation before any .vcf generation or sharing.
2. User reviews actual supported included field values and any format-omission explanation. Export-hidden values are not included. User may choose Edit export selections → N04; saving returns to N02 and a fresh preview is required.
3. User confirms Create and share .vcf; system checks the saved snapshot still matches the preview, generates the contact-only file and opens E02.
4. User chooses an external target or dismisses it. System returns to N02 without asserting recipient import/delivery.

**Success:** Standard supported .vcf created and handed to Android; compatible recipient can import without VCard Native. **Cancel:** Preview dismissal creates no file/handoff; Sharesheet dismissal does not undo saved profile or imply delivery. **Failure/recovery:** Validation/generation failure stays with reviewable data and offers retry/edit; a changed snapshot requires re-review. No file import or full-app backup is implied. Encoding/mapping remains P0.4.

## F07 — Save or share a QR image

**Entry:** N02 with current valid Contact or Web-profile QR. **Decision:** P0.2-06.

1. User selects the mode-specific Save QR or Share QR action. Contact-image save/share actions require S01 and explicit action-specific confirmation before generating an image for export; web-image actions retain the visible URL/online notice.
2. Only after the required contact-action confirmation, system generates the contact image from the reviewed snapshot; web images use the selected URL mode. This gate does not delay initial on-screen contact QR display. A mode/data change invalidates the pending image.
3. For Save, system opens E01 create-document picker; user selects a location; system writes and reports success only after successful completion.
4. For Share, system opens E02; user chooses a target or cancels. Returning restores the prior Share mode and focus.

**Success:** Confirmed image saved to the chosen location, or handed to Sharesheet. **Cancel:** Contact preview/picker cancellation produces no successful-save message; external share cancellation claims no delivery. **Failure/recovery:** Write denial/full storage/unavailable provider offers retry or another destination. Local destinations support offline saving; cloud providers may need internet. Generation failure keeps data available for correction. A QR image is not a backup.

## F08 — Change appearance preferences

**Entry:** N03 → N05. **Decision:** P0.2-07.

1. User opens Appearance; system loads saved dark/light and curated accent choices.
2. User changes a supported choice; system previews the appearance draft, without finalizing colors/tokens here.
3. For profile/cover image changes, user chooses the N04 link; N04 remains the single image-editing location. If N05 is dirty, show existing D01 first: Keep editing/dismiss stays at N05 without navigation; Discard changes restores saved appearance, then opens N04. Explicitly saved appearance permits the link using saved values (ordinary Save returns to N03; reopen N05 for the link). No automatic save or new dialog is added.
4. User selects images through N04/E03; canceling selection preserves the existing saved image. Returning from N04 to N05 reloads current saved appearance and refreshed saved imagery.
5. For appearance changes themselves, user selects Save in N05; system persists approved choices and returns to N03. Card/share surfaces use saved appearance.

**Success:** Appearance preferences persist locally. **Cancel:** Clean Back returns; dirty Back opens D01; ordinary Discard restores saved appearance and returns to caller. For a pending image link, Discard instead restores saved appearance then opens N04; Keep editing/dismiss stays at N05 without navigating. **Failure/recovery:** Failed save retains choices for retry. No template/font/custom-color or extra animation-settings feature is added. Photo selection follows F02.

## F09 — Create a manual full-application backup

**Entry:** N03 → N06 → Create full application backup. **Decision:** P0.2-08.

1. System explains backup coverage (profile, images, appearance and visibility), its difference from .vcf and that it contains information hidden from contact sharing.
2. User chooses Create backup; system opens E01 create-document picker.
3. User selects a destination; system writes the complete supported application backup with progress and prevents duplicate activation.
4. System reports completion only after confirmed write and remains on N06.

**Success:** Full-app backup saved to a user-chosen location. **Cancel:** Picker cancellation returns to N06 without changing local data or claiming a backup. Before a write commits, Back cancellation is offered only if safe; otherwise announce finishing. **Failure/recovery:** Read/write/storage/provider errors explain failure, preserve local state and offer retry/different location. Partial-file handling and backup format are deferred; do not report a partial file as usable. Local-file backup remains offline; no automatic cloud sync or encryption promise is added.

## F10 — Restore a validated full-application backup

**Entry:** N03 → N06, or no-profile N04 → Restore backup → N06. **Decision:** P0.2-08.

1. User chooses Restore; E01 opens a file picker for an application backup, not existing-vCard import.
2. User selects input; system validates without changing saved data and shows progress. Unsupported/corrupt input is rejected before any confirmation.
3. On valid input, system opens S02 with a safe summary and replacement explanation. Exact metadata available awaits P0.4.
4. User confirms Replace local data and restore (or Restore profile if none exists); system performs a safe replacement with progress. During committed replacement, navigation is temporarily unavailable with an explanation.
5. After confirmed success, system refreshes profile, imagery, appearance and visibility together and opens N01. Earlier QR/previews/drafts cannot survive as if current.

**Success:** One restored saved profile and associated settings/images; no merge or second profile. **Cancel:** File-picker cancellation returns to N06; validation Back cancels only when safe; S02 dismissal/Cancel leaves data unchanged. N06 Back returns to the actual caller, including first-run N04. **Failure/recovery:** Invalid input offers another file. Failed/interrupted restore preserves prior valid data; recovery must determine the actual state before reporting success or permitting retry. P0.4/P0.5 specify the safety mechanism. No undo, automatic backup or technical integrity format is selected here.

## F11 — Invalid inputs and unavailable external applications

**Entry:** N04/N05 Save, N02 generation, N01 action or external file operation.

1. User attempts an action; system checks applicable input/capability conditions and identifies the affected field/operation.
2. For invalid editor input, system keeps all entries, shows an associated error, focuses the first failure and explains correction without invented validation thresholds.
3. For unavailable external handlers, system remains/returns to the invoking destination with a readable explanation; it does not repeatedly launch a failing handler.
4. User corrects input, changes file location or configures an external handler, then retries explicitly; system rechecks before continuing the original flow.

**Success:** User can complete the corrected action or leave with saved data intact. **Cancel:** Dismiss transient feedback/Back to caller; dirty edits still use D01. **Failure/recovery:** Persistent errors leave a correction/return path, not a dead end or blank QR. Essential unsupported contact fields and oversize handling await P0.4; app never silently includes export-hidden data to make generation succeed. Public-key rejection follows F14.

## F12 — Interrupted edits, external handoffs and writes

**Entry:** Any flow interrupted by app backgrounding, process termination, device restart or external activity return. **Decision:** P0.2-12.

1. User backgrounds the app or the system interrupts an operation; system must not treat departure itself as Save/Share success.
2. On ordinary external return, restore the caller and retained draft/mode where possible; revalidate saved snapshot and external-operation result.
3. After restart, load confirmed saved state; resume normal My Card or no-profile creation as applicable. Recover transient drafts only according to later approved technical behavior.
4. If completion is unknown, explain uncertainty and reconcile state before offering retry; do not automatically relaunch Sharesheet, repeat a write or replace data again.

**Success:** Honest status, usable saved state and a deliberate recovery path; previously saved data survives restart. **Cancel:** User may leave idle recovered destinations using normal Back; any extant dirty draft uses D01. **Failure/recovery:** Unrecoverable uncommitted edits must not be described as saved. Interrupted restore must preserve/recover valid data under FR-06; implementation guarantees and draft persistence remain P0.5 dependencies. No persistent draft or operation-history product feature is assumed.

## F13 — Review and change display/export visibility

**Entry:** N03 → N04, or N02 → S01 → Edit export selections. **Decisions:** P0.2-04/P0.2-06.

1. User opens a supported field's visibility controls; system labels card display and contact export separately, using P0.4's later field-support/default policy.
2. User changes one control; system retains the other independently and explains that hosted web content is unaffected.
3. User saves; system refreshes the card and invalidates old contact previews/QR/files. When entry came from S01, return to N02 and require fresh review for an export.
4. N02 immediately displays a newly valid contact QR with its readable included-data summary; S01 review before presentation is voluntary. For .vcf generation/sharing or contact QR image save/share, S01 and explicit action-specific confirmation remain mandatory (F04/F06/F07). Export-excluded fields remain absent.

**Success:** Saved card and contact payloads follow their distinct settings; export-excluded data is absent from contact QR/.vcf. **Cancel:** D01 protects dirty changes; discard retains prior rules. **Failure/recovery:** Save failure retains draft; unsupported format fields are explained and never silently promised. No switch controls hosted visibility or revokes already shared copies.

## F14 — Optional public-key input and download

**Entry:** N04 public-key section for configuration; N01 for conditional download. **Decision:** P0.2-11.

1. User provides a public key via a supported input mechanism; system validates before accepting it as a draft value. File/input mechanism and accepted formats are unresolved P0.4/P0.5 dependencies.
2. User saves N04; system retains a valid user-provided public key with the profile. No private-key export is possible.
3. Where valid and display-enabled, N01 offers Download public key. The approved UX direction uses an Android save destination (E01) for local public-key export; exact technical mechanics still await P0.4/P0.5 specification and later approval.
4. User chooses a destination; system saves only the validated public key and confirms only a completed write.

**Success:** Optional public key is saved/displayed/downloadable under later approved format rules. **Cancel:** Input/destination picker cancel retains prior valid key; dirty editor departure uses D01. **Failure/recovery:** Reject unsupported/invalid/private-key input for this capability, retain prior valid key and offer correction. Missing/invalid/hidden key produces no download control. Whether/how a public key maps to contact formats remains P0.4; do not assume inclusion. This is a defined UX path with unresolved technical details, not a completed key-format specification.

## F15 — Root navigation, sheets and unsaved-change guard

**Entry:** Any internal destination. **Decisions:** P0.2-01/P0.2-10.

1. User selects a primary label; system shows N01/N02/N03 without stacking tab history; fresh Share entry selects Contact QR.
2. User opens secondary N04/N05/N06; system records its caller and provides Up. Primary bar is not an alternative exit from a dirty editor.
3. Back closes the keyboard first where applicable, then closes a sheet or returns from a clean secondary screen. Dirty N04/N05 departure opens D01.
4. Keep editing or dialog dismissal resumes the draft; ordinary Discard returns to caller. For N05's pending image link, Keep editing/dismiss stays at N05 and Discard restores saved appearance then opens N04, returning later to refreshed N05 (F08). Back at N02/N03 selects N01; Back at N01 exits using system behavior.

**Success:** Predictable caller return without duplicate destinations or unexpected data loss. **Cancel:** Dismissing S01 performs no export; dismissing S02 performs no restore; dismissing D01 keeps edits. **Failure/recovery:** If saved-profile state becomes unavailable, explain and enter no-profile N04 instead of presenting stale card/export content. Busy restore follows F10; no unguarded exit from a committed replacement is promised.
