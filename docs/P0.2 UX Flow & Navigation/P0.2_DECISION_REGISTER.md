## P0.2-01 — Primary navigation

- **Description:** How to reach the card, sharing and profile maintenance.
- **Approved choice:** Three labeled roots: My Card, Share, Profile; QR entry selects Share rather than pushing a duplicate.
- **Historical alternatives (not selected):** Two roots with Share secondary from My Card; one card root with a menu for all tools.
- **Advantages:** Common presentation/sharing remains directly reachable and navigation remains shallow.
- **Disadvantages:** Three persistent choices use more space than two; Profile must remain useful without duplicating My Card.
- **Requirement relationship:** PRD sections 4/8; FR-01/FR-04; P0.1-01/P0.1-04.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N01–N03, F04/F15.

## P0.2-02 — Secondary destinations and maintenance grouping

- **Description:** Whether to introduce standalone Settings and preview screens.
- **Approved choice:** Profile management hub → Edit Profile, Appearance, Backup & Restore; no separate Settings. Contact Export Preview and Restore Review are sheets. Six navigable screens total.
- **Historical alternatives (not selected):** Settings hub containing Appearance and Backup; full-screen preview instead of a sheet if readability demands it.
- **Advantages:** Avoids redundant settings/menu layers and preserves context for short review tasks.
- **Disadvantages:** Long export/restore content needs careful scrolling and large-text treatment; a full-screen preview could be clearer on constrained displays.
- **Requirement relationship:** PRD section 8 is provisional; FR-02/FR-03/FR-05/FR-06. P0.1-05/P0.1-07/P0.1-10.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N03–N06, S01/S02, F06/F08–F10.

## P0.2-03 — First-run routing

- **Description:** Create the one profile without separate onboarding.
- **Approved choice:** Open reusable N04 in guided creation mode; successful save opens My Card. Offer a small Restore backup entry to N06. Primary roots become available after creation/restore. Clean Back exits; dirty Back uses D01.
- **Historical alternatives (not selected):** Empty My Card with Create profile/Restore actions; omit first-run restore shortcut and expose it after initial creation.
- **Advantages:** Direct creation, no duplicate setup UI; existing backup can restore without creating a temporary profile.
- **Disadvantages:** Users cannot explore normal roots before saving; restore entry adds a secondary action to setup.
- **Requirement relationship:** FR-02/FR-06; P0.1-02/P0.1-07/P0.1-12. Required fields remain P0.4.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N04/N06, F01/F10/F15.

## P0.2-04 — Draft editing, visibility and loss guard

- **Description:** Save semantics and independent privacy controls.
- **Approved choice:** Explicit Save; one editor with separate Show on card / Include in contact export controls where supported. Dirty departure offers Keep editing / Discard changes. Primary navigation is not available as an unguarded secondary-editor exit.
- **Historical alternatives (not selected):** Save-and-leave as a third dialog action; different grouping of supported visibility controls. Independent controls themselves are required and are not optional alternatives.
- **Advantages:** Clear saved-state boundary; simple two-action loss guard; no accidental sharing of draft edits.
- **Disadvantages:** Requires explicit Save and can add a confirmation when leaving a dirty editor. Defaults, essential fields and format support cannot be finalized yet.
- **Requirement relationship:** FR-02/FR-03; P0.1-02/P0.1-05/P0.1-12. P0.4 defines validation/defaults; P0.5 specifies transient recovery.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N04/D01, F01/F02/F13.

## P0.2-05 — QR mode default, return and URL availability

- **Description:** Keep offline contact sharing primary while distinguishing optional online content.
- **Approved choice:** Every fresh Share entry uses Contact QR. External/sheet return preserves current mode. Web-profile QR requires a valid configured URL and shows destination/online/hosted-independence notices; missing URL offers an editor link without an active fake mode. Configure URL returns to Contact mode.
- **Historical alternatives (not selected):** Keep mode only during an uninterrupted Share session but reset also on external return; show a disabled web option with inline guidance instead of a selectable explanation. A persistent web default is inconsistent with the approved contact default and is not proposed.
- **Advantages:** Reliable offline default and reduced confusion between local and hosted information.
- **Disadvantages:** Users preferring the website must select it after each fresh root entry; repeated notices require concise design.
- **Requirement relationship:** FR-03/FR-04; P0.1-04/P0.1-05/P0.1-07. URL validity rules remain P0.4; no reachability checking feature.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N02/N04, F04/F05/F07.

## P0.2-06 — Contact export preview placement and confirmation

- **Description:** Balance quick QR presentation with informed contact disclosure.
- **Approved choice:** Clarification A: Contact QR remains the default and displays immediately when valid saved/export-enabled contact data can be encoded, with a readable included-data summary and voluntary S01 review before presentation. No blocking initial confirmation. Require S01 and explicit action-specific confirmation before generating/sharing a .vcf or saving/sharing a contact QR image. Never include export-excluded fields; invalidate stale QR previews/artifacts after relevant saved-profile or visibility changes. Confirm only the reviewed current saved-data snapshot. Web mode retains its separate URL disclosure and hosted-content independence. Mapping, encoding, limits and visibility defaults remain P0.4.
- **Historical alternatives (not selected):** Require S01 confirmation before first QR reveal on each Share entry; use a full-screen preview instead of a sheet. Export-excluded fields must remain excluded under every option.
- **Advantages:** Presentation is fast; file/image export is deliberate and reviewable. Accessible text accompanies QR content.
- **Disadvantages:** Direct QR display exposes included data before an extra confirmation; stricter first-reveal gating offers greater deliberation at the cost of taps. The owner accepted direct display with Clarification A's safeguards; first-reveal gating remains an unselected historical alternative.
- **Requirement relationship:** FR-03/FR-04; P0.1-04/P0.1-05. Field mapping and payload limits remain P0.4; this approval selects no encoding rule.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N02/S01, F04/F06/F07/F13.

## P0.2-07 — Appearance and image-editing entry

- **Description:** Avoid duplicating photo editors while making curated styling easy to find.
- **Approved choice:** Clarification B: N05 has a preview and explicit Save for dark/light and curated accents; N04 remains the single profile/cover image-editing location. A dirty N05 image link first opens existing D01: Keep editing/dismiss stays at N05 without navigation; Discard restores previously saved appearance then opens N04. Explicitly saved appearance permits navigation using saved values. Ordinary Save still returns to N03; reopen N05 to use its image link. Return from N04 refreshes current saved appearance and imagery. Canceling image selection does not replace an existing saved image. No second editor, automatic save or new dialog.
- **Historical alternatives (not selected):** Place appearance sections in N04; select photos directly from Appearance instead of linking, while still sharing one editing contract.
- **Advantages:** Clear separation of identity edits and styling; consistent save/cancel handling and one image-editing location.
- **Disadvantages:** Photo changes from Appearance take an extra transition; explicit Save adds a step compared with immediate settings persistence.
- **Requirement relationship:** FR-01/FR-05/FR-06; P0.1-03/P0.1-06/P0.1-07. P0.3 retains tokens/layout and curated values.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N04/N05/D01, F02/F08.

## P0.2-08 — Manual backup and restoration confirmation

- **Description:** Select files, explain full-app scope and prevent unintended replacement.
- **Approved choice:** N06 uses user-chosen Android file locations; validate restore first, then S02 replacement review. No merge; successful restore returns to My Card. Temporarily prevent navigation during committed replacement with accessible progress; cancellation before commit makes no changes.
- **Historical alternatives (not selected):** Full-screen restore review; an explicit confirm dialog instead of a review sheet. Automatic pre-restore backups/undo are outside the approved UX scope.
- **Advantages:** One clear replacement boundary; invalid input cannot reach confirmation; backup remains distinct from .vcf.
- **Disadvantages:** A committed restore briefly limits navigation; interruption safety and trustworthy summaries depend on later technical/format work.
- **Requirement relationship:** FR-06; P0.1-02/P0.1-07/P0.1-11. Backup format is P0.4; safe commit/recovery is P0.5; verification is P0.6.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N06/S02/E01, F09/F10/F12.

## P0.2-09 — Native external handoffs

- **Description:** Launch contact actions and exported artifacts without pretending to control recipient apps.
- **Approved choice:** Dialer prefill (user initiates call), SMS/email composers, external browser, Android Sharesheet, photo picker and file pickers. Copy hosted URL is inline. Return to caller and never equate return with successful delivery.
- **Historical alternatives (not selected):** Different working labels/placement for call versus SMS actions; system-supported handler selection. An internal WebView and automatic calls/messages are not proposed.
- **Advantages:** Familiar native handling, fewer permissions where feasible, graceful separation of local actions and external completion.
- **Disadvantages:** Handler availability varies; chosen providers/communication apps may require connectivity.
- **Requirement relationship:** FR-01/FR-04/FR-06; P0.1-03/P0.1-04/P0.1-07/P0.1-11. Exact integrations and permission choices remain P0.5.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** E01–E07, F03/F05–F07/F09/F14.

## P0.2-10 — Root Back and transient-surface behavior

- **Description:** Make Back consistent without growing a tab history.
- **Approved choice:** Back from Share/Profile returns to My Card; Back at My Card exits. Secondary screens return to recorded caller, sheets dismiss without action, D01 dismissal keeps edits. For N05's pending image link, Discard restores saved appearance then opens N04 and Keep editing/dismiss stays at N05 (Clarification B). Keyboard Back dismisses keyboard before editor departure. No general exit confirmation.
- **Historical alternatives (not selected):** Each primary root independently exits on Back; maintain recent primary selections as history.
- **Advantages:** Predictable home destination and no confusing repeated tab traversal.
- **Disadvantages:** Users accustomed to immediate exit from a root may need an additional Back; caller context must be handled consistently.
- **Requirement relationship:** PRD section 9 navigation/confirmation clarification; FR-02/FR-03/FR-06; P0.1-05/P0.1-11/P0.1-12.
- **Owner approval:** Granted by project owner on 2026-10-29. **Status:** APPROVED. **Affected:** N01–N06/S01/S02/D01, F15.

## P0.2-11 — Optional public-key interaction

- **Description:** Expose the already-approved public-key capability without inventing a format or networking feature.
- **Approved choice:** N04 input/validation and N01 conditional public-key-only download; recommend an Android save destination. Hide unavailable/invalid/display-hidden key actions. No standalone key screen.
- **Historical alternatives (not selected):** Place the download action in a card details sheet; settle input/download mechanism after P0.4/P0.5 instead of committing to a save-picker route.
- **Advantages:** Covers an often-overlooked approved capability while preserving public/private-key boundaries.
- **Disadvantages:** Input types, validity checks, export mapping and mechanics are unresolved, so the UX remains partially dependent on later planning.
- **Requirement relationship:** FR-01/FR-03 and PRD section 9 item 2; P0.1-03/P0.1-05/P0.1-11. No private-key export or key-generation feature is added.
- **Owner approval:** Granted by project owner on 2026-10-29 for UX direction; later specifications remain unresolved. **Status:** APPROVED. **Affected:** N04/N01/E01, F14.

## P0.2-12 — Interrupted operations and draft expectations

- **Description:** Distinguish saved persistence from uncommitted edits and uncertain external outcomes.
- **Approved choice:** Preserve draft/context across ordinary backgrounding where feasible; on restart load confirmed saved data and explain unrecovered work/uncertain outcomes honestly. Reconcile writes/restores before retry; never auto-repeat external handoffs. Do not promise persistent drafts as a new feature.
- **Historical alternatives (not selected):** Restore editor drafts across process death if later architecture supports it; return to saved state with an explicit loss notice when recovery is unavailable. Exact behavior requires P0.5 feasibility review.
- **Advantages:** Honest feedback and fewer duplicate operations; saved-data persistence and failed-restore safety remain binding.
- **Disadvantages:** Exact interruption UX is not fully settled until recovery capabilities are specified; uncommitted edits may be unrecoverable.
- **Requirement relationship:** FR-02/FR-06; P0.1-07/P0.1-11/P0.1-12. P0.5 specifies mechanism; P0.6 specifies verification.
- **Owner approval:** Granted by project owner on 2026-10-29 for UX direction; unresolved technical behavior must return for later planning review. **Status:** APPROVED. **Affected:** F02/F09/F10/F12 and all external returns.
