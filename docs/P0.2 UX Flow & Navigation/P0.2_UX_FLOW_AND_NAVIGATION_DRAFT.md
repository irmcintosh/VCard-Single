## 2. UX objectives and principles

Make the saved professional card and offline sharing easy to reach. Use native Android interactions and familiar Material 3 navigation, sheets, dialogs and system handoffs as approved interaction direction. Final components and layout belong to P0.3; libraries belong to P0.5.

Maintain one profile, a clear distinction between draft edits and saved data, and separate display/export visibility. Describe what is shared before handing data to another application. Explain that locally hidden fields do not alter the hosted website or revoke earlier exports. Avoid account creation, lengthy onboarding and controls for excluded functionality.

Keep core card viewing, editing, contact QR, .vcf creation and local-file backup/restore usable offline. Label actions that depend on external handlers or connectivity without treating absence of connectivity as loss of the local profile. Use inline validation and actionable feedback; require action-specific contact export confirmation, and use loss/replacement confirmations for unsaved changes or replacing saved state. Initial contact QR display has no blocking confirmation.

## 3. Approved primary navigation

The approved structure has three labeled primary destinations: **My Card**, **Share**, **Profile**. My Card is the saved-profile launch destination. A QR action on My Card selects the existing Share root; it does not push a duplicate Share screen. Profile is a compact management hub with Edit Profile, Appearance and Backup & Restore entry rows, not a second rendered business card.

Use a familiar three-item navigation bar for the primary roots; exact responsive placement is P0.3 work. Secondary screens provide an Up action. Primary navigation is not offered as an escape from dirty secondary editors; system Back and Up use the same loss guard. Root switching does not accumulate a history of tab selections. The count is **six navigable screens: three primary and three secondary**, plus **two bottom sheets and one reusable dialog**. QR modes, empty states, progress and first-run editor mode are states, not extra destinations.

Historical alternatives evaluated: two roots (My Card and Profile with Share pushed from My Card) reduce persistent navigation but make sharing less direct; separate Settings as a fourth root fragments infrequent maintenance. The approved three-root structure prioritizes common presentation/sharing tasks. A standalone Settings screen and a separate Backup hub are unnecessary; Backup & Restore is itself the maintenance screen. See P0.2-01/P0.2-02.

## 5. First launch and profile presence

If no saved profile exists, launch N04 in guided creation mode using the same editor used later. Explain that data is stored locally, provide concise field guidance and Save profile, and offer an unobtrusive Restore backup link to N06. Do not create sample contacts or add a separate onboarding/account flow. Required fields, accepted values and maximum lengths remain P0.4 dependencies; do not label an invented field set mandatory.

Save validates according to the future approved rules, writes one profile and opens N01 after confirmed success. Failures retain the editor contents. Back from clean first-run exits the activity; Back from dirty first-run opens D01. Discard then exits without creating a profile. Subsequent launch without a saved profile opens the same editor. Returning from first-run recovery without restoring returns to N04. Successful restoration opens N01. Normal primary roots become available after a profile exists. See F01/F10 and P0.2-03.

## 6. My Card and contact actions

N01 renders saved fields allowed for card display. Hide absent/hidden optional content and corresponding actions; do not substitute fake buttons. Include full name, professional title, organization, biography, location, phone, email, website, professional/social links and imagery as applicable. Show call/SMS/email/web actions only when their saved field is valid, present and display-enabled. Open the dialer with the number prefilled, a messaging/email composer, or an external browser. The owner completes the external action; return from another app never proves a call/message succeeded.

When an external handler is unavailable, keep the user at N01 with a specific explanation; allow retry after the device configuration changes. Do not silently expose a hidden field through an action. Missing image content degrades to the text card. The optional public-key download action appears only for a valid saved public key permitted for display; format, validation and download mechanics remain deferred (F14).

## 7. Editing, visibility and unsaved changes

N04 edits a draft of the one saved profile. Group identity, contact details, professional links, imagery, hosted profile URL and optional public key using readable sections; this grouping does not add fields. Provide separately named **Show on card** and **Include in contact export** controls for supported fields, never a single combined visibility switch. Support/default/essential-field policy is P0.4, so this specification does not assign default values or override non-hideable identity decisions. Explain supported format exclusions without implying every field fits in contact QR or .vcf.

N04 is the sole image-editing location; N05 links to it. Selection opens the Android photo picker; cancel preserves prior selection. A selected image remains a draft until Save; no cropping/editor feature is added. Public-key input is conditional on supported file/input handling to be specified later; private-key material must not be accepted for the public-key capability.

Save validates, shows field-associated errors and focuses the first failing field; retain all other edits. After successful persistence, return to the recorded caller (normally N03; N05 after its image link; N02 after Share correction); first creation instead opens N01. Clean Back/Up returns to the caller. Dirty Back/Up opens D01. Keep editing returns to the draft; Discard returns to the caller with saved data unchanged. Dismissing D01 means Keep editing. There is no autosave-to-profile or extra Save-and-leave dialog button.

Switching outside the app does not discard the draft. Exact restoration of transient draft state across process death is an unresolved P0.5 dependency, not a promise of a new persistent draft feature. Saved state must survive process/device restart. On interruption, report a loss of uncommitted work honestly if it could not be recovered; never report an unsuccessful save as complete. See F02/F12 and P0.2-04/P0.2-12.

## 8. Share modes and export privacy

Every fresh entry from another primary root or cold launch opens N02 in **Contact QR — works offline** mode. Returning from a sheet or external activity retains the current mode and scroll/focus where still valid. Switching to the other root and back resets to Contact QR; mode selection is not a saved default.

Clarification A: Contact mode immediately displays the offline QR when valid saved/export-enabled contact data can be encoded, with a readable summary of the included contact information. Review contact data opens S01 voluntarily before the user presents the QR; there is no blocking confirmation before initial QR display. Never include contact-export-excluded fields. Relevant saved-profile or visibility changes invalidate stale QR previews and artifacts; regenerate from current saved data before another presentation or operation. Field mapping, vCard encoding, QR payload limits and visibility defaults remain P0.4 responsibilities.

S01 and explicit action-specific confirmation are mandatory before generating/sharing a .vcf or saving/sharing a contact QR image; opening S01 before presenting the immediately displayed QR is voluntary. It identifies the chosen action, lists actual included values, identifies unsupported/omitted fields without including export-hidden values, and offers a link to edit visibility. This link dismisses the sheet and opens N04; saving returns to Share and requires a fresh preview for an export action. Preview confirmation uses the exact reviewed saved-data snapshot; if it changes, refresh and request review again. Do not generate an export file before confirmation. Payload mapping/limits are not selected here.

Web mode is clearly named **Web-profile QR — recipient needs internet**. Offer it only with a valid configured hosted URL; otherwise show a configuration explanation/link to N04 without a fake QR or active web-sharing controls. Show the destination URL and the notice that the hosted page is independent of local visibility settings and previously shared data cannot be revoked locally. Do not fetch the website or synchronize it. A URL can be valid in syntax but stale/unreachable; the app cannot certify current hosted content. Contact mode remains available without network access.

## 9. Contact file preview and sharing

N02 Share contact file requires S01 in .vcf context before generation or sharing. Only explicit action-specific confirmation of **Create and share .vcf** generates the supported standard contact file and opens Android Sharesheet (E02). A generation failure retains the preview and supports retry; closing Sharesheet returns to N02 without a “contact delivered” claim. No recipient installation of VCard Native is required. The file is contact-only and is never described as an application backup. No existing-vCard profile import is offered. See F06 and P0.2-06.

## 10. QR image saving, sharing and web links

In contact mode, Save QR / Share QR requires S01 and explicit confirmation of the matching action before generating an image for saving or sharing. Initial on-screen contact QR display remains immediate and requires no blocking confirmation. In web mode, use the visibly selected URL mode with its independence/online notice; never present web-image sharing as a contact-field privacy export. Labels distinguish **Save contact QR** from **Save web-profile QR**, and equivalent share actions.

Save uses an Android create-document/location picker (E01) and confirms success only after a successful write. A user-selected cloud provider may require connectivity; local-device destinations must support offline core use. Share opens E02 and reports only that control passed to Android. Returning from either retains mode. No destination chosen means no success. In web mode, Copy profile URL confirms clipboard placement only after success; Share profile URL opens E02. A QR image is not an editable profile backup. See F04/F05/F07.

## 11. Appearance

N03 opens N05. Offer only approved dark/light choices and curated accents, with a local appearance preview and explicit Save. Changes remain an appearance draft until saved; failed save retains choices, dirty Back/Up uses D01. Display follows saved appearance after discard.

Clarification B: N04 remains the single location for selecting/editing profile and cover images. If N05 has unsaved appearance changes when its Change profile/cover images link is selected, show existing D01 first. Keep editing (or dialog dismissal) stays at N05 without navigating. Discard changes restores the previously saved appearance, then proceeds to N04. If appearance changes were explicitly saved first, the image link may proceed using saved appearance. Ordinary N05 Save still returns to N03; reopening N05 for the link uses saved values. Returning from N04 to N05 displays the current saved appearance and refreshed saved imagery. Canceling image selection does not replace the existing saved image. There is no second image editor, automatic appearance save or new confirmation dialog.

No templates, arbitrary fonts, color editor or new animation controls are introduced. Exact tokens, rendering, motion and layout remain P0.3 work. See F08/P0.2-07.

## 12. Manual full-app backup and safe restoration

N06 explains the difference between **Full application backup** (profile, images, appearance and visibility) and .vcf contact sharing. Create backup selects a user-chosen destination via E01, writes the supported backup and shows completion only after success. A failed/cancelled write does not alter app state; partial-output cleanup is a later technical concern. Do not imply encryption, cloud sync or backup history features. A backup contains local application information, including fields hidden from sharing; the user controls the saved file.

Restore selects an application backup with E01, then shows validation progress. Invalid, corrupt or unsupported input is rejected with existing state unchanged. Only successfully validated input opens S02. Explain replacement of the one saved profile, imagery and settings; do not add merge/multiple-profile choices. Show only a safe summary supported by later backup metadata, without assuming a schema. Cancel or Back before confirmation changes nothing. Confirm **Replace local data and restore** (or **Restore profile** when no profile exists) performs restoration with explicit progress. After confirmed success, refresh all roots and open N01. Failure preserves valid prior state and offers retry/select another file; never claim recovery until state is confirmed.

Prevent navigation/dismissal during the short committed replacement stage, with an accessible explanation. Before commit, Back may cancel validation/review when safe. This does not replace the requirement to survive interruption without destroying valid data; transactional behavior and process-death recovery are P0.5 work informed by P0.4. No automatic pre-restore backup or undo feature is added. See F09/F10/P0.2-08.

## 13. State and feedback rules

| State | Approved interaction and recovery |
|---|---|
| No profile | Guided N04, optional restore entry; no placeholder contact or empty share artifacts |
| Missing optional data | Hide irrelevant card actions; explain unavailable web mode and offer configuration; no fake public-key button |
| Loading saved state / generating artifact | Labeled progress on current destination; suppress repeated action; do not show stale QR as current |
| Field validation failure | Inline error with field label and correction guidance; focus first error, preserve draft; no invented rule thresholds |
| Insufficient/oversized contact payload | Explain generation unavailable under later P0.4 rules; offer editing export selections or return; no silent truncation or automatic switch to web QR |
| Save/backup/image write success | Announce actual completed local action; do not infer recipient delivery or successful import |
| External action unavailable | Explain missing handler, return to caller, preserve saved/draft state; permit retry |
| File read/write denied, unavailable destination or full storage | Explain affected operation; retry or choose another location; retain valid saved state |
| Invalid backup or public-key input | Reject safely; keep prior valid data; format policy remains deferred |
| Interrupted action | Reconcile known saved state on return; show uncertainty if completion cannot be confirmed; never blindly repeat a handoff/write |
| Online destination unavailable | Explain external browser/connectivity issue when known; keep offline contact sharing available; no network monitoring feature |

Use brief status announcements for nonblocking success; keep errors and retry actions available long enough to read. Exact copy and components are P0.3 work. No separate error/success screen is added.

## 14. Android Back and cancellation contract

| Context | Back / Up / dismissal result |
|---|---|
| Software keyboard visible in editor | Back first dismisses keyboard; later Back follows editor guard; explicit Up follows guard directly |
| N02 or N03 primary root | Back selects N01; primary tabs are not a chronological stack |
| N01 primary root | Back exits/finishes activity using system behavior; no exit confirmation |
| N04/N05 clean | Return to actual caller, not always N03; first-run editor exits |
| N04/N05 dirty | D01; dismiss/Keep editing retains draft; ordinary Discard returns/exits. For N05's pending image link, Discard restores saved appearance then opens N04; Keep editing stays at N05 |
| N06 idle | Return to N03 or first-run N04 according to entry |
| S01 preview | Back/swipe/dismiss closes sheet to invoking N02; no artifact action |
| S02 restore review | Back/swipe/dismiss closes review to N06; no replacement |
| Validation/generation before commit | Cancel safely if supported; otherwise briefly show finishing state without claiming cancellation; technical feasibility deferred |
| Restore committed replacement | Navigation temporarily unavailable with progress explanation; system interruption still requires safe recovery |
| External Android activity | System manages Back; returning restores caller and revalidates pending data/action state; no presumed delivery |

Primary reselection does not reset drafts or scroll unexpectedly; N02 mode resets only on a fresh root entry, not reselection. Runtime loss of a saved profile returns to the no-profile state after explaining the situation; no blank card is shared.

## 15. Accessibility and large text

Provide text labels for primary navigation and action purpose, selected-mode announcements, headings for long forms and independent names/states for visibility controls. Read order follows the information and actions. QR content must have a textual included-data alternative and contact-file sharing path; screen-reader users need not interpret the QR bitmap.

Support large system text by scrolling forms/sheets and allowing action labels to wrap. Keep Save, preview confirmation and cancellation reachable without clipped fixed-height content. Sheet content may expand within the available viewport and scroll; no new screen is implied. Dialog focus starts on descriptive content and returns to its invoking control. Associate errors with fields and announce progress/completion without repeated focus jumps. Do not rely on color alone for mode, validity or success. Maintain the PRD's readable contrast, generally >=48 dp touch targets and essential screen-reader flows; P0.3 specifies layout/tokens and P0.6 verifies them. Support native system gestures; detailed implementation belongs to P0.5.
