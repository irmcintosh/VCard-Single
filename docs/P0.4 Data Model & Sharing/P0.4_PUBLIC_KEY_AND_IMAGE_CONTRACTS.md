## 1. Conditionally approved bounded modern OpenPGP compatibility

The owner selected modern OpenPGP compatibility for v1.0, subject to safe, maintainable feasibility. The matrix below supersedes the earlier v4 RSA-only draft restriction. Every intended-support row is **REQUIRES FEASIBILITY VALIDATION** on Android with a maintained parser/verifier; no row is implemented or experimentally proven. The owner approved the bounded matrix conditionally: any reduction requires explicit project-owner approval before implementation. P0.5 must evaluate maintained Android-suitable parser/verifier candidates, licensing, resource bounds, version support, cryptographic validation and revocation handling. P0.6 must verify the supported algorithms, fingerprints, signatures, bindings, public-only input, expired/revoked behavior and unsupported-format rejection. No custom cryptographic parser or unverified compatibility claim is authorized. If safe implementation is infeasible, document and escalate the limitation rather than silently removing support or weakening validation.

Accept one ASCII-armored transferable public certificate with a single primary key, bounded public subkeys and a supported encryption-capable primary/subkey. A signing primary authenticates the certificate; it need not itself encrypt. Algorithm IDs follow the [IANA OpenPGP registry](https://www.iana.org/assignments/openpgp). The matrix is this application's bounded target, not an assertion that all other standard combinations are invalid.

| Key version | Conditionally approved signing/certification primary | Conditionally approved encryption material | Status / boundary |
|---|---|---|---|
| v4 | RSA (1), 3,072-8,192 bits | RSA (1) primary or bound subkey, same size range | REQUIRES FEASIBILITY VALIDATION; existing RSA interpretation only, no key generation |
| v4 | RSA (1), 3,072-8,192 bits, or EdDSALegacy (22) using Ed25519Legacy | Bound ECDH (18) subkey using Curve25519Legacy | REQUIRES FEASIBILITY VALIDATION; legacy OpenPGP Curve25519 encoding, not native X25519 packet encoding |
| v4 | EdDSALegacy (22) using Ed25519Legacy | Bound RSA (1) encryption subkey, 3,072-8,192 bits | REQUIRES FEASIBILITY VALIDATION; mixed-algorithm relationship must verify |
| v6 | Ed25519 (27) | Bound native X25519 (25) subkey | REQUIRES FEASIBILITY VALIDATION; modern preferred EC pairing |
| v6 | RSA (1), 3,072-8,192 bits, or Ed25519 (27) | RSA (1) primary where applicable, or bound RSA (1)/X25519 (25) subkey; RSA components are 3,072-8,192 bits | REQUIRES FEASIBILITY VALIDATION; primary/subkeys must all be v6 |

Ed25519/EdDSALegacy sign; they are not encryption algorithms. X25519 and legacy ECDH encryption subkeys do not certify a primary. Every usable encryption component also needs verified bindings/key flags. Bare signing-only certificates are not accepted as the encryption-key capability; an encryption component may nevertheless be historical/expired/revoked and retained as described below.

[Predecessor RFC 4880](https://www.rfc-editor.org/rfc/rfc4880.html) informs v4 structure; [RFC 6637](https://www.rfc-editor.org/rfc/rfc6637.html) defines the older OpenPGP ECDH framework, not the later Curve25519Legacy assignment. [RFC 9580](https://www.rfc-editor.org/rfc/rfc9580.html) governs current v6 structure and modern/legacy distinctions. In particular, v6 cannot use the deprecated Ed25519Legacy/Curve25519Legacy OIDs; do not relabel legacy bytes as native algorithms 27/25. Native algorithms 27/25 in v4 are outside this initial application matrix, not declared universally forbidden by the RFC.

Out of scope for this approved contract: v3/v5 keys, other curves/algorithms (including DSA/Elgamal, X448/Ed448 and NIST/Brainpool EC), RSA outside the stated range, mixed primary/subkey versions, PEM/SPKI/X.509/SSH containers, binary keyrings and multiple primaries. Unsupported historical material is not corrupt by definition, but cannot be silently accepted, converted or dropped. Broader support requires explicit contract/feasibility review. No key generation, encryption/decryption UI, keyserver fetch, account or identity-certification feature is added.

## 2. Data validity, cryptographic relationships and usability

Input remains <=64 KiB (65,536 bytes), one complete PGP PUBLIC KEY BLOCK, one primary, <=4 subkeys, <=8 user IDs and <=128 packets. Parse bounded lengths/base64, reject truncated/malformed or excessive input and prevent recursive decompression. Recognized certificate packets are public key (6), public subkey (14), signature (2), user ID (13), with bounded ignorable marker (10)/padding (21) handling. Unsupported attributes/unknown semantics are classified as unsupported, not silently trusted. No compressed/literal/encrypted-message wrappers.

Reject secret/private packets **5 or 7**, private containers/armor and mixed public/private material unconditionally, irrespective of filename, password protection, armor relabeling or library willingness to extract a public view. Inspect the entire accepted input, not just its first public object. Never silently derive/save a public key from private input, and keep all key material out of diagnostic logs/rejected persistent caches.

Separate four independent key properties; backup byte integrity is a further, separate check:

1. **Structural validity:** complete public-only certificate, version/algorithm matrix, bounded packet grammar and matching primary/subkey versions.
2. **Cryptographic integrity:** mathematically verify the relevant self-certifications/direct signatures and subkey bindings using a suitable maintained verifier. v6 requires its valid Direct Key signature and v6 self-signatures; do not require a made-up v6 User ID when the standard permits none. v4 verifies applicable self-certification/direct-key semantics. Verify required embedded primary-key bindings for signing subkeys. Unknown critical semantics or unverifiable required relationships are unsupported/invalid; an armor label is insufficient.
3. **Current usability:** evaluate valid key flags, encryption capability, expiration, verified revocation and creation times independently of successful parsing/historical signature verification. Expiration does not make a formerly valid mathematical signature false.
4. **Identity trust:** VCard Native does not independently establish that the key belongs to the claimed person. Successful signature/binding verification is not real-world identity verification.

**Backup byte integrity:** entry size/hash and supported bytes must match the manifest; this does not establish identity trust or replace the required structural and cryptographic checks. Revocation status comes from verified, supported OpenPGP semantics, never a filename or untrusted text label.

Required cryptographic verification uses supported SHA-256/384/512 signature hashes and algorithm-appropriate rules; v6 salts/critical subpackets are handled by the maintained stack, not custom code. Weak/unsupported required signature hashes remain unsupported, including historical SHA-1 self-signatures; SHA-1 used for a v4 fingerprint is a different purpose. Nonessential third-party certifications may be retained as bounded public certificate data but never establish trust or bypass required self/binding checks. Unusual cases, including authorized-revoker cases that cannot be verified offline, remain P0.5/P0.6 technical feasibility questions. Do not invent a classification or ignore an unresolved relevant revocation and declare usability; until supported validation can classify them safely, they cannot pass input/restore validation.

Armor CRC24 is not a validity/authenticity gate: RFC 9580 says not to reject solely for absent/malformed/mismatched CRC24. Still reject malformed actual base64/packets/signatures. Canonical output follows version-aware armor rules, including no CRC24 generation for v6 certificates. Do not confuse this optional armor footer with the independent asset/backup SHA-256 check.

| Key condition | Storage and full-backup restore | Current N01 encryption-key action |
|---|---|---|
| Supported, data-valid and currently usable | Accept/preserve complete supported public-only material | Available only if saved, present and showOnCard=true |
| Supported, data-valid but expired | Preserve; expiry alone must not reject a complete valid backup | Unavailable while expired; existing inline explanation |
| Supported, data-valid with verified revocation | Preserve complete material needed to represent and verify revocation; owner-approved retention, not corrupt merely because revoked | Unavailable while revoked; communicate revoked/unavailable using existing inline status |
| Malformed structure or invalid required cryptographic relationships | Reject input/whole restore; preserve previous complete state | Unavailable |
| Private/secret-key material | Reject unconditionally, including mixed input; no extraction/conversion | Unavailable |
| Unsupported historical version, algorithm or packet structure | Reject whole restore before replacement; factual unsupported-public-key-format explanation; no opaque import | Unavailable |
| Required revocation/critical semantics or target library feasibility unresolved | Technical feasibility question for P0.5/P0.6; no acceptance claim or partial restore until supported validation is substantiated | No active action or implied trust |

A revoked primary disables all encryption candidates. Subkey revocation applies to the affected component: never present it as usable; a different currently usable, correctly bound, unrevoked component is evaluated independently under the existing policy. Device time is not trusted external time; if usability cannot be determined, expose no active action and explain uncertainty. Retention of supported data-valid revoked certificates and rejection of unsupported historical formats are settled owner policies. Unusual revocation classification remains technical feasibility work, not an exception to these policies. No quarantine/merge/new screen is introduced.

## 3. Storage and intentional public download

Use existing N04 input only; exact file/picker integration remains P0.5. After complete public-only validation, normalize armor line endings to LF and omit nonessential armor headers without changing cryptographic packet content, relationships, revocations or identities. Reparse/reverify the result; do not strip revocation/unsupported content to manufacture acceptance. Store accepted public-only bytes with assetId, mediaType application/pgp-keys, format openpgp-public-armored, keyVersion (4 or 6), primaryAlgorithm, byteLength, SHA-256 and full version-tagged fingerprint. Derive usability at evaluation time; never restore a cached usable=true claim.

Fingerprint representation is version-specific: v4 is the standard 20-octet SHA-1 fingerprint (40 uppercase hex characters); v6 is the standard 32-octet SHA-256 fingerprint (64 uppercase hex characters), as described by the respective key-version rules. The application chooses uppercase hex display; it is not a claim that the RFC mandates one human-readable v6 layout. A 64-character asset SHA-256 hashes the retained file bytes and is not the v6 key fingerprint. Never truncate either version to a short key ID as identity.

Explicit Save is still required; cancel/error retains the prior asset/draft. Retain supported revoked keys in saved profile data and communicate revoked/unavailable status through approved N01/N04 inline components. The user may replace or remove the key through existing N04 editing and explicit Save; no additional screen, sheet or dialog is introduced. Preservation of data-valid historical material does not authorize its current download. The prior visibility preference is preserved on restore, but the N01 action additionally requires currently usable supported encryption capability; otherwise hide the active action and use existing inline explanation. Filename remains vcard-native-public-key.asc, MIME application/pgp-keys ([IANA](https://www.iana.org/assignments/media-types/application/pgp-keys)). Success requires completed output, not return from a picker. No key/URL is inserted into contact QR or .vcf without separate approval.

Embedded key user IDs may disclose identities independently of profile/contact visibility. Keep the existing inline explanation; no new confirmation flow. Complete backup includes supported historical public-only bytes even when display-hidden, expired or verifiably revoked under the owner-approved retention policy. Never store/export secret material via a backup exception.

## 4. Image input and small canonical format set

Source support/limits remain still JPEG, PNG or WebP; no animated/multiframe, HEIF/GIF/SVG, corrupt/truncated/polyglot or fetched remote image. Inspect content, not filename/MIME alone. Existing source limits remain 20 MiB, each side<=8,192px and <=16,777,216 total pixels; retained portrait longest edge<=1,024px/cover<=2,048px, positive dimensions, <=8 MiB per retained asset.

| Approved canonical format | Source/use decision | Tradeoff |
|---|---|---|
| Metadata-stripped JPEG, image/jpeg, .jpg | Fully opaque JPEG source or fully opaque lossy WebP source; approved quality 90 after orientation/sRGB/downsample | Efficient photographic storage/backup; another lossy generation can alter pixels and quality 90 is not a cross-encoder quality guarantee |
| Metadata-stripped PNG, image/png, .png | Any alpha-bearing source, PNG source, or lossless WebP source | Preserves transparency/lossless needs; can be larger and still must meet 8 MiB limit |
| WebP as canonical output | Not selected for initial retained format set; keep WebP input support | Potential size/quality benefits, but encoder/API/version and reproducibility need extra validation; reconsider only through owner review |

No image-content/photo-classification heuristic or format selector is added. Source format, WebP lossless flag and decoded alpha determine the branch; if detection is uncertain choose PNG, never flatten alpha silently. [Android supported formats](https://developer.android.com/media/platform/supported-formats) and [CompressFormat documentation](https://developer.android.com/reference/android/graphics/Bitmap.CompressFormat) describe JPEG/PNG/WebP capability and explicit WebP encoder API distinctions. They do not prove target Pixel behavior; no SDK/picker/encoder is selected.

Bound decoding/allocation, apply orientation, convert to sRGB, downsample preserving aspect without upscaling, then freshly encode in the selected canonical format. Remove EXIF/GPS/IPTC/XMP/comments/source URI and arbitrary inherited metadata, retaining only necessary format/color information for the normalized representation. JPEG alpha is forbidden; PNG preserves alpha. No crop/filter tools or user image-editing route is added. Fail safely if the resulting asset exceeds 8 MiB; no automatic quality-reduction loop.

Reparse canonical output, verify actual MIME/codec/dimensions/metadata policy, and record assetId, mediaType, byteLength, width/height, sha256 and canonicalizationPolicyVersion=1. Validation is deterministic for a given retained file/policy, but different compliant encoders need not emit byte-identical JPEG/PNG. Hash exact retained bytes; backup/restore must copy/verify them without re-encoding, so later encoder changes cannot silently alter asset hashes. A source file is never retained simply because its declared format matches. The approved cover/portrait viewports remain display-only crops.

## 5. Ownership and the single N04 location

Acquire selected content only through the already-approved external handoff from **N04**. Do not rely on a source provider URI for permanent ownership or serialize permission grants into backups. Create validated app-owned bytes while input is readable; saved state survives source-file deletion, permission loss, process termination and device restart. Exact picker/provider/storage mechanism remains P0.5. [Android file-access guidance](https://developer.android.com/training/data-storage/shared/documents-files) describes user-mediated access; no specific picker implementation is selected here.

N05 links to N04: if appearance is dirty, existing D01 Keep editing/dismiss stays N05; Discard restores saved appearance then opens N04; explicitly saved appearance permits the route. Return refreshes saved appearance/imagery. Selection cancellation does not replace an existing image, and profile Save is still required to retain a new image. A failed file read/decode/copy or cancelled selection leaves prior valid bytes/reference unchanged. No second picker/editor in Appearance is added.

Missing/unreadable saved asset is a data-integrity failure: N01 can show its approved neutral fallback, but do not claim full backup success while omitting the missing asset. Re-select the image in N04 to repair. Restore packages missing a referenced asset are invalid. Asset replacement/cleanup must retain old valid bytes until the coherent Save/restore commit succeeds.

## 6. Backup, privacy and verification

Backup contains exact canonical JPEG/PNG and supported public-only certificate bytes, including hidden/historical values. Restored key data validity and current usability follow section 2: expiration alone does not corrupt a backup; supported data-valid revoked certificates must also be retained, with unusable actions unavailable. A valid backup must not fail solely because its supported key is revoked. Restore copies exact saved certificate bytes, including all supported material needed to represent and verify revocation; never strip packets, rewrite identity, substitute keys or normalize/re-encode the restored asset. Unsupported historical algorithms, private packets, malformed/unverifiable required relationships or mismatched bytes reject the entire restore rather than dropping the key or partially restoring the profile. No app-visible recovery/history/quarantine feature is added.

P0.5 feasibility evidence must cover each matrix pairing, v4/v6 fingerprint/armor semantics, full-input private rejection, verified certificate relationships, historical parsing separate from current-policy usability, license/runtime suitability and bounded work. P0.6 must later verify expiry/revocation/clock cases, designated-revoker uncertainty, malformed/mixed/private input, metadata/alpha/orientation, canonical JPEG/PNG, provider cancellation and exact-byte backup round trips. These are future obligations, not tests executed now. No cryptographic implementation, image pipeline or Android dependency was created.
