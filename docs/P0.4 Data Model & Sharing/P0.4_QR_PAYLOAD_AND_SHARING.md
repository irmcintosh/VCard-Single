## 1. Data sources and mode identity

**Contact QR:** the complete bounded UTF-8 byte sequence of the explicitly provisional vCard 3.0 profile specified in the vCard document, including escaping/folding/CRLF, generated from the saved export-filtered contact projection. No remote lookup, hosted pointer, image/key attachment, custom shortener or recipient VCard Native installation is needed. The same eligible values feed .vcf; QR is not silently reduced to a smaller subset.

**Milestone 1.11 Step 4E:** The shared export projection now includes optional explicit, independently enabled name components. With any included component, vCard N precedes FN using Family/Given/Additional/empty Prefix/empty Suffix. With none, retain the legacy FN/empty N bytes. Structured names count toward the existing exact byte, encoding-capacity and geometry limits; no truncation, field dropping or online fallback is authorized. ContactQrEncoder and all encoding/geometry constraints remain unchanged.

**Web-profile QR:** exactly the normalized ASCII serialized `hostedProfileUrl` URI, with no vCard wrapper, hidden contact values, profile identifier or appended tracking data. Configure only valid HTTPS URLs. Generation is local; recipient navigation requires connectivity and independently hosted content. No syntax check certifies website reachability/current content. Do not substitute website for missing hostedProfileUrl. URL copy/share uses the same selected saved URL; it does not serialize the profile.

Fresh N02 entry defaults to Contact QR; return from sheets/external activities retains the still-valid mode. Missing/invalid URL leaves web QR unavailable with N04 configuration guidance. No cloud publication/sync, automatic web fallback or mode-default setting is added.

## 2. Approved Clarification A — unchanged behavior

- Contact QR is the default sharing mode.
- Display the offline contact QR immediately when valid saved/export-enabled contact data can be encoded.
- Display a readable summary of the contact information included in the QR.
- Allow users to open the Contact Export Preview sheet voluntarily before presenting the QR.
- Require the Contact Export Preview sheet and explicit action-specific confirmation before generating/sharing a `.vcf` file.
- Require the same preview and confirmation before saving or sharing a contact QR image.
- Never include fields excluded from contact export.
- Invalidate stale QR previews and artifacts after relevant saved-profile or visibility changes.
- Do not introduce a blocking confirmation before the initial QR display.

These binding UX rules are not subject to the approved sizing/encoding constraints below. Failed generation shows the approved inline state rather than falsely displaying an old code.

## 3. Encoding specification and standards evidence

Use ordinary **QR Model 2**, error correction **M**, smallest fitting version within **1-40**, subject to actual approved-panel geometry. Use byte mode: ASCII-only payloads use the same ASCII/UTF-8 bytes without ECI; any non-ASCII contact bytes use UTF-8 with explicit ECI 26. These numerical constraints are approved planning requirements; real-device scan reliability remains unverified. The encoder version range now covers the standard model's versions instead of arbitrarily stopping at20; geometry remains an independent gate, not a full-capacity scan guarantee. No Micro QR, structured append, multiple-code split, compressed custom contact format or dynamic network code is authorized.

[DENSO WAVE's version guide](https://www.qrcode.com/en/about/version.html) confirms that version/capacity depends on data type and correction level, with 21 modules at version 1 and four more per side per version. Its [correction guide](https://www.qrcode.com/en/about/error_correction.html) describes level M as a common tradeoff; a nominal correction rate is not a guaranteed percentage of arbitrary covered screen area. [ISO's official record](https://www.iso.org/standard/83389.html) identifies ISO/IEC 18004:2024, edition 4. Only its public catalog/abstract was inspected, not the full paid standard. No full ISO conformance certification is claimed.

UTF-8 ECI 26 is corroborated by a manufacturer's [QR decoder documentation](https://evision.docs.alliedvision.com/en/latest/using/text_and_code_reading/easyqrcode/specifications.html); that is product documentation, not access to the normative ECI registry. P0.5 must confirm encoder support/assignment and P0.6 must verify real scanner interpretation of non-ASCII/ECI contact data. Older-reader behavior remains uncertain. Do not silently strip Unicode or switch to an unannounced encoding if a chosen scanner fails.

## 4. Capacity and scan-safe geometry

The former 1,024-byte/version 20 gate is replaced by four separate checks:

| Layer | Approved planning rule | What it does not prove |
|---|---|---|
| Theoretical encoding | Smallest Model 2 version1-40 fitting byte data plus actual mode/ECI/correction/terminator overhead, correction M | Character count alone is not capacity; theoretical fit does not prove screen fit or scanning |
| Application resource bound | <=4,096 actual serialized UTF-8 payload bytes before attempting encoding, including folds/CRLF | A4 KiB buffer guard is not claimed encodable capacity; the encoder must still reject no-fit |
| Physical rendering | Integer modules within the actual P0.3 panel and intact quiet zone/additional white pad, approved floor2dp and3 physical pixels | Neither dp nor pixel count alone guarantees optical/scanner behavior |
| Recipient compatibility | Actual P0.6 tests of contact recognition/import, Unicode/ECI, device/density/viewing conditions | No current scanner/recipient pass has been established |

The larger resource guard avoids premature rejection of data that might fit a larger version; the encoder's actual capacity remains lower where correction/mode overhead requires it. There is no universal maximum character count and no unconditional promise to render all versions. Keep M as a bounded default; no silent reduction to L or data/Unicode loss to make a code fit. Compare M/Q in later evidence if useful, but do not make an automatic correction-level downgrade an escape route.

ASCII-only data, including normalized hosted URLs, does not need an ECI marker because its byte meanings agree with the common ASCII subset. Non-ASCII contact data uses explicit UTF-8 ECI 26; do not remove that marker or transliterate on scanner failure. This approved conditional policy reduces avoidable ASCII-reader friction while retaining explicit Unicode intent. P0.5 must substantiate encoder behavior and P0.6 scanner interpretation; neither is proven now.

Require a four-module quiet zone on every side per [DENSO code-area guidance](https://www.qrcode.com/en/howto/code.html/index.html). P0.3's16dp outer white visual pad is additional. For version v, symbol side=17+4v modules and full quiet-zone side=25+4v. Thus v20 is105 and v40 is185 modules including quiet zones. No full ISO/ECI registry inspection or conformance certification is claimed.

Let d be actual physical-pixels/dp, P the available square panel pixels and A the16dp outer pad rounded outward to physical pixels per side. Let k=floor((P-2A)/(25+4v)); require k>=max(3,ceil(2d)), with no smoothing and centered leftover white pixels. Start from P0.3's preferred280dp panel; if necessary and room exists, grow within its existing 320dp cap before rejecting. The cap, padding, square shape and no-overlay visual rules are unchanged. Select the smallest theoretically fitting version that also satisfies the actual geometry; larger versions cannot be used to evade a failed module floor.

Illustrative density 3 arithmetic: at 280dp, available grid area is 744px; 2dp modules require 6px, allowing up to v24 (121*6=726px), not v25 (125*6=750px). At 320dp, grid area is 864px, allowing v29 (141*6=846px) but not v30 (145*6=870px). These examples show why a fixed version 20 cutoff was unnecessary and why theoretical version 40 capacity still cannot fit every panel. They are arithmetic examples, not device measurements or scan evidence.

If geometry cannot fit, preserve existing inline limitation/edit/VCF paths; do not change UI tokens, hide required text, add a fullscreen destination or silently lower approved module safeguards. Module floors and density envelope are approved planning constraints; real-device evidence may justify a controlled later revision instead of an unbounded capacity promise.

## 5. Oversize and failure behavior

Differentiate: input over the approved 4,096-byte resource gate; no version1-40 fits M/encoding overhead; module geometry insufficient; encoding failure; PNG/file/provider failure. Show factual inline explanation, no stale active QR and no claim that the selected data was partially encoded. Let the user explicitly edit export selections in N04 or choose .vcf from N02; return through S01 and re-review when required. No automatic exclusion of biography/location/links, no ellipsis in payload, no lower correction level fallback and no web-mode substitution.

A large hosted URL can pass URL syntax validation yet fail QR sizing; Copy/Share URL may still work independently. A large contact can fail QR but pass the separate 64 KiB .vcf limit. The included-data summary explains the attempted supported selections, with error state clearly indicating that no valid current QR exists; it must not imply an unavailable code contains them.

## 6. Snapshot and artifact lifecycle

1. Read a coherent saved aggregate and derive the mode-specific projection. Identify it with generation/revision, export-contract version, mode and action; record a digest of actual payload bytes in the transient operation context, not a public filename.
2. Immediately render a valid contact QR and readable included-data summary. Voluntary S01 review does not gate display.
3. For .vcf/contact-image actions, open S01 with the exact included values and explicit invoking-action label. On confirmation, compare the current saved generation/revision and contract; if changed, refresh and require that action's confirmation again before file/image creation.
4. Use immutable reviewed payload bytes for the artifact; never reread mutable fields while serializing. Bind confirmation to one action/attempt; cancellation or failure does not authorize a later unrelated action or new snapshot.
5. Before external handoff/write starts, check snapshot validity again. Serialize saves/restores with the capture/start boundary or fail stale. Once intentionally handed off, changing local settings cannot revoke the receiver's copy or a file already saved externally; do not claim otherwise.

Any successful saved change invalidates in-app derived QR/preview/artifacts conservatively. Restore issues a new generation. Appearance-only changes may invalidate more than technically necessary but cannot weaken privacy. Unsaved drafts never enter an export. In-flight OS operations whose outcome is unknown are reconciled before retry; never duplicate a handoff/write automatically after restart.

## 7. QR image/save/share contract

Export one lossless opaque PNG: `image/png`, black modules/white paper, no identity text/metadata/logo. Use 8 physical pixels/module with all four quiet-zone modules preserved; resulting PNG side is `(25 + 4v) × 8`, e.g. 840px at version 20 and 1,480px at version 40; actual current usable codes must also pass the on-screen geometry gate. This file geometry is separate from dp display geometry; no resampling after rasterization. Encode no EXIF/location/profile metadata.

Use `vcard-native-contact-qr.png` and `vcard-native-web-qr.png`, so filename and UI label distinguish modes without putting personal names in filesystem metadata. Contact PNG generation for save/share requires S01 first; web PNG uses selected URL and visible online/hosted-independence notice. The already-displayed contact QR matrix is not permission to write/export an image without confirmation.

Save through a user-chosen destination; local-file choice must work offline, selected cloud providers may not. Report success only after a confirmed complete write/close. Cancellation/failure may leave a partial external file; best-effort cleanup if supported, never a success claim. Do not overwrite another selected provider object without the provider's explicit semantics. A share uses native Sharesheet and narrow temporary `content://` read access under [Android's sharing guidance](https://developer.android.com/training/secure-file-sharing/share-file); return does not prove delivery. P0.5 selects the mechanism, not this document.

Transient files remain app-private before handoff, named without user text. Require a 24-hour maximum retention target for unused cache artifacts, cleaned when the app can safely do so; do not delete bytes an active granted receiver still needs. Invalidation prevents new reuse, not retroactive revocation. P0.5 must resolve safe cleanup/grant lifetimes and crash leftovers without public cache directories or a new history feature. External saved copies are user-controlled and outside this retention target.

## 8. Verification obligations and limits

P0.6 must check exact payload bytes/exclusions after UTF-8/folding; min/max fitting versions and gates; grid/quiet-zone geometry at different densities; Unicode ECI recognition; low brightness/glare/angle/distance; real second-device scan and contact-save behavior; and QR PNG save/share/file-provider cancellation. Test selection-change races, restore invalidation, app restart and stale-confirmation rejection. Imported essential fields must be checked, not only a scanner success icon.

No QR library was selected or installed, no QR image generated/scanned and no Android runtime tests performed. Standards research confirms design inputs, not field compatibility or reliable scans. Version/module/ECI constraints are owner-approved planning requirements with later evidence obligations; approval does not establish scan reliability. P0.2 and P0.3 contracts are unchanged; P0.5 has not started.
