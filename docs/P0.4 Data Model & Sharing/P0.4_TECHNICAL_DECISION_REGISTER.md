## Owner-approved public-key policy directions

### Later owner-approved M1.11 Step 4E structured-name extension (2026-11-01)

This bounded approval supersedes the original fixed-field/empty-N-only statements below. Retain required Full Name and add optional explicit firstName, middleName, lastName in Basic Information and Details. No automatic name splitting or Full Name overwriting. Apply the existing 160-scalar name normalization/validation policy. Optional components have independent default-off Contact Export settings and no separate card presentation; Full Name remains the identity.

Write additive AppData schema 3, read strict schemas 1/2/3, and default old absent components to empty editor values/export off. Backup formatVersion 1, A2 manifest/pointer framing, atomic intents, identity, assets and phone metadata remain unchanged. New schema-3 data/backups are not downgrade-safe.

Export contract version 2 remains offline vCard 3.0. Any included component yields N before FN, Family=Last, Given=First, Additional=Middle, Prefix/Suffix empty, each component escaped independently. No included components retains exact legacy FN/empty N ordering. Preserve phone, URL, privacy, NOTE and QR limits. Android Camera's literal NOTE `\n` is a recipient issue; do not alter valid escaping. Owner successful Candidate 01 trials justify this correction, not a universal claim; updated-APK Android/iPhone physical tests remain required. Milestone 1.11 OPEN; 1.12 unstarted.

The owner explicitly settled two policies in the P0.4 public-key policy finalization task:

- **Decision A - Revoked public keys:** Preserve supported, structurally valid public-only keys with valid required cryptographic relationships and verifiable revocation in saved data/full backups/restores. Retain complete supported revocation material; do not fail a valid backup solely for revocation. Actions must be disabled or unavailable when they would present revoked material as currently usable encryption keys. Communicate status using existing N01/N04 inline patterns; replace/remove through N04 and explicit Save.
- **Decision B - Unsupported historical formats:** Reject the entire restore candidate containing unsupported public-key versions, algorithms or packet structures before replacement. Explain the unsupported public-key format and preserve the existing profile, appearance, images, visibility and saved key unchanged. No opaque import, partial restoration, automatic conversion, key stripping or substitution; future compatibility is not promised for v1.0.

Historically, these two policies were approved before the full milestone. The current approval now covers all twelve full decisions and the bounded matrix subject to conditions A/B/C; no parser/dependency choice or runtime result is approved by this record. Supported data-valid expired keys also remain retained with currently unusable actions unavailable. Structural validity, cryptographic integrity, current usability and identity trust are independent; successful OpenPGP verification does not establish real-world identity. Unusual revocation classification remains P0.5/P0.6 feasibility work; no unsupported case may bypass validation. All twelve decisions below are now **APPROVED**.

## P0.4-01 — One aggregate and fixed field inventory

- **Decision description:** Saved profile lifecycle, cardinality and data/artifact separation.
- **Approved approach:** One current AppData aggregate with schema-1 compatibility and additive schema-2 phone metadata; one opaque profileId, one full name, ten optional text/contact/link slots, one hosted URL, one key and two images; three fixed professional-link categories. Saved appearance uses approved P0.3 enums. Runtime generation/revision identifies state; artifacts/drafts/grants are not backup data. The owner-approved Milestone 1.10 extension reads schema 1 and writes schema 2 to retain phone region, country-code formatting preference and canonical E.164 alongside the unchanged display value.
- **Historical alternatives (not selected):** Different internal aggregate organization with the same one-profile contract; broader cardinalities require separate owner evaluation rather than silent implementation.
- **Advantages:** Small bounded model; one coherent save/restore and no account dependency.
- **Disadvantages:** One phone/email and fixed link slots limit flexibility; future expansion requires explicit schema evolution.
- **Standards/authoritative references:** Approved P0.1 FR-01/FR-06; [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html) for approved JSON exchange syntax, not a database choice.
- **Relationship to P0.1–P0.3:** P0.1-02/03/07/10/12; P0.2-03/04/07/08; unchanged P0.3 component/surface inventory.
- **Implementation implications for P0.5:** Choose persistence, coherent commits and owned-asset references; no library chosen here.
- **Verification obligations for P0.6:** Save/restart/restore consistency and no multiple-profile path.
- **Owner approval:** Granted on 2026-10-29, subject to conditions A/B/C. **Status:** APPROVED.

## P0.4-03 — Bounded field validation and normalization

- **Decision description:** Text/phone/mailbox/URI rules without network validation.
- **Approved approach:** NFC/trim/control rejection; approved per-field scalar/byte limits; region-aware phone parsing/validation through Google's libphonenumber; restricted single ASCII mailbox with IDNA domain; validated absolute web URIs and fixed categories. Preserve meaningful user display values; store E.164 separately; no truncation or silent address inference. The selected region is user-changeable and initially suggested from device locale without location access.
- **Historical alternatives (not selected):** Hand-written country-specific phone validation, a location service, broader mailbox syntax, or different safety limits. Phone validation does not assert reachability.
- **Advantages:** Predictable safe serialization and readable error correction in the existing editor.
- **Disadvantages:** Some legitimate quoted/international mailboxes and phone extensions are excluded; validation does not prove reachability.
- **Standards/authoritative references:** [RFC 3986 URI syntax](https://www.rfc-editor.org/rfc/rfc3986.html), [RFC 5891 IDNA](https://www.rfc-editor.org/rfc/rfc5891.html); application limits/restricted subsets are approved requirements, not claims of complete standard validation.
- **Relationship to P0.1–P0.3:** FR-02/FR-04 privacy gates; existing N04 errors/C09/C13; no new screen or validation confirmation.
- **Implementation implications for P0.5:** Select safe Unicode/URI handling and field validators with identical Save/restore behavior.
- **Verification obligations for P0.6:** Boundary/Unicode/injection cases and preservation of unsaved corrections.
- **Owner approval:** Granted on 2026-10-29, subject to conditions A/B/C. **Status:** APPROVED.

## P0.4-06 — QR encoding and geometry envelope

- **Decision description:** Approved capacity/quality constraints without a universal character limit.
- **Approved approach:** Model 2/M; allow versions 1-40 but require actual encoder capacity and approved-panel geometry; approved 4,096-byte resource bound. ASCII-only byte payloads omit ECI, non-ASCII UTF-8 declares ECI 26. Four-module quiet zone plus unchanged 16dp outer pad; approved integer modules>=2dp/3px; start 280dp and use up to the existing 320dp cap if room; exported PNG 8px/module.
- **Historical alternatives (not selected):** Different bounded module/correction/ECI policy on later device evidence; no automatic lower correction, truncation, hidden-field inclusion or contact-to-web substitution.
- **Advantages:** Separates theoretical capacity, bounded resources, physical geometry and recipient evidence; removes unnecessary version 20/1,024-byte early cutoffs without promising dense-code success.
- **Disadvantages:** Geometry still excludes dense encodable data; M/ECI/module floors are approved planning constraints and untested; non-ASCII scanners may differ. Independent VCF remains available when QR cannot fit.
- **Standards/authoritative references:** [ISO catalog](https://www.iso.org/standard/83389.html), [DENSO versions](https://www.qrcode.com/en/about/version.html), [quiet zone](https://www.qrcode.com/en/howto/code.html/index.html), [correction](https://www.qrcode.com/en/about/error_correction.html); normative full ISO/ECI registry not inspected.
- **Relationship to P0.1–P0.3:** FR-04, P0.2-05/06, P0.3-07. Immediate valid contact QR/no first-display gate preserved.
- **Implementation implications for P0.5:** Substantiate encoder mode/ECI/version/overhead and integer rendering behavior without changing P0.3 tokens; no library chosen.
- **Verification obligations for P0.6:** Test actual Pixel density/panel widths, preferred/cap size, fitting boundaries, ASCII/no-ECI and Unicode/ECI contact recognition; mathematical fit alone is insufficient.
- **Approval qualification:** QR capacity/geometry are approved planning constraints, not verified scan reliability. Numerical values and P0.3 panel tokens are unchanged.
- **Owner approval:** Granted on 2026-10-29, subject to conditions A/B/C. **Status:** APPROVED.

## P0.4-08 — Modern public-only OpenPGP compatibility

- **Decision description:** Accepted public encryption-key representation and validity.
- **Approved approach:** One <=64 KiB armored public-only certificate under the asset contract's bounded v4 RSA/legacy ECDH Curve25519 and v6 RSA/native X25519 matrix, using supported signing primaries. Each row is REQUIRES FEASIBILITY VALIDATION. Store keyVersion/primaryAlgorithm and correct v4 40-hex or v6 64-hex fingerprint separately from the asset digest. Separate structural validity, required cryptographic integrity, current encryption usability and identity trust; retain supported data-valid expired/verifiably revoked material, including complete revocation evidence, with unusable actions unavailable. Owner policies A/B are settled; the matrix is conditionally approved pending feasibility validation. Any reduction requires explicit project-owner approval before implementation; if infeasible, document and escalate rather than silently removing support or weakening validation. No custom cryptographic parser is authorized. No contact KEY property.
- **Historical alternatives (not selected):** Expand specific matrix rows only after supported parser/verification evidence. No unbounded all-OpenPGP promise, custom crypto, private conversion, key generation or keyserver lookup.
- **Advantages:** Reflects the owner's modern-compatibility direction while distinguishing signing-only algorithms, legacy/native encodings, historical data and current action eligibility.
- **Disadvantages:** Android/library/policy integration remains unproven; unsupported algorithms/critical semantics still reject whole input/restore. Unusual revocation/authorized-revoker classification remains P0.5/P0.6 technical feasibility work; supported revoked-history retention and unsupported-format rejection are already owner-approved policies.
- **Standards/authoritative references:** [RFC9580](https://www.rfc-editor.org/rfc/rfc9580.html), [RFC4880](https://www.rfc-editor.org/rfc/rfc4880.html), [RFC6637](https://www.rfc-editor.org/rfc/rfc6637.html), [IANA algorithms](https://www.iana.org/assignments/openpgp), [BC documentation](https://www.bouncycastle.org/documentation/documentation-java/), [PGPainless changelog](https://github.com/pgpainless/pgpainless/blob/main/CHANGELOG.md); candidate license/runtime details in asset contract.
- **Relationship to P0.1–P0.3:** FR-01, P0.2-11 and C04/C09; no new key screen or crypto-product feature.
- **Implementation implications for P0.5:** Compare maintained Bouncy Castle/PGPainless candidates for all target rows, signature/binding/revocation semantics, v6 direct signatures/armor, historic/current-policy separation, resource limits, licensing and Android runtime suitability. Select no artifact/Gradle/SDK version now.
- **Verification obligations for P0.6:** Validate v4/v6 fixtures/legacy versus native curves, signing-only rejection, required relationships, private packets anywhere, CRC24 semantics, full fingerprints and expired/revoked/clock/unsupported backup cases.
- **Approval qualification:** Condition C: every unverified pairing remains REQUIRES FEASIBILITY VALIDATION. P0.5 must evaluate maintained Android-suitable parser/verifier candidates and P0.6 must verify the contract; any matrix reduction needs explicit owner approval. No final dependency or custom parser is authorized here.
- **Owner approval:** Granted on 2026-10-29, subject to conditions A/B/C. **Status:** APPROVED.

## P0.4-10 — Versioned bounded full-app archive
