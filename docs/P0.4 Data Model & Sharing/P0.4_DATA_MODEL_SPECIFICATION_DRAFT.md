## 2. Aggregate and lifecycle

Specify one local `AppData` aggregate. Owner-approved Milestone 1.11 Step 4E writes `schemaVersion = 3`, containing `profile`, `appearance` and `metadata`; readers retain versions 1 and 2. Related app-owned asset bytes are part of the same logical saved state. The additive version-2 extension stores the selected phone region, country-code export preference and canonical E.164 value while preserving the original phone display value. Version-1 values default the export preference to true; a valid international number supplies its region, otherwise use the device-locale region. Version 3 adds optional firstName, middleName and lastName plus their export preferences. Versions 1/2 default them to absent values (empty editor fields) and export off, never inferred from fullName. A2 framing, pointers, immutable generations and durable operation intents are unchanged. Older APKs reject schema 3; downgrade safety is not claimed.

- `profile` is either absent before first save or exactly one saved Profile. Full-app backup creation requires an existing saved profile; first-run recovery can restore without first creating one. No profile list, switching, merge or delete/reset feature is added.
- `profile.profileId` is an opaque locally generated UUID, created on first successful save, stable across ordinary edits and preserved through full backup/restore. It is not an account identity or an exported contact UID.
- N04 creation/editing uses a separate in-memory editing draft. Save validates all affected data/assets, then replaces the saved aggregate coherently or preserves prior state. Failed saves retain the draft. N05 appearance uses its own draft and explicit Save; it never auto-saves before the N04 image link.
- Restoring a valid backup replaces the whole aggregate after S02 confirmation; it never creates a second profile. The old valid aggregate remains recoverable until commit success is established.

P0.5 chooses persistence, transaction/recovery mechanisms and transient-draft restoration feasibility. P0.4 requires a coherent visible state; it does not promise a new persistent-draft feature.

## 3. Supported field inventory

Strings store normalized Unicode text under the companion validation policy. Optional values are `null` rather than empty strings. Counts are fixed v1.0 cardinalities, not extensible custom fields.

| Profile key / slot | Conceptual type and cardinality | Required? | Purpose and handling |
|---|---|---|---|
| fullName | String, one | Yes | Only mandatory user field; display and contact identity |
| firstName | Nullable string, one | No | Explicit given-name component; no automatic splitting or Full Name rewriting |
| middleName | Nullable string, one | No | Explicit additional-name component |
| lastName | Nullable string, one | No | Explicit family-name component |
| professionalTitle | Nullable string, one | No | Professional title |
| organization | Nullable string, one | No | One organization; no department subfield |
| biography | Nullable multiline string, one | No | Professional biography |
| location | Nullable string, one | No | Unstructured location; not coordinates/postal-address structure |
| phone | Nullable string, one | No | One telephone display value used for Call and Message; canonical E.164 value is stored separately when valid |
| email | Nullable string, one | No | One mailbox; no address list |
| website | Nullable absolute web URL, one | No | Personal/professional website |
| professionalLinks.linkedin | Nullable HTTPS URL, one | No | Fixed LinkedIn slot |
| professionalLinks.github | Nullable HTTPS URL, one | No | Fixed GitHub slot |
| professionalLinks.otherProfessional | Nullable HTTPS URL, one | No | One other professional/social URL, fixed generic label; no custom field/label editor |
| hostedProfileUrl | Nullable HTTPS URL, one | No | Independently hosted public profile for optional web QR/copy/share; not auto-derived from website |
| publicKey | Nullable PublicKeyAsset reference, one | No | Validated user-provided public encryption key, no key generation |
| profileImage | Nullable ImageAsset reference, one | No | Locally owned portrait |
| coverImage | Nullable ImageAsset reference, one | No | Locally owned cover |

This is **15 user-data slots**, counting the three fixed professional-link slots separately, plus internal identity, metadata and visibility. No second phone/email, arbitrary link list, name-part editor, address/map action, new networking feature or automatic contact import is introduced. Standard contact formats can hold more than this application exposes; that does not authorize additional fields.

Phone metadata belongs to the single profile, not to visibility: `phoneRegion` is a supported ISO region code, `phoneNumberE164` is nullable canonical international form, and `includeCountryCodeWhenSharing` is a boolean defaulting to true. A legacy unparseable value keeps its display text and null E.164 value until the user edits or removes it. `showOnCard` and `includeInContactExport` remain independent and alone determine eligibility.

## 4. Value objects and relationships

`ImageAsset` contains `assetId` (UUID), `mediaType` (`image/jpeg` or `image/png`), `byteLength`, `width`, `height`, `sha256`, `canonicalizationPolicyVersion` (1) and app-owned canonical bytes referenced by that ID. JPEG is used for opaque JPEG/lossy-WebP sources; PNG for alpha, PNG/lossless-WebP or uncertain source classification. Role-specific dimensions and byte limits remain unchanged; source bytes are not retained. Backup names use .jpg/.png consistently with actual canonical MIME; exact bytes are restored without re-encoding.

`PublicKeyAsset` contains `assetId`, `format` (`openpgp-public-armored`), `keyVersion` (4 or 6), `primaryAlgorithm`, `mediaType` (`application/pgp-keys`), `byteLength`, `sha256` and `fingerprint` plus accepted public-only bytes. The authoritative version/algorithm matrix in [the asset contract](P0.4_PUBLIC_KEY_AND_IMAGE_CONTRACTS.md) targets v4 RSA/legacy Curve25519 and v6 RSA/native X25519 with their supported signing primaries; all pairings are REQUIRES FEASIBILITY VALIDATION, not proven Android support. Fingerprints are uppercase 40-hex SHA-1 for v4 or 64-hex SHA-256 for v6; each uses its version-specific key-packet procedure. Asset SHA-256 is lowercase 64-hex over retained file bytes, distinct from either key fingerprint.

Structural validity and required cryptographic integrity determine key data validity; current usability (including expiry, verified revocation and clock status) is derived and never restored as a cached boolean. Identity trust is independent: signature verification does not establish the claimed real-world owner. Preserve supported data-valid expired and verifiably revoked certificates, including complete supported revocation material and hidden saved preferences; unusable encryption-key actions remain unavailable. Revoked-key retention is owner-approved. Unsupported historical versions/algorithms/packet structures reject the whole restore before replacement under the second owner-approved policy; preserve the existing profile, appearance, images, visibility and saved key unchanged. Unsupported/unverifiable/private/malformed input is never silently converted, stripped or partially imported. Unusual authorized-revoker/classification cases remain P0.5/P0.6 technical feasibility questions in the asset contract. Logical IDs are not arbitrary paths or permission-bearing URIs.

Exactly one profile owns at most two image references and one key reference. Bytes remain available offline after source selection permissions disappear or the provider changes its source file. Replacing an asset stages a new validated object; orphan cleanup must not remove an object still used by saved state, a live editing draft or an in-flight approved operation. P0.5 chooses reference management and storage.

`appearance = {theme, accent}` uses only P0.3's `dark`/`light` and `sapphire`/`jade`/`amethyst` enums; initial values are `dark`, `sapphire`. No font/template/custom-color/system-auto preference is introduced. Rendering tokens remain entirely in approved P0.3, not user-editable data.

`visibility` is a profile map keyed by the 15 inventory slot names. Each entry has `showOnCard` and `includeInContactExport`: booleans where supported; `null` means not applicable, never an implicit true. The complete eligibility/default matrix is authoritative in the privacy document. The name's two values are locked true under the approved essential-identity policy. Unsupported true values in backup input are invalid, not silently honored or ignored.

## 5. Metadata, revision and ownership

`metadata.createdAt` and `metadata.updatedAt` are UTC timestamp strings recording known local save times; device-clock timestamps may move backward, so timestamp ordering alone is not an integrity check. A device clock is not proof of chronology, identity or trust. Do not change the user's data based on online time services. Existing timestamps are retained on restore; runtime metadata separately records a new local generation.

Local operational metadata consists of random `generationId`, monotonic `stateRevision` within that generation and contract versions for export/validation. These are not user fields or contact exports. Increase revision after any successful profile, visibility or appearance save; after restoration issue a fresh generation and revision 1. Staging edits/cancelled operations never change saved revisions. Do not depend on timestamps to detect stale previews.

User controls saved data and intentional exports. Local ownership does not imply control over recipients, selected external providers, clipboard retention or the independently hosted website. No personal data, key contents, image paths, payloads or backup metadata goes into diagnostic logs. No mandatory account, backend or network validation is required.

## 6. Persistent state versus derived state

| Persistent/backup-eligible | Derived/transient; excluded from backup/contact metadata |
|---|---|
| One profile and stable profileId, all 15 slots including hidden data | Unsaved N04/N05 drafts and picker grants |
| Complete supported visibility map | N01 presentation and native action URI values |
| Validated app-owned images/key | Contact projection, readable export preview and serialized vCard |
| Saved theme/accent | QR matrix/image, URL QR and transient export files |
| Schema version and aggregate createdAt/updatedAt | Share mode/navigation/focus, generationId/stateRevision, temporary read grants, operation journal |

Contact exports contain only the allowlisted included contact projection, never an AppData dump. Backups contain the complete saved application state, including contact-hidden/card-hidden values. .vcf and QR images cannot restore the application.

## 7. Projection and snapshot invariants

Use a saved-state read snapshot identified by `(generationId, stateRevision, exportContractVersion, mode, action)`. Apply field eligibility and export visibility **before** formatting, NOTE composition, URL deduplication, preview generation or vCard serialization. Keep field provenance in the derived projection to ensure no unsupported field is indirectly added to an eligible property.

One approved supported text projection feeds both contact QR and .vcf, with identical property semantics. Their size/geometry gates differ. S01 displays actual supported included values for the requested action and a summary of format omissions without showing excluded values. Mandatory file/contact-image confirmation binds that snapshot and action; if it becomes stale, refresh and ask for action-specific confirmation again. Initial valid contact QR remains immediate, with voluntary S01 review only; no first-display gate is added.

Public-key download is its own conditional N01 action. It is not an override for excluding the key from contact formats. Web QR encodes only the configured hosted URL and clearly remains outside local contact-field visibility control.

## 8. Defaults, clearing and migration

No initial placeholder profile is saved. A fullName-only profile is valid; contact methods/images are optional. Defaults for empty/new fields are set in the privacy matrix; absent values never produce working-looking fake actions. Clearing an optional value keeps its supported visibility preference, but nothing is rendered/exported until a valid value is present again. Backups preserve that preference.

Reject unknown saved enum values or unsupported schema versions before restore; do not fall back to a default that might reveal data. Distinguish application schema version, backup format version and export contract version. Version-1 A2 and backup inputs remain readable with the documented phone defaults; version-2 writes include the additive metadata. No phone display text is rewritten on load, and invalid legacy numbers are preserved without fabricated E.164 data. Future schema changes need explicit migration specifications preserving privacy choices, asset ownership and one-profile cardinality. A newer unsupported backup leaves valid current data untouched.
