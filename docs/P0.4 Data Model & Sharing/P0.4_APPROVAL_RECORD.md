## Three binding approval conditions

### Condition A - Required full name and privacy defaults

- One mandatory fullName field is always shown on the card and always included in contact exports. Both visibility settings are locked true.
- Optional export-eligible fields are excluded from contact export by default. Eligible optional fields retain independent card-display and contact-export controls.
- The exact existing 15-slot field inventory, validation limits and eligibility/default matrix are retained. Image and public-key contact-export restrictions remain binding.
- Full-app backups include complete saved information, including hidden fields/preferences and supported assets.
- P0.4-02 is approved with this policy explicitly accepted. No anonymous-card mode, placeholder name, hidden-name fallback or new UI destination is authorized.

### Condition B - Provisional vCard 3.0

- vCard 3.0 is the approved initial implementation target, provisional with respect to recipient compatibility. Preserve the documented property mapping, including FN and empty structured N; the current standard is not changed by this finalization.
- P0.5 must retain the documented vCard 3.0 versus 4.0 evaluation and implementation considerations.
- P0.6 must include the existing paired comparison matrix: actual Pixel contact import, QR scanning/contact-save behavior, identity handling, Unicode, field fidelity and privacy exclusions. Record actual recipient/app/OS results; standards conformance alone does not prove compatibility.
- Any proposed change from 3.0 to 4.0 requires explicit project-owner approval before implementation. No format selector, automatic format fallback or additional name fields is authorized.
- Recipient compatibility remains unverified. These future obligations do not authorize P0.5 or P0.6 to start.

### Condition C - Modern OpenPGP feasibility

- The modern OpenPGP direction and existing bounded v4/v6 RSA/elliptic-curve compatibility matrix are conditionally approved. Preserve algorithm-specific signing/encryption requirements, version-specific fingerprints and the separate asset SHA-256 digest. Every unverified pairing remains **REQUIRES FEASIBILITY VALIDATION**.
- P0.5 must evaluate maintained parser/verifier candidates for Android suitability, licensing, resource bounds, key-version/algorithm support, required cryptographic validation and revocation handling. Bouncy Castle and PGPainless remain researched candidates; no library, artifact, dependency, Gradle or SDK version is selected here.
- P0.6 must verify supported algorithms, fingerprints, signatures, bindings, public-only input, expired/revoked behavior and unsupported-format rejection.
- No custom cryptographic parser or unverified compatibility claim is authorized. Private/secret-key material is unconditionally rejected, including mixed input; no silent public extraction/conversion.
- Supported, structurally and cryptographically data-valid expired/revoked public keys remain eligible for saved storage and full-app restoration; currently unusable actions remain unavailable. Unsupported historical formats reject the entire restore candidate without replacing existing data.
- Any reduction in the approved matrix requires explicit project-owner approval before implementation. If safe implementation is infeasible, document and escalate rather than silently removing support or weakening validation.
- Implementation feasibility remains unverified. Unusual revocation/authorized-revoker classification is deferred technical feasibility work, not permission to invent acceptance behavior.

## Previously settled public-key policies

1. **Revoked-key retention:** Preserve supported, structurally and cryptographically data-valid public-only keys with verified revocation in saved profile data and full backups/restores, including complete supported material needed to represent and verify revocation. Do not reject a valid complete backup solely because the key is revoked. Do not present revoked material as currently usable for encryption. Restore preserves exact saved bytes without identity rewrite, key substitution or stripping; existing N01/N04 inline status and N04 replacement/removal remain the only UI paths.
2. **Unsupported historical formats:** Unsupported key versions, algorithms or packet structures reject the whole candidate before S02/replacement. Explain unsupported public-key format and preserve the current valid profile, appearance, images, visibility and saved key unchanged. No opaque import, partial replacement, automatic conversion or key removal. Future compatibility/migration support is not promised for v1.0.

Structural validity, required cryptographic integrity, current usability and identity trust are distinct. Verified revocation follows supported OpenPGP semantics, not a filename/text label. Successful signature verification does not independently establish real-world identity. Primary versus subkey revocation retains the existing component-specific policy in the asset contract. Public keys remain excluded from contact QR and .vcf; normal public-key actions require saved, present, display-enabled and currently usable material.
