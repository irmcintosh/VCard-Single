## 1. Container and limits

**Owner-approved Milestone 1.11 Step 4E:** New backups retain formatVersion 1, the same ZIP/entry/asset/inventory rules, and use appSchemaVersion/data schemaVersion 3. The flat profile adds nullable firstName, middleName, lastName and matching visibility entries `{showOnCard:null, includeInContactExport:boolean}`. Hidden components are preserved in full backups. Strict schema-1/2 readers accept their original exact keys and default the new fields to absent/export off. Current schema 3 requires its exact keys/types, so corruption is not treated as an older/missing field. Explicit restore preserves identity, images, phone metadata and privacy and upgrades to schema 3; the A2 and durable recovery/deletion protocols are unchanged. Older APKs cannot read schema 3 or its backups; do not claim downgrade safety.

Specify an app-specific **ZIP container using STORE entries only**, extension `.vcardnative.zip`, MIME `application/zip`, suggested generic filename `vcard-native-backup-YYYYMMDD-HHmmss.vcardnative.zip` using a documented UTC timestamp. A name collision is resolved by the user/provider, never silent overwrite. This archive is an application backup, not a `.vcf`, system-wide Android backup or contact-import file.

The ZIP format reference is [PKWARE APPNOTE](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT); restrictions below are this application's approved narrower contract, not a claim that ZIP universally forbids other features. STORE avoids nested compression and adds little cost for already-compressed canonical JPEG/PNG assets. No archive encryption, compression choice UI, automatic synchronization, backup history, merge restoration or automatic pre-restore backup is introduced.

| Resource boundary | Approved maximum / rule |
|---|---|
| Input archive bytes | 24 MiB (25,165,824 bytes) |
| Sum of actual entry bytes | 20 MiB (20,971,520 bytes), regardless of declared headers |
| Entry count | 2–5 files, only allowlisted basenames, no directory entries |
| manifest.json | 64 KiB (65,536 bytes) |
| data.json | 512 KiB (524,288 bytes) |
| One of profile.jpg/profile.png and one of cover.jpg/cover.png | 8 MiB (8,388,608 bytes) each; canonical role geometry from asset contract |
| public-key.asc | 64 KiB (65,536 bytes); supported public-only key contract |
| JSON depth | <=16 container levels; aggregate field/cardinality limits still apply |

Use single-volume ZIP32, method 0 (STORE), no encrypted entries, ZIP64, data descriptors, extra fields, archive/file comments, symlinks, device entries, executable/self-extracting prefixes or trailing appended data. Writer may stage bytes to know sizes/CRC before serialization; P0.5 selects how. Reject inconsistent local/central headers, duplicate names, overlaps/offset overflow, truncated structures or unsupported feature flags. Do not loosen parsing because a generic ZIP viewer opens the file.

## 2. Allowlisted entries and schema

`manifest.json` and `data.json` are mandatory. For a non-null profileImage, exactly one of `profile.jpg`/`profile.png` is required; for coverImage, exactly one of `cover.jpg`/`cover.png`; for publicKey, `public-key.asc`. A null reference permits neither role variant. Allowed image extension/MIME pairs are .jpg=image/jpeg and .png=image/png; both variants for one role are invalid even if hashes match. The basename allowlist thus has seven possible names but any valid archive still has only 2-5 entries. No other path is valid. All names are fixed ASCII basenames: reject slash, backslash, absolute paths, drive prefixes, dot segments, NUL, case variants and duplicate normalized names. Never concatenate an input filename into a destination path. Stage into generated internal locations keyed by validated logical IDs, not archive paths. [Android's ZIP path-traversal guidance](https://developer.android.com/privacy-and-security/risks/zip-path-traversal) explains why extraction boundaries must be enforced.

Manifest top-level keys are exactly `format`, `formatVersion`, `appSchemaVersion`, `createdAt`, `files`. Values: format `vcard-native-backup`; `formatVersion` integer 1; `appSchemaVersion` integer 1 (legacy), 2 (phone metadata), or 3 (current structured names); createdAt parseable UTC timestamp; files a list of exact entry records `{path, mediaType, byteLength, sha256}`. It lists every entry except manifest.json once, in fixed order data.json, selected profile.jpg or profile.png, selected cover.jpg or cover.png, public-key.asc. Hashes are lowercase 64-character SHA-256 hex; byteLength is an integer actual byte count. No self-hash cycle is included.

data.json is the complete saved `AppData` object: exact root keys `schemaVersion`, `profile`, `appearance`, `metadata`; schemaVersion 1, 2, or 3 and a non-null profile are required. Version 1 uses the legacy profile-key set. Version 2 additionally requires `phoneRegion`, `includeCountryCodeWhenSharing`, and nullable `phoneNumberE164`. Current version 3 additionally requires the explicit nullable `firstName`, `middleName`, and `lastName` fields and their strict visibility entries; current backups use version 3. A version-1 backup remains valid and receives only the documented default phone metadata while retaining its phone display value; version 2 already contains phone metadata. Both legacy versions default structured-name components to absent/export off when upgraded to current data. Profile otherwise has exactly the inventory fields plus profileId and visibility in the data model. `professionalLinks` has all three fixed keys, nullable. `visibility` has all 15 slot keys, with exactly the two supported/null settings for each. `appearance` has only theme/accent; metadata only createdAt/updatedAt. Assets use the ImageAsset/PublicKeyAsset metadata fields defined in the model; raw bytes live in their matching ZIP entry, not base64 fields, arbitrary paths or external URIs. Media types are application/json, image/jpeg, image/png, application/pgp-keys as appropriate. Non-null ImageAsset includes canonicalizationPolicyVersion=1 and actual codec geometry; PublicKeyAsset includes format=openpgp-public-armored, keyVersion=4 or 6 and primaryAlgorithm from the bounded matrix, plus the correct 40/64-hex fingerprint. Recompute these from bytes, never trust the labels alone.

JSON is UTF-8 without BOM, using [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html). Approved strict parsing rejects duplicate object keys, unknown keys, wrong/null types where non-null is required, unsupported enums, invalid Unicode and nonfinite/fractional version/length values; bound actual bytes/depth before constructing an aggregate. Do not ignore an unknown visibility flag that might change disclosure. Unknown format/schema versions are not interpreted as version 1.

## 3. Integrity and semantic validation

Verify ZIP CRC and streamed actual sizes, then SHA-256 over each entry's exact bytes against manifest, then all model/privacy/asset constraints and reference relationships. [NIST's Secure Hash Standard](https://csrc.nist.gov/pubs/fips/180-4/upd1/final) is the digest reference. Hashes/CRC detect corruption, **not authenticity**: an attacker can change both file and manifest. No signature, password protection or encryption promise is made; safely validate even a hash-consistent package as untrusted input.

Each non-null asset reference requires exactly its allowlisted file and matching media type/byteLength/SHA-256; dimensions/fingerprint must match recomputation. Asset IDs must be valid unique UUIDs across referenced assets. Unreferenced files, missing files and mismatched references reject the entire restore. Do not copy live permission grants or stored absolute paths. Validate public-only key structure/support and required signature/binding mathematics separately from current encryption usability. Supported expired key data is not corrupt merely due to expiration; preserve it, recompute usability and disable the current action where unusable. Preserve supported data-valid certificates with verified revocations as historical data under the owner-approved retention policy; revocation alone must not fail a valid complete backup. A revoked primary disables all candidates, while subkey-only expiry/revocation is evaluated per component and never makes that affected component usable. Preserve exact saved bytes, including complete supported material needed to represent and verify revocation; no identity rewrite, key substitution, stripping or re-encoding during restore. Required structure/cryptographic integrity, current usability and identity trust are separate: signature verification does not establish real-world ownership. Unknown/unverifiable relevant revocation/critical semantics remain P0.5/P0.6 technical feasibility questions and cannot pass validation until safely classified under the supported contract. Unsupported historical versions/algorithms/packet structures, private packets, malformed keys, invalid required bindings or integrity mismatches reject the full restore. Never silently omit/delete the key. Validate canonical JPEG/PNG against exact basename/MIME/codec, metadata, role dimensions, canonicalizationPolicyVersion and hash; restore exact retained bytes without re-encoding. Reconstruct app-owned assets from bytes.

Require exactly one saved profile, valid fullName, locked essential visibility, supported optional values and known appearance enums. Hidden data is still validated. Metadata timestamps must parse; no clock order is trusted as integrity proof. Generation/revision, QR/files, unsaved drafts, grants, navigation and operation journals are excluded and regenerated locally. A .vcf renamed to ZIP or unsupported older/newer app format is rejected without replacing current state.

### Owner-approved historical-key policies and technical feasibility

Expiration, verified revocation, supported structure/cryptography and archive corruption are distinct. Integrity hashes cannot turn an unsupported key into a supported one, and an expired but data-valid key does not make a hash-consistent package corrupt. Apply the [asset compatibility/validity contract](P0.4_PUBLIC_KEY_AND_IMAGE_CONTRACTS.md) identically in model/input/restore handling. Preserve historical bytes and the saved visibility preference, but never restore a cached usability decision or enable a currently unusable action. All-or-nothing replacement still covers the whole profile and assets.

The owner has approved both retention of supported data-valid verifiably revoked certificates and rejection of unsupported historical formats. Every restored key must satisfy the explicit supported asset contract; unsupported versions, algorithms or packet structures cannot be imported as opaque bytes. Reject such a candidate before S02/replacement and explain that the backup contains an unsupported public-key format. Preserve the existing valid profile, appearance settings, images, visibility preferences and saved key unchanged; no partial replacement, automatic conversion, key stripping or substitution. No misleading success state is allowed. Valid candidates still follow the unchanged S02 review and explicit confirmation workflow. A future application version may introduce explicitly reviewed compatibility/migration support; v1.0 makes no such promise. Unusual cases such as unresolved authorized-revoker semantics remain technical feasibility questions for P0.5/P0.6, not permission to invent acceptance behavior. No quarantine destination or private-key conversion is allowed.

Format/schema 1 is approved as a specification; no deployed backup compatibility/migration is claimed. The asset-free synthetic example below is unchanged. Future asset-bearing examples must use the revised ImageAsset/key metadata and the exact one-variant-per-role name rules.

## 4. Creation and cancellation

F09 captures one coherent saved aggregate plus its immutable asset bytes; creation can use that snapshot even if subsequent saved changes occur, but label its capture time truthfully. It must not mix profile from one revision with images/visibility from another. With no saved profile, N06 explains Create backup is unavailable; Restore remains available through first-run N04. No empty fake profile is invented.

Before location choice, N06 explains that the file contains full saved data/assets, including hidden values and the key's embedded identities. Validate snapshot completeness, build/stage bounded bytes and write to a user-chosen destination. Local destinations must work offline. Selected cloud providers can require internet; that is external storage behavior, not app sync.

Cancellation before a write leaves app state unchanged. Success requires a fully written/closed output; an external provider may not support atomic replacement, so a cancelled/failed external write can leave an incomplete file. Best-effort remove partial output where possible and explain failure without claiming a valid backup. Do not alter existing app data. P0.5 chooses staging/file access/provider handling under [Android document-access guidance](https://developer.android.com/training/data-storage/shared/documents-files), not a picker implementation in this milestone.

## 5. Restore state machine and S02 review

**Milestone 1.11 owner-approved recovery extension (2026-11-01):** Existing archive format and schema-1/schema-2 acceptance remain unchanged. When the current repository is unavailable, independently validate the selected backup and use S02 for explicit recovery confirmation, not an empty-profile restore. Revalidate staged bytes and recovery context, construct a verified separate A2 replacement, preserve unavailable local data intact as private evidence, and install only the candidate named by durable intent. Invalid input/cancellation cannot modify existing state. Restart may resume that previously confirmed recovery; it must not select an older profile or a new backup automatically. Retained evidence is excluded from ordinary backup creation, does not expire automatically, and uses internal storage. See the later [storage/recovery protocol authorization](../P0.5%20Technical%20Architecture%20%26%20Feasibility/P0.5_STATE_STORAGE_AND_RECOVERY.md).

```text
N06 choose input → bounded internal staging → container/hash/model/asset validation
  invalid/unsupported/cancelled → N06 explanation; old saved state unchanged
  valid → S02 review → cancel/dismiss → N06; old state unchanged
                    → explicit replacement confirmation
                    → committed progress at N06 → verified success → refreshed N01
                                              → failure/recovery → valid old or complete new state
```

Validation never modifies the live saved aggregate. Keep a validated staged copy immutable while S02 is open; recheck digest/identity before commit. If local saved state changes between review and commit, refresh review of what will be replaced and require confirmation again. S02 summarizes one profile, presence of images/key, theme/accent and inclusion of hidden data, with an inline historical-key unusable/expired/revoked note when applicable; show safe bounded file-supplied labels as untrusted text, not raw paths or guaranteed author identity. No new metadata fields/screens are required.

Explicit action is Replace local data and restore, or Restore profile when none exists. Before confirmation, Back/cancel leaves current state unchanged. After commit begins, approved N06 progress temporarily prevents navigation/dismissal with an accessible explanation. This does not replace safe recovery on process termination/device restart. No third dialog is added.

P0.5 must provide an atomic or recoverable aggregate switch including all bytes/settings. Keep old valid state until the new aggregate/assets are durably ready; on failure roll back to it. After interruption, startup must resolve either the complete old state or complete new state, never a hybrid/dangling asset set. New generation/revision invalidates all previous export contexts. User-visible success is emitted only after the committed state is confirmed; uncertainty triggers reconciliation, not automatic re-application. Transient internal rollback/staging is correctness machinery, not a user-facing backup history/undo feature.

## 7. Version evolution and verification obligations

Support formatVersion=1 with appSchemaVersion 1 (legacy), 2 (phone metadata), and 3 (current structured names). Version-1 input receives the documented default phone metadata; versions 1 and 2 default structured-name components to absent/export off. Current writers emit appSchemaVersion 3 while retaining the ZIP/container formatVersion 1. A migration reads only an explicitly supported version into staging, validates all fields/assets/privacy flags, and only then offers S02; the original file and current saved state stay untouched until confirmation. The current reader does not rewrite the selected archive; a successful restore commits current schema 3. Unsupported future input explains the need for a compatible version and preserves current data.

P0.6 must plan round trips including all fields/visibility/theme/accent/images/key; no-profile restore; corrupt/missing/duplicate entries; malicious names/headers/overlap/CRC/hash; huge declared versus actual data; unknown versions/fields/enums; malformed JSON/duplicate keys; invalid/private/unsupported keys, preserved expired keys, retained supported verifiably revoked keys with unavailable actions, whole-candidate unsupported-history rejection and unresolved authorized-revoker cases; canonical JPEG/PNG, role-variant duplicates, metadata and image bombs; provider denial/full storage/cancellation; state changes during review; and interruption at every replacement boundary. Verify real restart recovery and exact privacy restoration, not merely archive readability. These are required evidence categories, not detailed implemented tests or passed results.

Backups are potentially sensitive plaintext files. Keep internal staging app-private, never log contents/metadata, minimize and safely clean rejected/interrupted staging, and state that exported copies are user-controlled. Full backup is distinct from contact-export restrictions and from recipient .vcf import. This phone-metadata addendum records the owner-approved Milestone 1.10 extension; earlier P0.4 approval status applies to the original specification.
