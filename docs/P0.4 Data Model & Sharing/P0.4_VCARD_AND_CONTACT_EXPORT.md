## 1. Standard and conditional compatibility approval

Retain **vCard 3.0 as the approved initial implementation target, provisional for recipient compatibility**, a deliberately small text-only profile, for both contact QR and .vcf. [RFC 2426](https://www.rfc-editor.org/rfc/rfc2426.html) defines that historical format; [RFC 2425](https://www.rfc-editor.org/rfc/rfc2425.html) supplies its directory framing/folding rules. vCard 4.0 in [RFC 6350](https://www.rfc-editor.org/rfc/rfc6350.html) is the newer standard and obsoletes those RFCs; it is a serious alternative, not unsupported by definition.

The 3.0 choice is a conservative interoperability choice for legacy contact readers, not a measured superiority claim. Official [AOSP source inventory](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/android-30/+/refs/heads/androidx-lifecycle-release/com/android/vcard) identifies versioned vCard parser classes; it does not certify the behavior of the current proprietary Pixel Contacts app. Individual current AOSP parser pages could not be fetched during research. [Google's Android Contacts instructions](https://support.google.com/contacts/answer/15147365?co=GENIE.Platform%3DAndroid&hl=en) document importing VCF files, but do not specify version/property fidelity. Actual app versions and results remain unverified.

### Targeted 3.0 versus 4.0 comparison

This table records the original full-name-only planning baseline. Step 4E's explicit structured-name mapping in section 2 supersedes its empty-N-only assumption; no production 4.0/MECARD alternative is implemented.

| Concern | Existing provisional 3.0 profile | 4.0 evaluation alternative |
|---|---|---|
| Identity | VERSION, FN and N required by RFC2426; current mapping uses FN plus empty N:;;;; | RFC6350 requires FN and VERSION:4.0 (immediately after BEGIN); N optional, so the one full-name input need not invent structured parts |
| Full-name fidelity | Empty N might import/sort poorly; standards framing alone does not settle recipient behavior | FN-only better reflects collected data semantically; receivers/scanners may still mishandle recognition/import |
| Encoding/folding | Application chooses UTF-8 and conservative 75-octet folds under the historical line-folding rules | UTF-8 mandated ; 75-octet folding with intact multibyte characters specified explicitly |
| Phone | TEL:{canonical number} with no invented classification | Compare TEL;VALUE=uri:tel:{canonical number}; do not reuse a 3.0 property string blindly |
| Email | EMAIL;TYPE=INTERNET:{mailbox} | Compare EMAIL:{mailbox}; no need for the legacy INTERNET parameter |
| URL/ORG/TITLE/NOTE | Existing filtered text/URI mappings | Same user fields, using 4.0 property/value/escaping rules; preserve all included values, no added name fields |
| Android/QR compatibility | Legacy-format hypothesis, not a demonstrated advantage | Modern standard, not a demonstrated universal advantage; same fixtures must be tested |

References: [RFC2426](https://www.rfc-editor.org/rfc/rfc2426.html) and [RFC6350](https://www.rfc-editor.org/rfc/rfc6350.html). The official [Android Contacts VCF workflow](https://support.google.com/contacts/answer/15147365?co=GENIE.Platform%3DAndroid&hl=en) does not state version/property fidelity or QR recognition. Current Pixel/other-recipient behavior has not been tested. Retaining 3.0 provisionally avoids an unreviewed cross-document format change, not because 3.0 has been proved more compatible. FN-only 4.0 remains the preferred semantic alternative to evaluate if empty N fails.

Do not expose a 3.0/4.0 format chooser or separate sharing presets. P0.4-04 is approved provisionally under condition B. P0.5 must retain the documented 3.0/4.0 evaluation and implementation considerations; P0.6 must execute the paired compatibility matrix below, including actual Pixel contact import, QR scanning/contact-save behavior, identity handling, Unicode, field fidelity and privacy exclusions. Standards conformance alone does not prove compatibility. Any change from 3.0 to 4.0 requires explicit project-owner approval before implementation. No sender-side .vcf profile import is introduced.

## 2. Allowlisted field mapping and order

Every optional row is emitted only if saved, valid, present and `includeInContactExport = true`. FullName is required/locked under the approved privacy policy. Filter before forming composite properties; never serialize the whole profile. Fixed property ordering below also determines preview ordering.

| Source | Property / exact contract |
|---|---|
| Constant framing | BEGIN:VCARD, then VERSION:3.0 |
| Included firstName/middleName/lastName | When any export-enabled component is present: `N:{escaped lastName};{escaped firstName};{escaped middleName};;`, then `FN:{escaped fullName}`. Excluded/absent components are empty. Family/Given/Additional/Prefix/Suffix are exactly five components |
| fullName with no included name components | Legacy order `FN:{escaped fullName}`, then `N:;;;;`; never invent components from fullName |
| organization | `ORG:{escaped organization}` as a single component; no invented department |
| professionalTitle | `TITLE:{escaped professionalTitle}` |
| phone | `TEL:{formatted phone}` using the saved country-code preference: international form when enabled, selected-region national form when disabled; Contact Preview and QR use this exact value. No invented HOME/WORK/CELL classification |
| email | `EMAIL;TYPE=INTERNET:{normalized mailbox}` |
| website | `URL:{serialized website URI}` |
| professionalLinks.linkedin, github, otherProfessional | Repeated `URL:{serialized URI}` in fixed category order; no receiver-specific labels/X-properties |
| location and/or biography | One NOTE assembled from eligible lines in order: `Location: {location}`, then `Biography: {biography}`, joined with LF before TEXT escaping |
| Constant ending | END:VCARD, final CRLF |

Empty `N` remains intentional for profiles without explicit, export-enabled name components. FN always contains the unchanged saved Full Name; structured edits never overwrite it. Some camera recipients handle empty N poorly, including observed iPhone company-name fallback. Explain this legacy limitation and let the owner supply components; never split names automatically or place Full Name into Family. Contact Preview shows Full Name followed by individually labeled included First/Middle/Last Name rows, all from the same filtered projection. Prefix/Suffix remain empty.

Do not emit ADR/GEO for free-form location, KEY, PHOTO, LOGO, hostedProfileUrl, appearance, profileId, generation/revision, timestamps, UID, private file paths, source URIs, MIME cache locations or unsupported values. Location/biography share NOTE but remain independently filtered; labels do not include excluded values. Professional category labels are not guaranteed to survive as contact labels.

## 3. Text and URI serialization

Emit UTF-8 bytes without BOM, CRLF content-line delimiters and a final CRLF. Fixed property/parameter names are application constants, never user strings. For TEXT values escape backslash as `\\`, comma as `\,`, semicolon as `\;` and logical newline as `\n`; colon inside ordinary TEXT is not a property separator requiring blanket escaping. Escape each structured component before inserting its semicolon separators. Input line breaks cannot inject properties.

URI values are validated/serialized absolute ASCII URIs under the privacy policy, with Unicode host/path represented using IDNA/percent encoding as appropriate. Do not apply generic TEXT backslash escaping to a URI or percent-decode/rewrite it at export time. EMAIL is a validated single ASCII mailbox, not a raw contact-line fragment. Keep Unicode names/biography as UTF-8 without transliteration.

Apply line folding after value escaping and UTF-8 encoding: require at most **75 octets per physical line**, excluding CRLF, continuing with CRLF plus one space; continuation prefix counts toward that physical-line budget. Split only at UTF-8 character boundaries and never inside an escape pair or percent-encoded triplet. This application octet bound is a conservative implementation policy for the historical RFC wording, not a claim that RFC 2426 uses the exact newer RFC 6350 octet language. Unfolding must reproduce the logical lines/values exactly.

One phone/email only; multiple contact URL properties are supported. Format the canonical E.164 phone with the saved country preference after Contact Export filtering; do not change inclusion or My Card visibility based on formatting. For a parseable phone, Contact Preview row, QR payload and `TEL` property all use the same libphonenumber INTERNATIONAL or NATIONAL string. Preserve the legacy digit-derived fallback for an unparseable version-1 phone without inventing a country code. After export filtering, deduplicate identical serialized URLs, retaining provenance of all included contributing slots for preview. Never consult excluded slots to create labels/fallbacks. Identical text appearing in another deliberately included field is not semantic redaction.

## 4. Preview, filename, MIME and handoff

S01 is required before .vcf creation/sharing and before contact QR image save/share; it binds the requested action and current saved snapshot. Voluntary review before initial QR presentation remains voluntary. Show actual human-readable included data/format omissions before serialization, with no export-hidden values. If saved data changes, discard the pending approval, refresh and request confirmation again. No file is created before the required action-specific confirmation.

Use generic filename **vcard-native-contact.vcf**, avoiding personal names in filenames, and MIME **text/vcard** without a MIME version parameter in the Android share type. [IANA's registration](https://www.iana.org/assignments/media-types/text/vcard) covers identifying vCard data of different versions and records older aliases. Actual VERSION:3.0 in the file remains authoritative. `text/x-vcard` is a legacy compatibility candidate to investigate, not an automatic fallback or additional UI option.

After confirmed creation, hand the file to native Android Sharesheet using an app-owned, narrowly exposed `content://` URI and temporary read access, not `file://` or broad persistent access. [Android secure-file-sharing guidance](https://developer.android.com/training/secure-file-sharing/share-file) supports that access boundary. P0.5 chooses the provider/integration/cleanup mechanism; no manifest or dependency is selected here. Return/cancel never proves recipient delivery/import. The file is contact-only, never called a full-app backup.

Limit serialized .vcf to **64 KiB (65,536 bytes)** as an application guard, counting folding/delimiters. Over-limit or invalid serialization returns an inline failure with editing/retry; do not truncate, silently omit an included supported field, append another contact or auto-switch standards. A contact that cannot fit a QR can still use .vcf if this independent limit passes.

## 5. Synthetic payload examples

Examples use fictional names, reserved example domains and no real recipient data. Code blocks use visual newlines; actual exported bytes must use CRLF. They illustrate the approved serialization specification, not successful recipient imports.

Name only (the new-profile optional-export defaults):

```text
BEGIN:VCARD
VERSION:3.0
FN:Example Person
N:;;;;
END:VCARD
```

Selected professional/contact values (all shown rows explicitly export-enabled):

```text
BEGIN:VCARD
VERSION:3.0
FN:Zoë Example
N:;;;;
ORG:Example Research\, Inc.
TITLE:Engineer\; Research
TEL:+12025550123
EMAIL;TYPE=INTERNET:zoe@example.invalid
URL:https://example.invalid/work
URL:https://example.invalid/professional
NOTE:Location: Example City\nBiography: Builds tools\, carefully.
END:VCARD
```

If location is excluded, the NOTE becomes only `NOTE:Biography: Builds tools\, carefully.`; if both location and biography are excluded, omit NOTE entirely. Hidden organization never becomes a TITLE/NOTE fallback. This example is not a ready-made file or test result.
