## 1. Shared text rules and length limits

Count Unicode scalar values after normalization, not UTF-16 code units or bytes. Require well-formed Unicode; preserve meaningful scripts, accents, emoji and internal spaces. Normalize Unicode to NFC, trim outer whitespace, and map empty/whitespace-only optional values to null. Preserve the resulting saved display value separately from URI/serialization derivations. Do not force case on personal text.

Single-line fields reject CR/LF, NUL, DEL and other C0 controls; multiline biography normalizes CRLF/CR to LF, permits LF, replaces tabs with spaces and rejects other C0/DEL controls. Reject unpaired surrogates. Reject explicit bidi embedding/override/isolate control characters U+202A–U+202E/U+2066–U+2069 in contact fields to reduce spoofing; ordinary RTL letters and joiners remain valid. This restricted policy is an owner-approved tradeoff, not a claim that all such text is malicious. Never silently truncate an overlength value.

| Slots | Approved scalar limit / policy |
|---|---|
| fullName | 1–160 after trim; only mandatory user field |
| firstName, middleName, lastName | 160 each, optional single-line; same NFC/trim/control policy as Full Name; never inferred |
| professionalTitle, organization, location | 160 each, optional |
| biography | 2,048, optional multiline |
| phone | 32 display characters, optional; canonical rules below |
| email | 254 ASCII serialized mailbox characters, optional; local part <=64 |
| website, each fixed professional link, hostedProfileUrl | 2,048 serialized URI bytes each after normalization |

Field limits apply to Save and restore alike. Image/key/file/archive limits are in their owning documents. Overlength errors retain the user's draft and identify the affected field. No new confirmation dialog or screen is introduced.

## 2. Phone, email and URL policies

**Phone — owner-approved Milestone 1.10 refinement:** One optional value; accept ASCII digits, space, `+`, `-`, `.`, `(` and `)` only. A plus may occur only at the start after trimming. Use Google's `libphonenumber` metadata to parse and validate against the selected supported country/region; do not substitute hand-written country rules or claim number reachability. Suggest the initial region from the device locale only, with no location permission, and allow explicit region selection in onboarding and Edit Profile. Preserve the entered display value and persist its canonical E.164 representation separately so export formatting never loses the full international number. Extensions, pause/wait characters and alphabetic vanity numbers remain unsupported; explain correction instead of guessing or discarding an extension. Call/SMS use the same saved number; no separate SMS field.

The optional `includeCountryCodeWhenSharing` preference defaults to `true`. If true, Contact Export, its preview, QR and .vcf use libphonenumber's INTERNATIONAL representation; if false, they use its NATIONAL representation for the selected region. The toggle affects formatting only: it never changes `showOnCard`, `includeInContactExport`, or whether a phone row is included. My Card visibility and Contact Export inclusion remain independent. Show the formatted value before saving the setting and show that same value in Contact Preview. New profile edits that cannot be parsed fail validation without replacing the prior profile.

Legacy A2 schema-version-1 profiles and version-1 backups remain readable. Preserve their original phone display text; infer a region from a valid international number, otherwise suggest the current device locale, and derive E.164 in memory when parsing succeeds. Do not rewrite the saved display text during load. Milestone 1.11 Step 4E adds schema 3 structured names while retaining schema 2 phone metadata and readers for both older schemas. A nonempty legacy number that the library cannot parse remains intact with no fabricated E.164 value, and retains the prior digit-derived export fallback until the user edits or removes it. Re-saving other fields must not silently change that legacy number.

**Email:** One mailbox, not a display-name/address list. Require an ASCII dot-atom local part (case preserved) plus a valid domain converted to its ASCII IDNA form and lowercased. Reject empty labels, leading/trailing or consecutive dots in local part, whitespace, controls, quoted local parts, comments and multiple `@`. Atom characters are ASCII letters/digits and `!#$%&'*+-/=?^_` plus backtick, braces, vertical bar and tilde; dots separate nonempty atoms. This includes `+` and apostrophe. This deliberately narrower contract excludes SMTPUTF8 local parts and unusual valid quoted mailboxes; do not describe it as full RFC email support. Domain syntax validation is local, no DNS/MX check or deliverability assertion. Show the normalized saved address before Save completes.

**URLs:** Require explicit absolute scheme/host; never prepend a scheme silently. website permits `https` or `http`; the three professional-link slots and hostedProfileUrl require `https`. Reject credentials/userinfo, empty/malformed host, whitespace/control characters, backslashes, invalid percent escapes, `file`, `content`, `javascript`, `data`, `intent` and other schemes. Accept valid ports 1–65535, paths, query and fragment; preserve their case/meaning. Lowercase scheme/host, IDNA-encode domain hosts, percent-encode non-ASCII path/query/fragment code points as UTF-8 URI octets while preserving existing valid percent triplets and URI delimiters; do not fetch or shorten URLs. Hostnames must pass IDNA2008 validity checks; reject disallowed input rather than silently applying a transitional compatibility mapping. A configured hosted address must be intended as a public URL; syntax alone cannot prove public accessibility. No automatic query/tracking stripping or HTTP→HTTPS rewrite. Validation is not reachability/certificate/current-content verification.

Fixed categories are `linkedin`, `github`, `otherProfessional`, in that display/export order. Category is a label, not a verified provider identity; no hardcoded hostname restriction beyond URL safety and no OAuth/account validation. A URL in a LinkedIn slot may still be incorrect; user retains responsibility. No arbitrary label editor or unlimited link list is added.

## 3. Visibility eligibility and approved defaults

These defaults are applied to a new profile/previously absent supported field; existing saved preferences survive clearing and re-entry. Missing values never render/export. A disabled/non-applicable setting must explain support, not masquerade as a working switch.

| Inventory slot | Show on card | Include in contact export | Backup contents |
|---|---|---|---|
| fullName | true, locked | true, locked | Saved name and locked settings |
| firstName, middleName, lastName | Not applicable; Full Name remains card identity | false independently, user-enable per component | All saved values and preferences, including excluded components |
| professionalTitle | true | false | Full saved value/settings |
| organization | true | false | Full saved value/settings |
| biography | true | false | Full saved value/settings |
| location | true | false | Full saved value/settings |
| phone | true | false | Saved display value, canonical E.164 value when valid, selected region and country-code export preference |
| email | true | false | Saved normalized value/settings |
| website | true | false | Saved URL/settings |
| professionalLinks.linkedin | true | false | Saved URL/settings |
| professionalLinks.github | true | false | Saved URL/settings |
| professionalLinks.otherProfessional | true | false | Saved URL/settings |
| profileImage | true | null — unsupported | Owned image bytes/reference and display setting |
| coverImage | true | null — unsupported | Owned image bytes/reference and display setting |
| publicKey | false | null — unsupported | Data-valid public-only key bytes/reference and display setting, including supported historical keys |
| hostedProfileUrl | null — configuration, not a card field | null — separate web-mode configuration | Saved hosted URL |

Full name is approved as essential/non-hideable because the card and standards-compatible contact export require a usable identity. There is no fallback to a hidden field or invented name. N04 should explain the locked identity policy; both independent controls remain editable for eligible optional text fields. The owner explicitly accepted this choice/default policy in P0.4-02 under condition A; both full-name settings are locked true. No contact method is required; initial contact QR may contain only the name.

Private-by-default contact export does not mean invisible-by-default card: review the explicit difference during N04 setup. An optional field can be shown/not exported, hidden/exported, shown/exported or hidden/not exported. Do not copy one setting into the other on Save. The public-key display setting governs its N01 download action; unsupported contact-format export does not prevent its separately intentional download. The action additionally requires current supported encryption usability. The asset contract's bounded v4/v6 matrix, version-specific fingerprints and REQUIRES FEASIBILITY VALIDATION rows govern support; a signing-only component is not encryption capability. Supported data-valid expired and verifiably revoked keys survive storage and full backup/restore; neither status alone makes valid bytes corrupt. No active action presents an expired/revoked key as currently usable. Preserve the saved display setting, but availability additionally requires saved, present and currently usable material. Existing N01/N04 inline status communicates revoked/unavailable; replacement/removal stays in N04 with explicit Save. Structural validity, required cryptographic integrity, current usability and identity trust remain independent; successful signature verification does not prove real-world identity. Unsupported historical versions/algorithms/packet structures or unverifiable required semantics reject the entire restore before replacement, not the key alone. Explain unsupported public-key format factually and leave all current saved data/settings/assets unchanged; no partial import, conversion or stripping. Unusual classification cases remain P0.5/P0.6 feasibility questions. Private-key rejection is unconditional; no KEY property is authorized.

## 4. Storage, card, contact and full-backup boundaries

1. **Stored:** all valid saved fields, assets and preferences, even when hidden. Unsaved invalid drafts are not promoted into saved state.
2. **Card:** saved present display-enabled content and corresponding approved actions; no hidden contact value in a button label, accessibility label, image annotation or fallback action.
3. **Contact QR/.vcf:** apply export visibility to each eligible field before composing properties. Images/key/hosted URL/appearance/internal metadata are not contact payloads under this approved specification. No hidden field is recovered from a biography, link label, key identity or other metadata by the serializer.
4. **Full backup:** complete saved profile, images, key, appearance and visibility, including hidden data. Explain this on N06 before location selection. Backup is not governed by contact-export visibility and is not encrypted/authenticated under this approved specification.

Filtering is field-based, not a semantic data-loss-prevention promise. If a user deliberately includes their phone inside an export-enabled biography, disabling the separate phone field does not redact that free text. S01 shows actual included content so the user can correct it. Never add a hidden field automatically to improve compatibility or QR capacity.

## 5. Hosted profile and unsupported fields

The hosted URL is independent configuration, not auto-published contact data. Its web QR/copy/share can disclose the hosted destination even though it has no contact-export switch. N02 must show the exact URL, internet requirement and hosted-content independence notice. Local switches neither change the website nor revoke earlier exports. Do not derive a hosted URL from website or extract hidden data from the web.

For a format-unsupported field, use non-applicable export state and explain Not included in contact QR or .vcf. S01 can explain omitted categories without printing their hidden values or enabling them. Name/phone/email/website and the supported metadata map exactly as in the vCard document. Assets remain locally retained and backup-eligible, not silently linked via network URIs in contacts.

## 6. Input/operation failure vocabulary and recovery

| Failure class | Suggested user-facing meaning | Required recovery |
|---|---|---|
| REQUIRED_NAME | Enter a full name | Keep draft, focus name; do not create fake profile |
| FIELD_TOO_LONG | Shorten this field to its stated limit | Retain value; no silent truncation |
| INVALID_EMAIL / PHONE / URL | Explain the specific supported format | Keep other edits; no network lookup |
| UNSUPPORTED_FORMAT | This file/format is not supported | Preserve prior asset/state; choose another |
| CONTACT_TOO_LARGE / QR_GEOMETRY | Contact QR cannot fit these selections safely | Explicitly edit export choices or use .vcf; never auto-switch modes |
| STALE_EXPORT | Saved information changed; review again | Regenerate projection and require the action's confirmation |
| STORAGE_OR_PROVIDER_FAILURE | Could not finish saving/reading | Retry or choose location; no false success |
| INVALID_BACKUP / UNSUPPORTED_VERSION | Backup cannot be restored | Keep valid state; choose compatible backup |
| OUTCOME_UNKNOWN | Completion could not be confirmed | Reconcile saved/output state before retry; no automatic duplicate operation |

These are error categories/copy guidance, not new UI destinations or logging payloads. Use approved inline C13/C14, S01/S02 and D01. Never display parser internals, raw key material, system paths or input excerpts in diagnostic logs. Accessibility labels must preserve privacy and honest state.
